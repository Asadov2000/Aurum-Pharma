# Восстановление сессии при работе в двух вкладках

Статус: frontend координирует refresh и один защищённый повтор одной origin
блокировкой `aurum:auth-cookie`. Backend, отзыв session ID и схема БД не меняются.
Access остаётся в памяти каждой вкладки, refresh — только в httpOnly cookie.

## Причина и исправление

Cookie общая для вкладок, а access — отдельный. Успешный refresh отзывает прежний
session ID. Раньше блокировка освобождалась после refresh, до ответа защищённого
повтора. Другая вкладка могла выполнить следующий refresh, и единственный повтор
первой снова получал 401. Изолированный тест настоящих frontend-модулей с моделью
ротации воспроизводит этот порядок без задержек: до исправления один запрос
отклонён, после — оба успешны.

Production bootstrap всегда устанавливает `recoverWithFreshAccess` и загружает
`features/auth/recovery.ts` только при восстановлении, сохраняя startup budgets. Его
`recoverSessionWithFreshAccess` использует `runCookieRequest` с callback, который
устанавливает токен и завершает один повтор до освобождения cookie-lock. Он не
ожидает прежнюю single-flight bootstrap promise, которая сама может ждать lock.
Обычный bootstrap refresh сохраняет существующее объединение параллельных вызовов.
Низкоуровневые DI-тесты API могут по-прежнему задавать только прежние hooks;
это не настройка runtime или способ включить небезопасный режим через UI/env.

Редкий координатор ответа `lib/apiResponseRecovery.ts` также загружается отдельно.
Проверки текущей authority и неактивного support session, а также отказ для
неповторяемых запросов остаются в основном API-модуле. Lazy-координатор не
импортирует session state: он получает явно связанные callbacks клиента и
повторно проверяет authority после загрузки, до refresh или диалога.
URL-модуль `sidebar-icons.svg` объединён с уже загружаемым AuthenticatedShell:
его потребители и раньше зависели от shell. SVG не меняется; отдельный стартовый
JS-запрос и повторные preload-ссылки исключены без повышения бюджетов.

## Обязательные границы

- До refresh под lock и перед повтором проверяются generation, logout epoch,
  support context и отмена запроса. После ответа сохраняются прежние проверки.
- Только ошибки самого refresh допускают прежние ограниченные сетевые повторы
  с тем же operation ID. Ошибка/таймаут исходной операции не повторяет мутацию
  и не трактуется как отказ refresh или команда выхода.
- `_retry` по-прежнему разрешает ровно один автоматический auth-повтор.
- MFA/password step-up выходит из lock до открытия диалога. Отмена проверяется
  до диалога и после ожидания; замена identity/support сохраняет прежний отказ.
- Recovery-повтор использует Axios timeout не более 30 секунд, сохраняя более
  короткий срок запроса. Первый запрос и глобальные таймауты не меняются.
  Отмена транспорта освобождает lock; `Promise.race` с продолжающейся мутацией нет.
- Logout, явный вход и другие cookie-запросы используют ту же блокировку.
  Возврат позднего ответа не восстанавливает закрытую или заменённую сессию.

Без Web Locks остаётся прежняя очередь одной вкладки и запрет небезопасного
восстановления после logout. Межвкладочная гарантия для такого браузера не заявляется.
Сериализованные recovery могут вызвать дополнительные refresh при всплеске 401;
новое межвкладочное хранение/рассылка токенов ради оптимизации не добавлены.

## Доказательства

`frontend/tests/lib/api.crossTab.test.ts` проверяет две независимые загрузки
реальных API/store/auth-модулей, общий FIFO lock и управляемую модель сервера.
`frontend/tests/features/auth/recovery.test.ts` проверяет отказы refresh, ошибки
повтора, logout, замену сессии, отмену, bootstrap, MFA и освобождение lock.

`frontend/e2e/auth-cross-tab-recovery.spec.ts` использует две страницы одного
browser context, настоящий UI-вход и API/БД одноразового CI-стенда. Transport
barrier задерживает повтор, пока вторая вкладка пытается обновить cookie.
Подставных 401/успешных ответов и тестовых backdoor в приложении нет; ожидаются
исходный 401, повторный 200 и успешная загрузка обеих вкладок. Токены/cookie тест
не читает; trace, screenshot и video авторизации выключены.

Эта гонка соответствует кандидату `AUTH-PARALLEL-BOOTSTRAP-01`. Точная причина
исторического CI3686 отдельно не установлена: совпадение класса сбоя не доказывает
идентичность старого interleaving. Изменения не являются deployment или допуском пилота.
