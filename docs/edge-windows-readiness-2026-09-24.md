# Edge read-only: Windows host и изолированный smoke, 2026-09-24

`scripts/windows-host-readiness.ps1` завершился успешно на текущем Windows-хосте:
Windows build 26200, Visual Studio с WinUI workload, .NET 8/10, Windows SDK,
MSBuild и Developer Mode доступны; отсутствующих компонентов нет. Это проверка
инструментов, не установленного продукта на целевом аптечном ПК.

`scripts/smoke-edge-cold-read.ps1` создаёт одноразовые PostgreSQL, Redis и Edge
API в уникальной внутренней Docker-сети без host ports, общих томов и Cloud.
Доступ к общей dev/demo БД отсутствует. После выполнения скрипт проверяет метки
принадлежности и удаляет только созданные им ресурсы.

Проверенный сценарий:

1. До установки подписанного snapshot `/healthz` возвращает 503.
2. После установки и криптографической проверки snapshot `/healthz` возвращает
   200; отдельный Edge read-model process читает 3 товара и 5 партий без Cloud.
3. При остановке тестового PostgreSQL `/healthz` возвращает 503; после запуска
   базы — 200. После перезапуска Edge API подписанные чтения снова доступны.

Отдельный запуск с `-VerifyMigration0151Downgrade` проверил переход
`0151 → 0150 → 0151` только в одноразовой БД; затем повторил тот же smoke.

Это **process/health smoke**, не пользовательский HTTP-вход и не автономная касса.
Текущий Edge Compose ещё не поставляет локальные API и frontend как Windows-службы,
а offline-вход, локальный backup/restore и денежный writer не готовы. Испытания
24 часа, 7 и 30 дней, перенос на запасной ПК, RPO/RTO и работа с реальным
оборудованием остаются отдельными условиями пилотного допуска. Cloud backup
не является Edge backup. Для полного Windows acceptance потребуется установленный
runtime на целевом ПК с 4 CPU, 8 GB RAM и SSD, а восстановление потребует
защищённого переноса credential и fencing старого узла.

Профилирование каталога на отдельной тестовой БД показало ошибку оценки планировщика
после массовой установки: для 10 000 строк он предполагал одну, выбирал bitmap
scan с сортировкой и читал первую страницу за ~80 мс. После `ANALYZE` тот же
RLS-запрос использовал первичный индекс и занял ~0,2 мс. Миграция 0151 добавляет
проверяемое обновление статистики до активации нового snapshot. Повторный
изолированный замер на 100 000 товарах, 250 000 партиях и 701 чанке: установка
267,4 с, предварительная проверка 13,8 с, первый готовый запрос 35,9 мс,
повторные запросы p95 13,1 мс; сама страница SQL p95 3,9 мс. Это ниже
ориентира 300 мс в данном тесте, но не означает приемку на целевом ПК.
