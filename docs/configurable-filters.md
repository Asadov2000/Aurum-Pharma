# Настраиваемые фильтры Aurum Pharma

## Цель

Фильтры должны помогать быстро находить рабочие данные на слабом компьютере и
при нестабильном интернете. Единый вид — строка поиска и панель условий справа
на компьютере, снизу на телефоне. Значения принадлежат конкретному разделу;
общий компонент отвечает за отображение, доступность и сброс.

## Правила интерфейса

- Поиск или главный идентификатор раздела остаётся видимым всегда.
- В отчётах проверяемые даты остаются в строке, чтобы ошибки периода были видны.
- Все доступные дополнительные условия находятся в панели; отдельного выбора
  видимости полей больше нет. Старый `defaultVisible` не влияет на раскладку.
- Метки под строкой показывают активные условия. `activeLabel` содержит понятное
  значение, а при его отсутствии используется название поля. Внутренние UUID
  не подставляются вместо неизвестного названия точки или кассы.
- Снятие метки вызывает `onClear`; «Сбросить» возвращает значения к исходным
  условиям раздела (например, к активным точкам или текущему месяцу).
- Число рядом с кнопкой «Фильтры» показывает количество активных условий.
- «Готово», крестик, фон и `Escape` закрывают панель с сохранением выбора.
- Панель использует общий `Modal`: фокус остаётся внутри, после закрытия
  возвращается к кнопке; блокировка прокрутки страницы общая с другими окнами.
  Длинное содержимое прокручивается отдельно, нижние действия остаются видимыми
  и учитывают безопасную область телефона.
- Строковый поиск отправляется после паузы 300 мс. На тяжёлых отчётах фильтры
  применяются кнопкой, чтобы не выполнять запрос после каждого ввода.

## Конфиденциальность и разделение данных

Общий компонент больше не читает и не записывает `localStorage`. Старые ключи
раскладки игнорируются и не могут скрывать условия:

```text
aurum:filter-layout:v1:<user_id>:<tenant_id>:<screen>
```

Значения фильтров не сохраняются компонентом между перезагрузками. Контекстный
`preferenceKey` сохраняется для пересоздания состояния панели при смене
пользователя, аптеки или раздела. Доступность поля определяется разрешениями:
скрытое правами поле нельзя вернуть через старую настройку.
Если разрешение отозвано во время открытой сессии, поле убирается из панели,
его активное значение очищается через `onClear`.

## Реализованные разделы

Компонент используется в каталоге, партиях, приходах, чеках и возвратах,
сверке платежей, аудите, уведомлениях, сотрудниках и ролях, аптеках, точках,
кассах, поставщиках, отчётах, биллинге и платформенных списках. Набор условий
объявляет сам раздел; единый вид не расширяет его параметры API. Если у списка
есть только поиск, пустая кнопка открытия панели не показывается.

Поля «аптека», «пользователь», «точка», «касса» и «поставщик» появляются только
при наличии соответствующего разрешения или области просмотра.

## Серверный контракт

Настраиваемая панель не означает произвольный конструктор SQL. Каждый раздел
объявляет собственный типизированный список разрешённых параметров. Сервер:

- принимает только известные поля и операторы;
- валидирует даты, денежные диапазоны, UUID и максимальную длину строк;
- применяет `tenant_id`, RLS и область разрешений независимо от интерфейса;
- использует параметризованные запросы без подстановки SQL-фрагментов;
- ограничивает размер страницы и добавляет `id` как стабильный второй ключ
  сортировки;
- отвечает `422` на неизвестные или несовместимые параметры.

Управленческие списки используют отдельные `POST /search` endpoints. Значения
поиска передаются в JSON-теле, не попадают в URL и стандартный access-log.
Ответы помечаются `Cache-Control: private, no-store`, а frontend отменяет
устаревший запрос при быстром изменении строки. Старые компактные `GET`-списки
сохранены для выпадающих полей и совместимости рабочих экранов.

Такой контракт защищает от SQL-инъекций, обхода прав и чрезмерно дорогих
запросов, даже если запрос отправлен вручную без интерфейса.

## Где фильтры не нужны

Настраиваемую панель не добавляем в кассу POS, вход, онбординг, настройки,
карточку одного документа и мастер создания. На этих экранах она отвлекает от
одной основной операции и увеличивает риск ошибки кассира.

## Дальнейшее развитие

Именованные наборы вроде «Просрочка моей точки» можно хранить на сервере после
утверждения отдельной модели прав. Такой набор должен сохранять только
разрешённые поля, иметь владельца и область видимости, проходить повторную
валидацию при каждом открытии и автоматически удалять условия, к которым
пользователь потерял доступ. Общие наборы для аптеки сможет публиковать только
пользователь с отдельным разрешением.
