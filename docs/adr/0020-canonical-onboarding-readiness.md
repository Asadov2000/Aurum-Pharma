# ADR 0020: Каноническая готовность и одноразовый trial

- Статус: принято
- Дата: 2026-08-21
- Связано: ADR-0009, ADR-0017, ADR-0019

## Контекст

Экран «Старт» использовал ручные отметки и счётчик каталога из
`onboarding_checklist`. Эти проекции могли расходиться с фактическими точками,
лицензиями, кассами, товарами и настройками. Ручной и автоматический запуск
пробного периода выполнялись разными переходами, поэтому повтор запроса или
гонка могли создать несколько подписок либо частично изменить состояние.

## Решение

1. Готовность вычисляется только из таблиц доменов, которым принадлежат данные:
   tenant, ownership/membership, branch, register, settings, catalog, incoming,
   sale, shift и subscription.
2. API возвращает один согласованный snapshot готовности. UI не позволяет
   вручную отмечать обязательные шаги и показывает действия только по доступным
   пользователю маршрутам.
3. `wizard_state` и `onboarding_checklist` остаются совместимыми проекциями для
   истории и необязательных событий. Они не могут сделать неготовую аптеку
   готовой к запуску.
4. Trial запускается один раз. Факт фиксирует неизменяемый
   `trial_activation`; существующие trial-активации мигрируются в этот журнал.
5. Ручной и автоматический запуск используют один сервисный переход, один
   порядок блокировок и одну транзакцию. В ней согласованно создаётся подписка,
   меняется tenant, завершаются проекции онбординга и записывается активация.
6. Ручной запуск требует активного владельца и действующей auth-сессии. Эти
   условия повторно проверяются после блокировки и внутри ограниченной
   `SECURITY DEFINER` DB-команды.
7. Каждый запрос запуска имеет UUID операции. Повтор уже завершённой активации
   возвращает существующий результат и не создаёт новую подписку.
8. Автоматический запуск после окончания setup выполняется только для полностью
   готовой аптеки. Неготовая аптека остаётся в setup и должна получить отдельное
   напоминание; частичный запуск запрещён.
9. Цена следующего платного периода определяется контуром версионного биллинга
   по ADR-0017. Онбординг не получает обход platform approval для применения
   цены.
10. Лицензия, реквизиты чека и активная касса должны образовывать одну готовую
    физическую точку. Нельзя собрать ложную готовность из трёх разных филиалов.
11. Перед активацией сервис блокирует строки, из которых рассчитана готовность:
    точку, кассу, настройки, активного владельца и достаточный набор каталога.
    Поэтому обязательное условие нельзя отозвать между проверкой и commit.

## Последствия

- Экран показывает фактическое состояние и не создаёт ложную готовность.
- Слабая сеть и повтор нажатия не приводят к двойному trial или подписке.
- Удаление или изменение обязательной настройки до запуска немедленно снова
  блокирует запуск.
- Заблокированный аккаунт владельца не считается активным владельцем, даже если
  membership и ownership ещё не отозваны.
- Запрос готовности сложнее одного счётчика, но выполняется одним обращением к
  PostgreSQL и использует tenant-ограниченные подзапросы.
- Напоминания для просроченного, но неготового setup остаются отдельной задачей;
  они не должны менять billing или tenant state.
