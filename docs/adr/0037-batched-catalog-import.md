# ADR-0037: Пакетная запись каталога с построчным восстановлением

- Статус: принято
- Дата: 2026-09-08
- Связано: ADR-0034, ADR-0035, ADR-0036, миграция 0143
- Уточняет пункт 5 ADR-0034 о savepoint при применении строк.

## Причина

Разбор файла не доказывал скорость записи каталога. Полный синтетический импорт
15 000 товаров со штрихкодами не завершился успешно за 170 секунд наблюдения
при неизменных production-лимитах обработчика. Для каждой строки выполнялись
отдельные поиск дубликата, savepoint и операции записи. Кроме того, повторный
импорт существующего штрихкода ошибочно отклонял ту же связь с товаром.

## Решение

1. Внешняя транзакция по-прежнему охватывает весь импорт. Тайм-ауты 120/150 секунд,
   deadline 600 секунд, tenant slot, durable claim и ограничения ресурсов
   сохраняются. Увеличение лимитов не является способом ускорения импорта.
2. Для обычных больших файлов применяется ограниченная пакетная обработка.
   Поиск существующих товаров и штрихкодов выполняется для пакета; записи и
   проверки владельцев кодов находятся в одном savepoint пакета.
3. Неоднозначные дубликаты, повторяющиеся ключи и конфликты требуют прежней
   последовательной обработки. Неуспешный пакет сначала откатывается целиком,
   затем строки обрабатываются в исходном порядке с отдельными savepoint.
   Сигнал тайм-аута проходит наружу и не запускает повторную обработку.
4. Штрихкод, уже принадлежащий тому же товару и аптеке, принимается повторно.
   Код другого товара остаётся конфликтом: откатываются и изменения карточки.
   Обычное ручное добавление штрихкода не меняет свой контракт.
   Новые связи подтверждаются результатом `INSERT RETURNING`; после
   `ON CONFLICT DO NOTHING` отдельный запрос проверяет только спорные коды.
   Отдельный запрос необходим, чтобы увидеть результат конкурирующей транзакции
   в новом снимке `READ COMMITTED`. Полная проверка принадлежности сохраняется.
5. Права worker не расширяются. Идентификаторы товаров генерирует БД;
   сопоставление результата пакетного INSERT с входом не зависит от порядка
   RETURNING. Такой порядок не гарантируется
   [SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/queryguide/dml.html#correlating-returning-records-with-input-data-order).
6. Обновление сохраняет правило «пустое поле не затирает существующее».
   Полностью неизменённая карточка не получает лишнюю запись UPDATE в аудит.
   Триггерный аудит и RLS остаются действующими для всех пакетных запросов.
7. Неуникальный частичный индекс `(tenant_id, lower(brand_name))` ускоряет поиск
   активных товаров. Он не запрещает создание копий и не меняет сравнение
   PostgreSQL `lower()` с нормализованным входным именем.

## Доказательства и границы

`scripts/benchmark-catalog-write.ps1` создаёт собственные PostgreSQL, Redis,
MinIO и Celery, применяет штатные миграции и роли. Общая dev/demo БД и её файлы
не используются. Контроллер проверяет конечные данные свежими транзакциями,
точные связи и идентификаторы штрихкодов, аудит и неизменность другой аптеки.
Измеряются время до наблюдения commit и пик памяти всего контейнера worker.

CI использует небольшой полный сценарий; он не заменяет замер пилотного объёма.
Нагрузочные результаты относятся к зафиксированным синтетическим данным,
исходникам и ресурсам стенда. Они не доказывают производительность staging,
одновременных импортов разных аптек или юридический допуск.

После hard timeout состояние может оставаться `importing` до восстановления
через API после deadline. Read-only наблюдение benchmark не запускает это
восстановление. Отсутствие успешного завершения нельзя интерпретировать как
отключённый тайм-аут; для отката отдельно проверяются lock и сохранённые данные.
