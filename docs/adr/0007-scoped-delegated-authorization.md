# ADR-0007: Контекстная авторизация и безопасное делегирование прав

- Статус: принято
- Дата: 2026-07-17
- Заменяет модель уровней ролей из `docs/spec-v3.md`
- Уточняет ADR-0005 и ADR-0006

## Контекст

Aurum Pharma является multi-tenant системой: один глобальный аккаунт может
работать только через явно разрешенную связь с конкретной аптекой. Внутри
аптеки доступ дополнительно ограничивается филиалами.

Текущая модель `level = 1..4` смешивает четыре разных понятия:

- системное доверие к Developer и Aurum Administrator;
- владение аптекой;
- рабочую роль сотрудника;
- возможность передавать права другим.

Из-за этого владелец может создавать только роли условного четвертого уровня,
а permissions из разных branch-назначений объединяются без сохранения области
действия. Кроме того, создание глобального аккаунта и назначение сотрудника
сейчас являются одной операцией.

Продукт должен оставаться конструктором. Названия должностей не определяют
доступ. Готовые варианты являются только необязательными шаблонами, которые
копируют начальный набор галочек.

## Решение

### 1. Корни доверия не являются пользовательскими ролями

`Developer`, `Aurum Administrator` и `Tenant Ownership` являются защищенными
типами полномочий. Их нельзя создать, изменить или назначить через обычный
конструктор ролей.

- Только Developer создает, изменяет и отзывает platform-доступ Developer и
  Aurum Administrator.
- Aurum Administrator создает tenant-аккаунты, tenant membership и первоначальное
  владение. При наличии отдельной platform capability он также может пригласить
  непривилегированного кандидата команды Aurum Pharma, но не может назначить ему
  platform-доступ Developer/Administrator или изменить собственные полномочия.
- Platform-доступ Developer/Administrator создается, изменяется и отзывается
  только защищенным Developer workflow. Приглашение кандидата само по себе не
  дает ни одной platform capability.
- Владелец создает роли и назначает их только активным membership своего tenant.
- Передача владения выполняется отдельным подтверждаемым workflow. В tenant
  всегда остается хотя бы один активный владелец.

Полная свобода Developer означает максимальный предел platform-делегирования,
но не разрешает отключать аудит, нарушать tenant isolation, изменять завершенные
продажи или обходить обязательные подтверждения.

### 2. Аккаунт отделяется от сотрудника аптеки

Целевая модель содержит отдельные сущности:

- `app_user` - глобальная идентификация, аутентификация, MFA и глобальный статус;
- `tenant_membership` - связь аккаунта с tenant и tenant-статус
  `pending | active | suspended | offboarded`;
- `tenant_ownership` - защищенное владение tenant;
- `access_role` - tenant-scoped набор capabilities;
- `role_assignment` - назначение версии роли membership в явной области;
- `platform_access_grant` - platform-полномочия Developer/Administrator;
- `support_session` - временный доступ support-пользователя к выбранному tenant.

Профиль сотрудника, его блокировка и увольнение относятся к membership, а не к
глобальному аккаунту. Tenant API не ищет глобальные аккаунты по email и не может
самостоятельно прикрепить существующий аккаунт другого tenant.

В пилоте обычный tenant-аккаунт принадлежит одному tenant. Схема membership
сохраняет возможность безопасно поддержать несколько tenant позднее.

### 3. Capability хранит область и правило делегирования

Числовые `role.level` и `permission.min_level_required` больше не являются
источником авторизации. Для каждой capability хранятся:

- код и рабочая группа;
- допустимая область: `PLATFORM`, `TENANT_ALL`, `BRANCH_SET` или `OWN`;
- целевой тип роли: platform или tenant;
- уровень риска: `normal`, `sensitive` или `critical`;
- кто может использовать capability;
- кто может делегировать capability;
- необходимость step-up MFA и дополнительного подтверждения.

Право использовать действие и право передавать его другому пользователю -
разные полномочия. Итоговый набор новой или измененной роли обязан быть
подмножеством текущего `delegation envelope` актера в том же tenant и scope.

### 4. Scope является частью каждого решения

Авторизация проверяет пару `(capability, resource scope)`, а не глобальный
`set[str]`.

- `TENANT_ALL` задается явно и никогда не кодируется как неоднозначный `NULL`.
- `BRANCH_SET` содержит явный непустой список разрешенных филиалов.
- Permission из филиала A не дает доступ к филиалу B.
- Tenant-wide permission не выводится из наличия любого tenant-wide assignment:
  scope хранится и проверяется для каждой capability.
- Любой lookup по ID дополнительно ограничивается текущими tenant и branch.
- Frontend-проверки используются только для UX; сервер проверяет каждый запрос.

### 5. Конструктор получает только доступный каталог

Сервер возвращает не полный каталог capabilities, а только:

`active capabilities ∩ target scope ∩ actor delegation envelope`.

- Developer видит полный каталог в разрешенном им контексте.
- Administrator не получает Developer/Administrator capabilities, которые не
  может передавать.
- Owner получает только tenant capabilities, разрешенные для сотрудников его
  tenant.
- Пользователь без доступа к конструктору не получает маршрут, пункт меню и API.
- Подделанный запрос с отсутствующей в каталоге capability отклоняется и
  записывается как authorization failure.

Шаблоны фильтруются тем же серверным каталогом. Применение шаблона копирует
разрешенный набор в черновик и никогда не обходит итоговую серверную проверку.

Если редактор больше не имеет права управлять существующей ролью, роль нельзя
молча пересохранить с урезанным скрытым набором. Изменение блокируется без
раскрытия недоступных capability.

### 6. Роли публикуются версиями

Редактирование активной роли создает новую неизменяемую версию. Перед
публикацией интерфейс показывает diff и количество затронутых memberships.
Публикация выполняется одной транзакцией с optimistic concurrency check.

Архивировать роль с активными назначениями можно только вместе с явной заменой.
Изменение роли, назначения, membership или ownership увеличивает существующие
`policy_revision` и `subject_revision`.

Решение реализовано миграцией `0117`: `access_role_version` хранит immutable
снимок опубликованного определения, `access_role_version_permission` - его
capabilities, а каждое `user_assignment` закреплено одновременно за ролью и
конкретной опубликованной версией. Публикация переводит предыдущую версию в
архив, обновляет активные назначения и revisions в одной DB-транзакции.
Прямое изменение опубликованных снимков запрещено DB guard даже support-роли.

### 7. Опасные операции

Для critical capabilities, изменения platform-доступа, владения, полного
экспорта и запуска support session обязательны:

- недавняя MFA-аутентификация;
- явное отображение значимых параметров операции;
- ограниченный срок подтверждения;
- причина действия;
- неизменяемый audit event.

Создание или повышение Developer/Administrator и передача владения требуют
второго подтверждающего, когда в системе есть второй подходящий субъект.
Emergency-доступ является отдельным персональным break-glass workflow и всегда
создает оповещение.

### 8. Support-доступ

Support-пользователь не получает постоянный неограниченный tenant-контекст.
Developer или Administrator выбирает tenant, указывает причину и запускает
короткую `support_session` с явным набором capabilities. По умолчанию сессия
read-only. В интерфейсе постоянно отображаются tenant, причина и срок.

BYPASSRLS остается только внутренним механизмом выделенного DB-пула. Сам факт
соединения через support-пул не считается разрешением бизнес-операции.

### 9. Offline

Конструктор, account lifecycle, role lifecycle, ownership и support capabilities
никогда не доступны offline. Будущий offline grant из ADR-0005 содержит только
закрытый набор узких POS-команд и точные tenant/branch/register/user scope.
Отзыв ограничивается authorization revisions, сроком grant и следующей
синхронизацией; мгновенный Cloud-отзыв при полном отсутствии связи невозможен.

### 10. Аудит

Неизменяемый аудит покрывает:

- создание и изменение account security state;
- membership, invitation и ownership lifecycle;
- platform grants и support sessions;
- role draft/version/publish/archive;
- точный before/after diff role capabilities;
- assignment и scope;
- отклоненные попытки повышения полномочий.

Событие содержит IDs, revisions, actor, tenant, branch scope, request ID, причину
и результат. Email, телефон, секреты и токены в аудит не записываются.

## Миграция

1. Добавить новые таблицы и capability metadata без удаления текущих данных.
2. Создать membership и ownership из существующих tenant-аккаунтов и owner
   assignments.
3. Перенести tenant roles в versioned access roles и явные scopes.
4. Перевести серверные проверки на scoped authorization snapshot.
5. Перевести UI и API создания аккаунтов, команды и конструктора.
6. После сравнения результатов отключить legacy `level`, support bypass и
   tenant endpoint, создающий `app_user`.
7. Удалять legacy-поля только отдельной последующей миграцией.

Каждый этап обязан быть обратно совместимым до переключения чтения, иметь
рабочий `downgrade()` и проверяться на одноразовой тестовой БД. Общая dev-БД
только обновляется вперед.

## Обязательные проверки

- Admin не получает Developer-only capability и global audit.
- Owner не создает аккаунт и не связывает чужой email.
- Нельзя назначить или изменить собственные полномочия.
- Нельзя создать эквивалент Owner/Admin/Developer через набор capabilities.
- Permission и данные филиала A не действуют в филиале B.
- Tenant A не видит memberships, roles и assignments tenant B.
- Concurrent revoke побеждает начатое, но не подтвержденное расширение роли.
- Устаревшая публикация роли отклоняется, а история версий не изменяется.
- Архивирование роли с активными назначениями требует опубликованную замену.
- Invitation является одноразовым, tenant-bound, истекаемым и отзывным.
- Последний Owner не может быть удален или приостановлен.
- Изменение роли немедленно меняет online authorization revision.
- Шаблон и прямой API-запрос не обходят delegation envelope.
- Audit хранит точный diff и остается неизменяемым.

## Последствия

Плюсы:

- конструктор становится действительно свободным для рабочих ролей;
- platform, tenant и branch границы невозможно смешать названием или уровнем;
- owner и support lifecycle отделены от обычных ролей;
- UI получает минимальный безопасный каталог;
- модель совместима с будущим Edge/offline контуром.

Цена:

- необходима поэтапная миграция auth/roles и связанных тестов;
- scoped snapshot сложнее текущего множества строк;
- role versioning увеличивает число записей;
- support workflow требует отдельного UI и MFA.

Эта сложность принимается, потому что исправление только frontend или добавление
новых числовых уровней не устраняет privilege escalation и cross-branch риски.
