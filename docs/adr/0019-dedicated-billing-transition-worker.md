# ADR 0019: Изолированный worker переходов подписки

- Статус: принято
- Дата: 2026-08-19
- Связано: ADR-0009, ADR-0015, ADR-0017

## Контекст

Автоматические переходы `trial -> grace_period` и
`grace_period -> suspended` выполнялись общим Celery-процессом через
`aurum_support` с `BYPASSRLS`. Компрометация одной фоновой задачи давала доступ
ко всей БД, а раздельные чтение и ORM-обновление создавали гонку с подтверждением
оплаты, которое может одновременно восстановить подписку и доступ аптеки.

Эти два перехода не являются денежными командами: они не создают счёт, платёж,
проводку или корректировку. Поэтому им не нужен пользовательский MFA/approval,
но нужна отдельная машинная граница с минимальными правами и сериализация с
денежным контуром.

## Решение

1. Переходы обслуживает отдельный процесс и очередь `billing-worker`.
2. Процесс получает только `DATABASE_URL_BILLING_WORKER` и `REDIS_URL`; JWT,
   app/support/migrator credentials, MinIO и SMTP ему не передаются.
3. PostgreSQL-роль `aurum_billing_worker` имеет только `CONNECT`, `USAGE` схемы
   и `EXECUTE` двух точных DB-команд. У неё нет membership, прямых прав на
   таблицы/sequence, `BYPASSRLS`, `CREATE` или `TEMP`.
4. Команды являются `SECURITY DEFINER`, принадлежат `aurum_schema_owner`,
   проверяют `SESSION_USER`, используют фиксированный `search_path`, полностью
   квалифицированные имена и только серверное время.
5. Worker не передаёт tenant, статус, срок или grace-период. Он передаёт только
   ограниченный размер пакета `1..100`.
6. Перед изменением конкретной подписки команда берёт advisory locks `9603`,
   затем `9701`, и повторно проверяет состояние после блокировки. Это тот же
   порядок, который используют применение цены и подтверждение оплаты.
7. Повтор безопасен: переход выполняется только из точного исходного статуса.
   Существующие audit-триггеры фиксируют фактическое изменение.
8. Архивная аптека никогда не возвращается в `readonly`.
9. Будущие денежные фоновые операции не могут расширять эти команды. Для них
   остаётся обязательным отдельное неизменяемое задание с operation ID, request
   hash и approval по ADR-0017.

## Последствия

- Утечка DB-учётных данных billing worker не даёт чтения tenant или
  финансового журнала.
- Общий Celery worker больше не может выполнять billing queue.
- Параллельное подтверждение оплаты и блокировка подписки сериализуются.
- Остановка billing worker задерживает только плановые переходы и не мешает API
  или кассе; после восстановления повтор задачи безопасен.
- Добавляются отдельный секрет, контейнер и обязательные ACL/concurrency-тесты.
- Redis пока остаётся общим транспортом Celery, поэтому его учётные данные не
  считаются отдельной границей доверия. До production нужен отдельный broker
  или Redis ACL, ограничивающий billing-процесс его очередью; это не расширяет
  права DB-роли из данного решения.
