# ADR-0034: Ограниченная обработка файлов каталога

- Статус: принято
- Дата: 2026-09-07
- Связано: ADR-0030, миграции 0133 и 0141

## Причина

Импорт уже имел отдельный процесс, тайм-ауты и один активный импорт аптеки.
Однако предпросмотр разбирал файл в процессе API, а общий обработчик ошибок
строки мог поглотить сигнал тайм-аута. Принудительное завершение процесса не
гарантирует выполнение его обработчика ошибки.

## Решение

1. API только сохраняет файл и ставит предпросмотр в `catalog-worker` после
   commit. Фаза `previewing` означает обработку; `validating` — готовый результат.
   Подтверждение допускается после предпросмотра с корректными строками.
2. Предпросмотр и импорт делят один активный слот аптеки. Tenant advisory lock
   сериализует допуск, частичный уникальный индекс защищает инвариант в БД.
3. Каждая фаза получает новый UUID исполнения и неизменяемый deadline 10 минут,
   включая ожидание очереди. Повтор того же запроса не продлевает deadline.
4. Worker держит session advisory lock на одном физическом PostgreSQL-соединении
   через две транзакции: запись начала исполнения, затем разбор и применение.
   UUID, tenant и фаза проверяются до чтения объекта. Дубликат при занятом lock
   завершается без чтения; доставка после потери процесса обнаруживает записанное
   начало и завершает задание ошибкой, не разбирая файл повторно.
   Если новая фаза поступила до освобождения lock предыдущей, допускаются пять
   повторов получения lock с интервалом секунду. Это повтор допуска к работе,
   а не повтор разбора файла; deadline остаётся прежним.
5. Применение строк — одна транзакция с savepoint для допустимых ошибок строки.
   Soft timeout проходит наружу и откатывает всю транзакцию. Превышение deadline
   перед commit также запрещает частичный успех. Ошибка фиксируется отдельно.
6. Тайм-ауты задачи: 120 секунд мягкий и 150 секунд принудительный. Потерянная
   постановка в очередь или неподтверждённая доставка восстанавливается при
   запросе статуса/новом запуске: после deadline свободный execution lock
   позволяет перевести задание в `failed`. Это восстановление по обращению,
   а не независимый планировщик. Живой worker не блокирует запрос статуса.
7. Загрузка и повторное чтение объекта ограничены 10 MiB; настройка API может
   уменьшить этот предел. Сохраняются лимиты 50 000 строк, 64 колонки, 2048
   ZIP-записей и 128 MiB распакованного XLSX. Production worker имеет пределы
   памяти/CPU контейнера. Парсер не получает HTTP/support-секреты.
8. Браузер опрашивает обе активные фазы, восстанавливает сохранённое задание,
   сверяет статус после потерянного ответа и обновляет каталог после успеха.
   Автоматического повторного подтверждения импорта нет.
9. В логи попадают только ID задания, тип ошибки и числовые результаты.
   За границу Celery выходит фиксированная ошибка без исходного сообщения.

## Проверки и ограничения

Тесты проверяют реальные конкурирующие транзакции, tenant-изоляцию, дубликаты,
потерю дочернего процесса, rollback при тайм-ауте, восстановление слота и UI.
`backend/scripts/benchmark_catalog_import.py` воспроизводит расход ресурсов
парсера на синтетических CSV/XLSX и отказы на превышение границ.

Миграция сохраняет прежние задания и файлы. Сообщения старого формата без UUID
не исполняются новым worker; прежние активные задания получают 10 минут до
восстановления и требуют новой загрузки. При обновлении остановить обработку
каталога, применить миграцию и запустить согласованные версии API/worker/UI.

Ресурсный замер парсера не доказывает скорость записи 50 000 товаров в БД или
суммарную память всех процессов Celery. Отдельная DB-роль, read-only MinIO
credentials, сети/Redis ACL из ADR-0030 и внешний допуск пилота остаются открытыми.
