# ADR-0001: Cloud + Branch Edge

- Статус: принято
- Дата: 2026-07-12
- Решение для: offline POS, Windows-клиент, web-клиент и синхронизация филиала

## Контекст

Aurum Pharma сейчас является online-first приложением: React-клиент обращается к
Cloud API, а PostgreSQL в облаке хранит рабочие данные. PWA кэширует только
статические файлы. Локальной финансовой БД, очереди продаж и sync-протокола нет.

Для аптек Таджикистана зависимость кассы от WAN неприемлема. При этом очередь
денежных операций только в IndexedDB не дает достаточных гарантий сохранности,
идемпотентности, конкурентного складского учета и восстановления после сбоя.

## Решение

На каждой физической точке работает один Aurum Edge:

- Edge-профиль существующего FastAPI backend;
- локальный PostgreSQL;
- локальная раздача собранного React frontend;
- sync worker для обмена с Aurum Cloud;
- адаптер сертифицированной ККУ или фискального модуля;
- локальные health checks, backup и recovery.

Кассовый клиент всегда обращается к Edge, даже когда интернет исправен. Потеря
WAN поэтому не меняет путь продажи и не требует переключения режимов.

Для одной кассы пилотный Edge может работать на том же Windows-ПК. Для двух и
более касс используется выделенный mini-PC, проводная LAN и UPS. Клиенты никогда
не подключаются к PostgreSQL напрямую.

## Почему PostgreSQL

Финансовая БД Edge использует PostgreSQL, а не SQLite. Текущий домен зависит от
RLS, JSONB, триггеров складских движений и `SELECT FOR UPDATE`. Второй движок БД
потребовал бы второй реализации наиболее критичных бизнес-правил и увеличил бы
риск расхождения Cloud и Edge.

SQLite допускается только для некритичных настроек Windows host, если такая
потребность появится. Он не является журналом продаж или платежей.

## Владение данными

| Владелец записи | Данные | Вторая сторона |
|---|---|---|
| Cloud | пользователи, роли, tenant, branch, register, настройки, каталог, штрихкоды, suppliers, billing | Edge получает версионированные snapshots и команды |
| Branch Edge | смены, продажи, возвраты, оплаты, чеки, остатки филиала, приходы, списания и fiscal operations | Cloud получает read-only проекцию |
| Узел происхождения | append-only audit с actor, node, sequence и временем | Cloud хранит проверяемую копию |

Cloud не изменяет Edge-owned остатки напрямую. Управленческое действие для
филиала становится версионированной командой Edge. Edge не редактирует
Cloud-owned справочники самовольно.

## Single writer

Для operational-данных филиала существует ровно один writer. Он не меняется при
пропадании или восстановлении интернета. Несколько независимых Edge для одного
остатка запрещены.

Аварийная передача writer выполняется контролируемо:

1. старый Edge останавливается;
2. проверяются backlog, backup и checksum;
3. увеличивается `writer_epoch`;
4. новый Edge активируется;
5. Cloud отклоняет события старого epoch.

Автоматический active-active failover без consensus-протокола не используется.

## POS-инварианты

- Подтвержденная продажа неизменяема.
- Исправление и возврат являются новыми связанными операциями.
- Один `operation_id` создает не более одного бизнес-эффекта.
- Повтор с тем же payload возвращает прежний результат.
- Повтор с тем же ключом и другим payload отклоняется как конфликт.
- Остаток партии не становится отрицательным.
- Номера внутренних и фискальных чеков хранятся раздельно.
- Неизвестный результат платежа или fiscal-команды не повторяется вслепую.
- Cloud не подтверждает событие до durable commit.
- Неоднозначное состояние получает статус `requires_reconciliation`.

Продажа фиксируется одной атомарной командой-агрегатом: позиции, выбранные партии,
price snapshot, оплаты, рецепт, движения, внутренний чек и outbox. Текущая цепочка
REST-запросов draft/items/payment/complete сохраняется до внедрения этой команды,
но получает транзакционные блокировки и идемпотентность.

## Синхронизация

Используются PostgreSQL transactional outbox/inbox и доставка `at-least-once`.
Однократный эффект обеспечивают уникальные ключи:

- `operation_id`;
- `event_id`;
- `origin_node_id + writer_epoch + sequence`;
- `payload_hash`.

Edge инициирует исходящие HTTPS-соединения. Push идет небольшими возобновляемыми
пакетами. Pull использует cursor. Потерянный ACK приводит к безопасному повтору.
Пропуск sequence останавливает watermark и запускает replay. Периодические
snapshot/checksum выявляют расхождения.

Last-write-wins для финансовых и складских данных запрещен. Конфликты устраняются
разделением владельцев, а некорректное событие попадает в quarantine. Cloud-отчеты
показывают момент последней успешной синхронизации.

## Клиенты

Windows POS использует WinUI 3 + WebView2 и загружает подписанную локальную сборку
React. Windows host отвечает только за lifecycle, принтер, сканер, денежный ящик
и строго типизированный bridge. Он не владеет продажами и sync.

Браузер владельца работает с Cloud. Браузер кассира в LAN в будущем может работать
с Edge API. Service Worker и IndexedDB не являются единственным хранилищем денег;
там допустимы только статические assets, безопасный UI-cache и черновики.

## Безопасность Edge

- device enrollment с привязкой к tenant, branch и register;
- отдельный сертификат каждого устройства и mTLS;
- неэкспортируемый ключ в TPM, защита через DPAPI и BitLocker;
- кассир работает без прав администратора Windows;
- подписанный installer, manifest и updater с защитой от downgrade;
- RLS и минимальные DB-привилегии; support BYPASSRLS на Edge не выдается;
- access/refresh tokens, пароль и приватные ключи не хранятся в web storage;
- backup шифруется и регулярно проверяется восстановлением;
- рецептурные и персональные данные реплицируются только при необходимости.

Offline-auth Aurum не является разрешением на нефискальную продажу. Действующий
порядок ККУ требует передать сформированные разрешённым фискальным механизмом
offline-чеки оператору в течение 24 часов. Более короткий предел может задать
провайдер или политика безопасности; более длинный предел запрещён без нового
официального основания. Перевод системных часов назад не продлевает разрешение.

## Фискальная граница

Фискальную команду создает только Edge. Cloud и Windows host не повторяют ее
самостоятельно. Неопределенный результат запрашивается у ККУ/ОФД по тому же
`operation_id`.

До реального пилота требуется официальный SDK/API и подтвержденный offline-режим
сертифицированного провайдера. Внутренний чек Aurum не заменяет фискальный чек.
Основания: [Постановление Правительства РТ №638](https://www.andoz.tj/docs/boju_hiroj/%E2%84%963%281514%29%2015.01.2026.pdf)
и [Налоговый кодекс РТ, статья 85](https://ncl.tj/node/1605). Постановление
Правительства №432 от 09.10.2021 признано утратившим силу.

## Отказы и восстановление

- WAN outage: POS продолжает локальные наличные продажи.
- Потерянный ACK: событие отправляется повторно без второго эффекта.
- Power loss: транзакция целиком сохранена либо целиком откатана.
- Printer failure: повторно печатается тот же чек.
- Disk full/corruption: новые внешние эффекты блокируются, Edge переходит в recovery.
- Edge/LAN failure: используется утвержденная аварийная процедура через
  сертифицированную ККУ; импорт выполняется только при наличии официального API.
- Физическая потеря всей аптеки во время offline: абсолютный RPO 0 невозможен без
  синхронной второй физической копии или внешнего канала.

Для первого пилота обязательны UPS, проводная LAN и резервный 4G-канал. 4G ускоряет
sync, но POS от него не зависит.

## Rollout

1. Исправить cloud-инварианты POS и добавить реальные конкурентные тесты.
2. Ввести атомарную online-команду продажи и operation idempotency.
3. Реализовать read-only Edge и shadow sync со сверкой checksum.
4. Перевести одну кассу на Edge-owned наличные продажи.
5. Проверить несколько касс, WAN/LAN/power/disk faults и backup restore.
6. Подключить подтвержденный fiscal adapter.
7. Провести ограниченный коммерческий пилот и только затем расширять offline-функции.

В первой offline-версии не поддерживаются карты с неизвестным статусом, offline-
возвраты, изменение цен/ролей, billing и межфилиальные перемещения.

## Последствия

Преимущества: касса не зависит от WAN, используется один backend-домен, финансовые
правила остаются в PostgreSQL, а web и desktop разделяют UI.

Стоимость: Edge становится отдельным продуктовым компонентом, требующим installer,
обновлений, мониторинга, backup/recovery, device PKI и службы поддержки оборудования.
