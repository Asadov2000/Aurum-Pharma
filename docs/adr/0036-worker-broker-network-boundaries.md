# ADR-0036: Очереди Redis и сети фоновых обработчиков

- Статус: принято
- Дата: 2026-09-07
- Связано: ADR-0030, ADR-0034, ADR-0035

## Причина

Разделение PostgreSQL-ролей и ключей MinIO не ограничивало общий пароль Redis.
Обработчик мог читать чужие очереди и прикладной кэш; общая сеть давала прямой
доступ ко всем внутренним ресурсам. Отправка импорта из API также импортировала
конфигурацию обработчика, хотя API не должен получать его секреты.

## Решение

1. Существующий Redis и его том сохраняются. API, beat, системный обработчик,
   каталог, billing и mailer получают шесть разных Redis identities. Контейнер
   получает только собственный `CELERY_BROKER_URL`; общий `REDIS_URL` остаётся
   у API для прикладного кэша. В production подключения сохраняют проверяемый TLS.
2. Имена очередей `default`, `catalog-worker`, `billing-worker`, `platform-mailer`
   не меняются. ACL разрешает только собственную очередь, её четыре приоритета,
   binding и необходимые команды доставки. API отправляет только импорт;
   beat отправляет системные, billing и mailer задачи. Обработчик может повторно
   поставить задачу только в собственную очередь.
3. Неподтверждённые доставки разделены ключами
   `aurum:broker:<queue>:unacked`, `unacked_index`, `unacked_mutex`. Реплики одной
   роли используют общее пространство своей очереди. Глобальный префикс транспорта
   не применяется: он изменил бы имена уже накопленных очередей.
4. Remote control, события, gossip, mingle, heartbeat и хранение результатов
   отключены. Проверка здоровья читает локальный PID и выполняет PING с собственными
   broker credentials. Она подтверждает живой процесс и соединение, но сама по себе
   не доказывает успешную бизнес-операцию.
5. API использует отдельный `catalog_producer`; планировщик — `beat_app`.
   Отправка задачи не загружает DB/MinIO settings обработчика. Неизвестные очереди
   не создаются автоматически.
6. Ресурсы разделены внутренними сетями `db`, `broker`, `storage`:

   | Процесс | Сети ресурсов |
   |---|---|
   | API | db, broker, storage |
   | Системный обработчик, billing | db, broker |
   | Каталог | db, broker, storage |
   | Mailer | db, broker; отдельно mailer-egress |
   | Beat | broker |
   | PostgreSQL, bootstrap, migrate | db |
   | Redis | broker |
   | MinIO и его provisioners | storage |
   | Logical backup | db, storage |
   | Physical base backup | db |

   Существующие сети приложения, мониторинга, recovery, Edge и внешней доставки
   сохраняют свои назначения. Одноразовые тестовые БД не включаются в runtime-сети.

   PostgreSQL, Redis и MinIO не публикуют порты на хост и в dev/demo. Обслуживание
   выполняется из Docker через `exec` или профиль maintenance. Отдельные тестовые
   PostgreSQL/Redis сохраняют свои тестовые порты; адреса API, интерфейса и общего
   gateway не меняются.
   Prometheus в dev также остаётся только в сети monitoring без публикации порта.

   Docker Desktop не открывает port bindings контейнеров, имеющих только internal
   bridge-сети. Дополнительная обычная сеть с опубликованными портами также даёт
   mailer с внешним маршрутом доступ к этим портам по IP ресурса. Это подтверждено
   изолированной пробой и соответствует ограничениям
   [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/).
   Поэтому такой обход для служебных консолей не применяется. Регрессионный тест
   включает настоящий сетевой профиль mailer с `mailer-egress` и проверяет все
   IP ресурсов, а не только DNS или контейнеры без внешнего маршрута.

## Обновление с сохранением задач

Перед первым переключением требуется короткое окно обслуживания:

Для существующего production-развёртывания предварительно добавить только
шесть новых `REDIS_CELERY_<ROLE>_PASSWORD` и соответствующие
`CELERY_<ROLE>_BROKER_URL`: отдельные случайные пароли и проверяемый TLS.
Существующие секреты и `REDIS_PASSWORD` сохраняются. `New-ProductionSecrets.ps1`
предназначен для пустого каталога нового развёртывания; повторная генерация всего
каталога не является способом обновления. Затем выполнить production preflight.

1. Собрать новые образы, не заменяя работающие контейнеры.
2. Остановить API и beat, затем дать всем четырём прежним workers завершиться.
3. После их остановки проверить старые глобальные `HLEN unacked` и
   `ZCARD unacked_index`: оба результата должны быть нулевыми.
4. При ненулевом результате или ошибке проверки вернуть прежние контейнеры,
   дождаться восстановления/завершения доставок и повторить проверку. Не удалять
   ключи, не выполнять FLUSH, не очищать списки очередей.
5. Только после успешной проверки обновить Redis ACL, сети и обработчики.
   Обычные очереди могут быть непустыми: их имена и сообщения сохраняются.

Demo launcher выполняет эту последовательность до пересоздания инфраструктурных
контейнеров. При отказе предварительной проверки он запускает прежние контейнеры.
Ошибки после начала обновления инфраструктуры требуют диагностики; автоматический
возврат всей инфраструктуры этим механизмом не обещается. Production-оператор
должен выполнить ту же предварительную проверку перед `compose up`.

## Проверки и границы доказательства

Отдельный Docker-набор проверяет настоящий Redis ACL: разрешённую доставку,
чужие очереди, записи доставок, кэш, административные команды и pub/sub; данные
контрольных ключей должны сохраняться. Реальный Celery проверяет четыре очереди,
retry и восстановление после потери процесса. Сетевые пробы проверяют разрешённые
и запрещённые соединения по DNS и непосредственному IP. Полный CI остаётся gate.

Это логическая изоляция одного Redis, а не отдельные процессы кэша и broker:
общие память, CPU и отказ Redis остаются общим риском. API сохраняет широкий доступ
к прикладному Redis. Docker bridge не является межсетевым экраном на уровне портов:
многосетевой API доступен на своих интерфейсах. Разделение сетей закрывает прямые
пути к несвязанным ресурсам, но не доказывает невозможность обращения к API.
Технические проверки не заменяют внешний security review и пилотный допуск.
