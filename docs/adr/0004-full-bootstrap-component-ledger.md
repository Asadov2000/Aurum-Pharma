# ADR-0004: Компонентный контейнер полного Edge bootstrap

- Статус: принято
- Дата: 2026-07-15
- Уточняет: ADR-0002, ADR-0003

## Контекст

Профиль `cash_sale_v1_full_v1` нельзя считать готовым только по имени строки в
`sync_activation_bootstrap`. До передачи денежной записи Cloud должен доказуемо
зафиксировать все данные, необходимые кассе. Объём каталога и партий требует
возобновляемой доставки частями, а отсутствие товаров, пользователей или
открытой смены является допустимым состоянием и не должно путаться с отсутствием
самого компонента.

Offline-auth создаёт отдельную границу риска. На Edge запрещено копировать
refresh/access-токены, TOTP secret, email-коды и обычный cloud password hash.
Компрометация кассового компьютера не должна раскрывать данные, пригодные для
входа в Cloud или другую аптеку.

## Решение

Полный профиль использует неизменяемый компонентный ledger. Его обязательный и
точный набор:

- `catalog` - активный ассортимент, штрихкоды и розничные цены без закупочных цен;
- `inventory` - партии, сроки, доступные количества и блокировки филиала;
- `offline_auth` - короткоживущие, привязанные к устройству offline grants;
- `authorization` - эффективные POS-права без списка permissions в JWT;
- `shift` - проверенный baseline смены и правила её локального открытия;
- `pos_materialization` - локальная материализация capability и счётчиков операций.

Foundation из ADR-0003 остаётся обязательной отдельной частью. Каждый компонент
имеет минимум один chunk, даже если `item_count=0`. Это позволяет отличить
проверенное пустое состояние от неполной загрузки. Chunk хранит JSONB payload,
число элементов и canonical SHA-256. Компонент связывает непрерывную цепочку
chunk metadata, а `component_manifest_hash` связывает отсортированный точный
набор компонентов. Домены хешей разделены строками
`aurum:activation-bootstrap-component:v1` и
`aurum:activation-bootstrap-components:v1`. Итоговый snapshot дополнительно
связывает foundation, `component_manifest_hash` и весь activation scope доменом
`aurum:activation-full-snapshot:v1`.

Таблицы component/chunk имеют полный tenant/branch/Edge/register/epoch scope,
точные внешние ключи, RLS и запрет UPDATE/DELETE. Общий audit log получает только
метаданные компонента; payload chunk туда не копируется. `aurum_app` может только
читать строки в своём RLS scope.

DB-предикат `is_cash_sale_v1_bootstrap_complete` проверяет:

1. профиль, foundation и точный набор шести компонентов;
2. непрерывные индексы chunk от 0, количество chunk и сумму `item_count`;
3. хеш каждого компонента и общий `component_manifest_hash`;
4. соответствие итогового snapshot точному activation scope и обоим корням.

Readiness и переход в `ready/activated` дополнительно требуют истинности этого
предиката. Миграция создаёт контейнер и защитную границу, но не публикует полный
профиль: runtime продолжает создавать только `foundation_shadow_v1`.

Offline grant будет выпускаться Cloud только после свежей online-аутентификации,
для одного tenant/branch/Edge/user и ограниченного набора POS-команд. Он получает
короткий абсолютный срок, номер политики/отзыва и привязку к ключу устройства.
Windows Edge хранит материал через DPAPI, а production-вариант требует ключа в
TPM, mTLS device identity, защищённого монотонного времени и anti-rollback
состояния. До реализации и тестирования этих условий `offline_auth` не может быть
сформирован, а полный профиль - подготовлен.

## Последствия

Плюсы: одна строка или один загруженный chunk больше не могут создать ложную
готовность; большие payload доставляются с продолжением после обрыва; пустые
компоненты представлены однозначно; секреты Cloud не переносятся на кассу.

Цена решения: prepare полного профиля обязан сначала атомарно сформировать все
компоненты и их хеши. Изменение любого payload после prepare требует новой
попытки activation, а не исправления существующего ledger.
