# ADR-0038: Строгий контракт access JWT и ограниченный переход

- Статус: принято
- Дата: 2026-09-08
- Связано: ADR-0007, ADR-0009, ADR-0033

## Причина

Access JWT проверял подпись и время, но не имел обязательных issuer, audience
и идентификатора экземпляра. Общий decoder передавал claims в middleware,
который выбирает tenant-контекст и support pool до проверки пользователя в БД.
Некорректные типы нельзя приводить к boolean или UUID на этой границе.

## Решение

1. Все access JWT выпускаются с подписанным JOSE header
   `typ: aurum-access+jwt`, обязательными `iss`, `aud`, `jti`, `sub`, `sid`,
   `iat`, `exp` и boolean-флагами `is_developer`/`is_administrator`.
   `tenant_id` присутствует всегда; `null` допустим для платформенного доступа.
2. `JWT_ISSUER` и `JWT_AUDIENCE` — непустые стабильные значения из конфигурации
   (`aurum-pharma` и `aurum-pharma-api` по умолчанию). Они не выводятся из Host,
   URL браузера, localhost или Tailscale. Среды используют независимые секреты.
   Допускается только одна точная строка audience, не массив получателей.
3. Общий decoder проверяет подпись единственным алгоритмом из серверной
   конфигурации, issuer, audience, тип и обязательные claims. Идентификаторы —
   канонические UUID; флаги — JSON boolean, даты — целые неотрицательные числа,
   а не строки или boolean. Срок ограничен настроенным временем access token.
   Проверка происходит до назначения контекста в AuthContextMiddleware.
4. `jti` — новый случайный UUID для каждого выпуска, в том числе повторного
   refresh. Это идентификатор экземпляра, не запрет повторного использования
   bearer-токена. Отзыв доступа по-прежнему проверяется через `sid`, состояние
   пользователя, membership, роли и password/MFA proof в БД.
5. Фабрика запрещает перезаписывать зарегистрированные claims через `extra`.
   Permissions в JWT запрещены; авторизация остаётся серверной. Некорректный
   JWT приводит к обычному 401 на защищённом endpoint, не к 500. Исключения
   преобразования NumericDate внутри PyJWT также закрываются на этой границе.

## Переход существующего single-host развёртывания

Refresh-токены остаются непрозрачными значениями в httpOnly cookie. Их формат,
хеши, сроки и сессии не меняются; миграции БД нет. JWT_SECRET при обновлении
контракта не ротируется. Каждый refresh/replay уже выпускает новый access JWT.
Обычный клиент после 401 обновляет access через cookie и повторяет запрос;
перезагрузка сразу использует refresh. Однако password/MFA формы намеренно
не повторяют автоматически отправку секрета.

Для открытых форм предусмотрен **необязательный**
`JWT_LEGACY_ACCESS_UNTIL` — абсолютная UTC-метка Unix в секундах:

- `0` по умолчанию: только строгий новый контракт;
- будущее значение при старте API не может быть дальше 15 минут;
- прошедшее значение допускает запуск, но не legacy JWT;
- deadline сравнивается с текущим временем на каждом decode, поэтому окно
  завершается без перезапуска и не продлевается перезапуском;
- в окне допустима только прежняя форма: header `JWT`, все ключи
  `iss`/`aud`/`jti` отсутствуют, подпись, обязательная identity, флаги и даты
  валидны, `exp - iat` не превышает 900 секунд и настроенный срок;
- частичные новые claims, значения `null` вместо отсутствия, неверный тип
  и смешение старого/нового профиля отклоняются. Для legacy issuer/audience
  временно не проверяются; это ограниченное сохранение прежнего доверия.

Порядок rollout:

1. Проверить CI, собрать согласованную версию API и сохранить данные/сессии.
2. При необходимости один раз задать фиксированный будущий deadline максимум
   на 15 минут. Не вычислять скользящее `now + TTL` в Docker entrypoint,
   restart policy или каждом запуске launcher.
3. Согласованно заменить все API-процессы. Старый decoder PyJWT без audience
   отвергает новые JWT с `aud`; произвольное смешение старых/новых реплик
   не является поддержанным rolling deployment.
4. Проверить вход, refresh, прежнюю аптеку и защищённые действия. После
   истечения окна старый access отклоняется, а прежняя действующая refresh
   cookie продолжает работать. Убрать прошедший override при обслуживании.

## Проверки

Core-тесты покрывают отсутствие/тип/значения claims, подпись, алгоритм,
NumericDate, невозможность расширить legacy TTL, смешанные профили и точную
границу deadline без перезапуска. Настройки проверяют default strict,
прошедший deadline и отказ длительного окна. Middleware-тесты используют
реально подписанный некорректный JWT и проверяют отсутствие support-контекста.
HTTP/DB-тесты проверяют переход с прежней cookie, replay потерянного refresh
и отказ изменяющего запроса до записи. Полный CI сохраняет проверки отзыва
сессий, tenant-изоляции, MFA/password и браузерных потоков.

Решение следует разделам 3.8–3.12
[RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.8).
Проверка стандартных claims делегируется
[PyJWT](https://pyjwt.readthedocs.io/en/stable/api.html#jwt.decode).
Это внутренний профиль Aurum, не заявление о реализации OAuth/OIDC.
