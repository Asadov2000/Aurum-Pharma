# ADR-0002: Передача права записи Cloud -> Edge

- Статус: принято
- Дата: 2026-07-14
- Уточняет: ADR-0001

## Контекст

Read-only Edge уже получает события Cloud, проверяет их цепочку и строит локальную
проекцию продаж. Для offline POS этого недостаточно: в заранее определённый момент
Edge должен стать единственным владельцем операций филиала. Простая замена
`writer_node_id` небезопасна: при задержанном запросе, повторе пакета или ошибке
оператора Cloud и Edge могут одновременно принять денежную операцию.

Передача права записи должна быть проверяемой, необратимой автоматически и
оставлять полный след для расследования. Потеря интернета сама по себе не является
основанием для смены писателя.

## Решение

### Неизменяемые эпохи

Каждый период владения записью хранится в `sync_writer_epoch`. Идентификатор
события в потоке состоит из:

`origin_node_id + writer_epoch + sequence`.

Номер `sequence` начинается с 1 внутри каждой эпохи. `sync_stream` остаётся только
указателем на текущую эпоху, а история эпох не перезаписывается и не удаляется.

Эпоха существует только после фактической передачи права записи. Её состояния:

- `active` - единственный разрешённый писатель филиала;
- `fenced` - запись навсегда запрещена, данные остаются доступными для проверки.

Подготовка хранится отдельно в `sync_writer_activation` со состояниями `prepared`,
`ready`, `aborted` и `activated`. Отменённая попытка не создаёт фиктивную эпоху и
не мешает повторить передачу с тем же следующим номером. Для филиала допускается
не более одной `active` эпохи и одной незавершённой попытки. Возврат `fenced`
эпохи в `active`, изменение readiness и удаление истории в рабочей БД запрещены.

Корневые checksum новой эпохи связываются с терминальными source/projection
checksum предыдущей эпохи, хешем bootstrap snapshot и хешем activation manifest.
Cloud и Edge сверяют обе цепочки. Совпадение только проекции недостаточно.

### Двухфазная передача

Подготовка выполняется только оператором поддержки:

1. Cloud блокирует строку потока и фиксирует `activation_id`.
2. Проверяются активный Cloud writer, отсутствие незавершённых смен и черновиков,
   последний совпавший source/projection checkpoint и монотонный счётчик чеков.
3. Создаётся попытка активации с capability `cash_sale_v1` и одной разрешённой
   кассой; operational-запись филиала блокируется до активации или отмены.
4. Edge загружает подписанный snapshot, сверяет manifest, checkpoint и baseline
   номера чека, затем записывает идемпотентный readiness report.

Активация выполняется одной транзакцией:

1. Повторно блокируются поток, попытка активации, старая эпоха, readiness и
   счётчик кассы.
2. Все значения сравниваются с подготовленным manifest; изменение хотя бы одного
   checkpoint отменяет активацию.
3. Старая эпоха переводится в `fenced`, новая - в `active`.
4. `sync_stream` переключается на новый узел и начинает новую цепочку с позиции 0.
5. DB-fence запрещает Cloud и любому другому Edge изменять operational-данные
   филиала.

Операция идемпотентна по `activation_id`. Частичная передача права записи
невозможна: транзакция либо фиксируется полностью, либо полностью откатывается.

### Граница первого пилота

Первая Edge-owned capability разрешает только:

- открытие и закрытие смены назначенной кассы;
- атомарную наличную продажу;
- получение результата по `operation_id`;
- печать и повторную печать того же внутреннего чека.

Карты с неизвестным статусом, возвраты, изменение цен и ролей, billing,
межфилиальные перемещения и ручное редактирование завершённой продажи запрещены.
Остаток филиала принадлежит одному Edge; разделять один склад между независимыми
писателями нельзя.

### Чеки и курсоры

Внутренний номер чека выдаёт транзакционный `register_receipt_counter`. Счётчик
монотонен для кассы и не сбрасывается при смене или новой writer epoch. Откат
транзакции откатывает и резервирование номера.

Курсор репликации включает `writer_epoch`. Cloud выбирает события только по точным
`origin_node_id` и `writer_epoch`; одинаковые sequence из разных эпох никогда не
попадают в один пакет.

## Защитные условия релиза

Реальная активация Edge writer остаётся выключенной, пока не готовы одновременно:

- отдельная минимальная DB-роль для Cloud ingest без прямой записи в доменные
  таблицы;
- mTLS, сертификат устройства и ключ в TPM/DPAPI;
- BitLocker, подписанный installer и защита updater от downgrade;
- offline-auth с монотонным временем и ограниченным сроком;
- полная bootstrap-проекция каталога, партий, пользователей, смен и настроек;
- проверенный backup restore, power-loss, disk-full и повтор потерянного ACK;
- официальный fiscal adapter и подтверждённые правила offline-фискализации.

Bearer credential остаётся только локальным development-транспортом и не может
включить production writer. Lease-based и active-active failover не используются.

## Текущее состояние реализации

Миграция `0044` создаёт журнал эпох, readiness ledger, epoch-scoped cursors,
двойную проверку checksum и транзакционный счётчик чеков. Миграция `0045`
добавляет отдельный журнал попыток, защищённые операции
`prepare -> readiness -> activate/cancel`, точные scope-FK, DB-fence доменных
операций и проверки конкурентности/RLS. Активация выключена конфигурацией и
принудительно запрещена в production.

Следующий этап должен реализовать подписанный bootstrap, Edge API
`cash_sale_v1`, Cloud ingest, mTLS/device identity и тестовую матрицу отказов
питания, диска и сети. До выполнения защитных условий Cloud остаётся единственным
production-писателем.

## Последствия

Плюсы: исключается незаметный split-brain, сохраняется доказуемая история,
повторы безопасны, а нумерация чеков не зависит от смены узла.

Цена решения: передача writer требует явной процедуры, bootstrap и проверки
готовности. Автоматическое переключение при сбое сознательно отложено, потому что
без consensus оно создаёт больший финансовый риск, чем кратковременная остановка.
