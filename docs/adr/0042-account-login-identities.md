# ADR-0042: Вход по паролю или подтверждённому телефону

- Статус: принято по решению владельца продукта; реализация проходит проверку
- Дата: 2026-09-12
- Связано: [ADR-0033](0033-optional-account-mfa.md),
  [ADR-0038](0038-strict-access-token-contract.md),
  [ADR-0024](0024-isolated-auth-email-delivery.md)

## Решение

1. Обычные способы входа: почта с паролем или подтверждённый телефон с SMS-кодом.
   SMS отправляет Payom. Оба способа открывают один аккаунт с теми же членствами,
   ролями и выбранной аптекой; способ входа не выдаёт дополнительных permissions.
2. Первый вход в приглашённый аккаунт без пароля допускает одноразовый код на
   собственную почту. Этот переход доступен также существующим аккаунтам без
   пароля. После установки пароля email-код больше не является способом входа.
   Подтверждение контакта само по себе не создаёт аптеку или членство.
3. После первого входа предлагается создание пароля. Настройка доступна и позже
   в безопасности аккаунта. Пользователь с подтверждённым телефоном может
   продолжать пользоваться SMS-входом без пароля. Опасное действие, требующее
   пароль, сначала требует его безопасной установки, если другой допустимый
   способ повторного подтверждения отсутствует.
4. Контактный `phone` и подтверждённый номер для входа разделены. Старые номера
   автоматически не подтверждаются. Подтверждённый номер глобально уникален;
   два аккаунта не объединяются по совпадению контактов. На первом этапе
   поддерживается международная запись `+992` и девять последующих цифр.
5. Смена номера выполняется в действующей сессии после повторного пароля.
   Если пароля нет, требуется свежий код на уже принадлежащий аккаунту контакт.
   При включённой MFA она также проверяется. SMS для подтверждения нового номера
   отправляется **только на новый номер**. Старый заменяется после успешного
   подтверждения; остальные сессии и незавершённые проверки отзываются.
6. Восстановление пароля требует одноразовый код на подтверждённую почту или
   подтверждённый телефон. Включённая MFA сохраняется и проверяется. После
   восстановления отзываются прежние сессии и незавершённые проверки; необходим
   новый вход. Новый номер без доказательства владения прежним аккаунтом не
   является способом восстановления. Потеря всех контактов требует поддержки,
   её отдельная процедура не имитируется публичным endpoint.
7. MFA добровольна для всех и управляется в настройках. После включения она
   обязательна для обоих способов входа. SMS и пароль не создают фиктивное
   `mfa_at`; обычный вход не создаёт `password_at` для опасных действий.
   Access-токен остаётся в памяти, refresh — только в httpOnly cookie.

## Одноразовые коды и доставка

Проверка пароля bcrypt остаётся в backend. Узкая зависимость авторизации
использует существующий support pool только для проверки учётных данных и
выпуска доказательства входа. Чтение хеша по почте и выпуск такого доказательства
не выдаются `aurum_app`: обычный tenant pool не должен иметь возможность получить
хеш и передать его как уже проверенный пароль. Бизнес-запросы после входа
продолжают работать под обычным tenant-контекстом и RLS. Новая runtime-роль или
расширение PostgreSQL для паролей этим решением не вводится.

Коды разных назначений разделены: вход, восстановление, создание пароля,
повторное подтверждение и смена номера. Срок кода — 5 минут, повторная выдача —
не чаще раза в минуту, не более 5 проверок одного кода. Ограничения по контакту,
IP и общему числу SMS защищают от перебора и неконтролируемых расходов. Ошибка
проверки не должна откатывать счётчик попыток. Коды хранятся в виде хешей;
email-доставка сохраняет изолированный зашифрованный outbox.

До подтверждения контакта или пароля публичные ответы не раскрывают
существование аккаунта или наличие у него MFA.
Контакты, коды, пароли, токены и ответы провайдера не записываются в логи.

Payom подключается по официальному
[контракту API](https://payom.tj/modules/api): персональный HTTPS endpoint
`/api/message`, Bearer-ключ и согласованное имя отправителя. Адрес и ключ
поступают из конфигурации, не из браузера. Автоматические повторные отправки
после неопределённого сетевого результата запрещены: SMS уже могло уйти.
HTTP 2xx означает принятие запроса, а не подтверждённую доставку на устройство.
Публичная документация не описывает схему ответа и уведомлений о доставке;
её подтверждение у Payom и проверка на реальных номерах обязательны перед
рабочим включением. Отдельные callbacks без проверенного контракта не добавляются.

`SMS_PROVIDER=disabled` — значение по умолчанию. Явный `development` не обращается
к провайдеру и запрещён за пределами development. В режиме `payom` код SMS
никогда не возвращается клиенту даже при локальном запуске.

## Проверка и выпуск

Нужны тесты первого входа и перехода на пароль, двух способов входа, сохранения
сессии, MFA и восстановления, одноразовости/истечения/перебора кодов, конкурирующей
смены номера, отзыва сессий и недоступности чужих аккаунтов. Проверка SQL-прав
и функций авторизации входит в полный backend-набор. UI проверяется в обеих
темах и на узком экране; новый макет не меняет серверные проверки доступа.

Миграция не сбрасывает пользователей, пароли или данные аптек. Upgrade общей
dev-БД допустим, downgrade — только в одноразовой БД. Выпуск проходит через PR
и обязательный CI gate. Работающий локальный макет и успешные mock-тесты не
являются доказательством настоящей доставки SMS.
