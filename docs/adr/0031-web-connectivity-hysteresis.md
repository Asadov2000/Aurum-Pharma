# ADR 0031: Устойчивое определение связи в web-клиенте

- Статус: принято
- Дата: 2026-09-04

## Контекст

Пилотная web-версия работает online-first. Полный offline POS до готовности Edge,
offline-auth и фискального адаптера запрещён. При слабом интернете единичный
таймаут `/healthz` не должен сразу блокировать кассу: перегруженный тестовый ПК или
краткий провал сети может ответить на следующий запрос. Одновременно один только
`navigator.onLine` не доказывает доступность backend.

Разные разделы не должны самостоятельно определять доступность сервера, иначе
касса, онбординг, биллинг и склад могут показывать противоречивые состояния.

## Решение

1. `ConnectivityProvider` является единым источником server-connectivity для
   серверных действий web-клиента.
2. Событие браузера `offline` немедленно переводит интерфейс в `offline` и
   блокирует новые серверные операции. `online` запускает health-check, но само по
   себе не считается подтверждением доступности backend.
3. Один неуспешный health-check переводит состояние в `checking`, но не блокирует
   действие, защищённое серверной идемпотентностью. Два последовательных сбоя
   подтверждают `server-unavailable` и блокируют новые изменения.
4. Health-check имеет восьмисекундный timeout. После первого сбоя повтор идёт
   через 1,5 секунды, после подтверждённой недоступности — каждые 10 секунд.
   После успешной проверки следующая планируется через 30 секунд. Все режимы
   используют один последовательный таймер, поэтому фоновые и аварийные проверки
   не дублируют друг друга.
5. `focus`, видимая страница после `visibilitychange`, `online` и
   ручная кнопка запускают проверку. Сигнал, пришедший во время активного запроса,
   не теряется: выполняется одна отложенная проверка без параллельного дубля.
6. Поздний ответ устаревшего health-check не может изменить более новое состояние
   после `offline`, размонтирования или следующего запроса.
7. Подтверждённые `offline` и `server-unavailable` передаются в React Query через
   `onlineManager`. Восстановление использует штатный refetch только тех запросов,
   которые разрешают `refetchOnReconnect`; глобальный ручной refetch запрещён.
8. POS, онбординг, billing, platform billing, списание и возврат поставщику
   используют общий `useConnectivity`. Локальные настройки текущего устройства
   продолжают работать без backend и отдельно показывают только сеть браузера.

## Инварианты

- `checking` не означает offline-продажу и не создаёт локальных денежных или
  складских операций.
- Checkout, платежи, возвраты, смены и команды чека сохраняют собственные
  idempotency/reconciliation правила; connectivity UI не заменяет их.
- При подтверждённой недоступности уже загруженные данные можно просматривать, но
  новые server-side изменения запрещены.
- Кэш и service worker не должны представлять внутренний чек как фискальный и не
  дают права на offline POS.

## Следствия

- Краткий единичный таймаут больше не блокирует кассира.
- Реальный длительный сбой определяется без ложного обещания offline-работы.
- Возврат из сна на телефоне или PWA проверяет актуальное состояние немедленно.
- До следующего этапа остаются отдельные POS-риски: межвкладочная блокировка одной
  кассы, отмена устаревших запросов и проверка очереди сканера при смене связи.
