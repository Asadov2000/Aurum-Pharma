# ADR-0011: Идемпотентные команды черновика POS

- Статус: принято
- Дата: 2026-08-09

## Контекст

При слабом интернете сервер может применить изменение корзины, а клиент не
получить HTTP-ответ. Повтор с новым идентификатором тогда создаёт вторую позицию
или показывает кассиру устаревший чек. Обычный повтор запроса недостаточен:
сервер должен отличать повтор той же команды от повторного действия кассира.

## Решение

Создание черновика, добавление, изменение и удаление позиции получают UUIDv4
`operation_id`. До изменения домена сервер под транзакционной advisory-блокировкой
проверяет tenant-scoped журнал POS-команд.

Первая команда атомарно сохраняет:

- тип команды, пользователя, аптеку и связанный чек;
- SHA-256 канонического запроса;
- валидированный снимок результата, достаточный для точного повтора ответа.

Повтор с тем же пользователем, типом и hash возвращает сохранённый результат без
нового побочного эффекта. Повтор UUID с другим смыслом завершается `409`.
Идентификатор также не может пересекаться с другими POS-операциями. Журнал
защищён RLS, append-only ограничениями и audit-триггером.

Клиент сохраняет не более одной незавершённой команды на кассу до отправки.
Маркер не содержит токенов и персональных данных. После потери ответа клиент
сначала запрашивает сохранённый результат или повторяет ту же команду с тем же
UUID. До сверки блокируются следующие изменения корзины, оплата, новый чек и
смена кассы.

## Следствия

- потерянный ответ больше не превращает один физический скан в две позиции;
- перезагрузка страницы не теряет координаты незавершённой команды;
- журнал увеличивает объём БД, поэтому политика архивирования будет вводиться
  только вместе с доказанным минимальным сроком безопасного повтора;
- это не offline POS: без Edge кассир по-прежнему не может создавать новые
  операции при полном отсутствии сети;
- checkout, платежи и возвраты сохраняют собственные специализированные
  идемпотентные журналы и инварианты.
