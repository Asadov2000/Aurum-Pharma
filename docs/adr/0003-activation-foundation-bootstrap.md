# ADR-0003: Базовый activation-bound bootstrap

- Статус: принято
- Дата: 2026-07-15
- Уточняет: ADR-0002

## Контекст

Перед передачей права записи Edge должен получить воспроизводимый снимок данных,
привязанный к конкретной попытке активации. Обычный enrollment bootstrap из
ADR-0002 восстанавливает историю shadow-проекции продаж, но не фиксирует
конфигурацию аптеки и кассы на границе handover.

Полный offline POS дополнительно требует каталога, цен, партий, остатков,
пользователей, ролей и открываемой локальной смены. Эти проекции ещё не готовы,
поэтому частичный снимок не должен создавать ложную готовность Edge writer.

## Решение

Первый профиль называется `foundation_shadow_v1`. При `prepare` Cloud:

1. Под общей блокировкой читает tenant, tenant settings, выбранный филиал и кассу.
2. Сам вычисляет canonical SHA-256 базового payload и всего activation snapshot.
3. Передаёт вычисленный snapshot hash в существующий протокол handover.
4. В той же транзакции сохраняет неизменяемые записи
   `sync_activation_bootstrap` и `sync_activation_foundation`.

Клиент больше не задаёт `bootstrap_snapshot_hash`. Повторный запрос с тем же
`activation_id` допустим только при совпадении исходного запроса и уже
сохранённого серверного bootstrap.

Foundation payload содержит только:

- юридические и рабочие реквизиты tenant без email и телефона;
- POS-настройки tenant;
- лицензию, расписание и заголовок чека выбранного филиала;
- имя, тип принтера и активность выбранной кассы без `printer_config`;
- явные `schema_version=1` и `currency=TJS`.

Обе таблицы имеют tenant/branch/Edge scope, RLS, точные внешние ключи, audit
metadata и запрет UPDATE/DELETE. Payload не копируется в общий audit log, чтобы
не расширять поверхность хранения чувствительных реквизитов; audit log получает
безопасную запись метаданных родительского bootstrap.

Edge получает снимок только через машинно-аутентифицированный endpoint. Для
development transport manifest подписывается HMAC с отдельным доменом ключа.
Это не production-подпись: bearer transport по-прежнему запрещён production
guard, а реальная активация writer выключена.

## Fail-closed граница

`foundation_shadow_v1` всегда имеет `readiness_eligible=false`. API readiness,
DB-вставка readiness и переход activation в `ready/activated` требуют будущий
профиль `cash_sale_v1_full_v1` с `readiness_eligible=true`. Отдельные настройки
`EDGE_WRITER_READINESS_ENABLED` и `EDGE_WRITER_ACTIVATION_ENABLED` по умолчанию
выключены и запрещены текущей production-конфигурацией.

Следующий профиль обязан атомарно добавить как минимум каталог и цены, партии и
остатки, безопасную offline-auth проекцию, права кассира, смену и локальную
материализацию. Только после проверки целостности всех частей Edge сможет
отправить readiness report.

## Последствия

Плюсы: сервер владеет составом snapshot, повторная доставка воспроизводима,
RLS ограничивает снимок конкретным Edge, а неполные данные не могут включить
денежную запись.

Цена решения: подготовленная ветка остаётся замороженной до отмены handover;
foundation snapshot сам по себе не делает offline POS доступным и потребует
расширения новым версионированным профилем.
