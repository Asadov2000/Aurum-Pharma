# ADR-0040: Создание товара со штрихкодом и безопасным повтором

- Статус: принято
- Дата: 2026-09-08
- Связано: ADR-0035, ADR-0037, ADR-0039, миграция 0145

## Причина

Ручное создание карточки и добавление штрихкода выполнялись разными запросами.
При конфликте кода могла остаться карточка без ожидаемого штрихкода. Повтор
создания после потерянного ответа не имел устойчивого идентификатора операции.
Для создания неизвестного товара внутри прихода нужно сохранить введённые
количество, цены и даты, затем сразу выбрать созданную карточку.

## Решение

1. Существующий `POST /catalog` получает необязательные `operation_id` (UUID4)
   и `initial_barcode` с кодом и его типом. Начальный штрихкод требует ключ
   операции. Старые вызовы без обоих полей сохраняют прежний контракт.
   Обе формы создания веб-приложения всегда передают ключ операции.
2. Карточка и её начальный штрихкод создаются атомарно в одной транзакции.
   Конфликт кода откатывает обе записи и соответствующие записи аудита.
   Код другого товара не переносится и не перепривязывается автоматически.
3. Для карточки сохраняются исходный ключ операции и отпечаток нормализованного
   запроса. Эти поля неизменяемы; ключ уникален внутри tenant, включая архивные
   карточки. Их физическое удаление запрещено, чтобы не потерять факт операции.
   Старые и импортированные карточки получают `NULL` без изменения содержимого.
4. Повторы сериализуются блокировкой операции. Тот же ключ и исходный запрос
   возвращают актуальную карточку без новой записи и аудита. Другой запрос с тем
   же ключом получает конфликт. Поиск явно ограничен tenant, включая поддержку
   с `aurum_support`. Числа и пустые необязательные поля нормализуются до хэша.
5. Отпечаток сравнивается с исходным запросом, а не редактируемыми полями товара.
   Повтор не отменяет последующие правки, не восстанавливает архивную карточку
   и не добавляет заново штрихкод, который позже удалили отдельной операцией.
   Ответ подтверждает результат создания; он не запрещает дальнейшую работу
   с карточкой по существующим правилам каталога.
6. `catalog.create` разрешает начальный код только вместе с новой карточкой.
   Изменение кодов существующих товаров по-прежнему требует `catalog.update`.
   Привилегии фонового обработчика импорта из ADR-0035 не расширяются.
   Внешние схемы чтения не раскрывают внутренний отпечаток запроса.

## Интерфейс и сбои связи

В позиции прихода сотрудник с `catalog.create` может открыть «Новый товар».
Перед открытием сохраняется уже введённая строка прихода. Поисковое название
можно перенести в карточку; дозировка, упаковка, цены, отпуск и хранение не
выводятся из названия автоматически. Отпуск и хранение выбираются явно,
штрихкод необязателен. Используется общая форма каталога.

После успешного создания товар выбирается в исходной позиции. Остальные поля
прихода сохраняются. Создание товара и сохранение его выбора в приходе — две
операции: если вторая не подтверждена, интерфейс оставляет выбранный товар и
показывает состояние несохранённого черновика, не предлагает создавать дубль.

Пока результат создания неизвестен, клиент удерживает исходный запрос и ключ,
блокирует изменение полей и предлагает точный повтор. Временный отказ, включая
ограничение частоты запросов, не доказывает, что предыдущая попытка откатилась.
Закрытие и навигация предупреждают о неподтверждённом результате или вводе.
Отправка формы в модальном окне не отправляет родительскую форму прихода.

Черновик прихода сохраняется на сервере по ADR-0039. Незавершённая форма новой
карточки хранится только в памяти до отправки: восстановление её содержимого
после закрытия браузера этим решением не обещается. Данные карточки не пишутся
в `localStorage`. Разные ключи операции без штрихкода могут создать одинаково
названные товары: уникальность названия не вводится вместо явной проверки.

## Проверки

- Создание с начальным штрихкодом и без него, явный выбор условий.
- Откат карточки при конфликте кода; изоляция tenant и прежние права изменения.
- Одновременные одинаковые повторы; конфликт изменённого запроса.
- Повтор после редактирования, удаления кода и архивации карточки.
- Неизменность служебных полей и отсутствие новых прав у фонового обработчика.
- Сохранение полей прихода, потерянный ответ и временный отказ при повторе.
- Закрытие вложенной формы, навигация, мобильная ширина и отсутствие случайной
  отправки родительского документа.
- Upgrade на общей БД без очистки; downgrade только в одноразовой тестовой БД.
