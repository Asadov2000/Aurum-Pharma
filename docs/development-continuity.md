# Продолжение разработки без повторной реализации

Правила находятся в `AGENTS.md`, раздел «Актуальность и продолжение между
запусками». Здесь — порядок применения и примеры восстановления. Документ
не подтверждает готовность функций и не заменяет GitHub, код и тесты.

## Проверка в начале задачи

1. Прочитать последнее указание пользователя и `AGENTS.md`. Установить, кто
   продолжает этап: облачный запуск или локальный основной агент.
2. Прочитать фактический SHA `main` на GitHub, состояние своего checkout и
   активные PR. Для выбранного результата найти также недавние merged/closed PR.
   Если выдача ограничена, уточнить поиск или пройти доступные страницы.
3. Сопоставить PR и checkpoint с реальными head/base, проверками и кодом.
   Продолжить незавершённый PR. При отсутствии PR доказать незавершённость
   следующего согласованного этапа по его критериям, а не по старому сообщению.
4. Зафиксировать решение: продолжить PR, ждать CI, выбрать подтверждённый этап
   или остановить запись из-за неоднозначности. Только затем изменять код.

`git fetch origin main` обновляет ссылки Git, но сам по себе не проверяет PR,
критерии готовности, работу другого агента, запущенное приложение или БД.
Чистую отдельную ветку начинают от проверенного свежего main. Существующую
ветку продолжают с сохранением её работы; защищённый runtime-checkout не
переключают ради разработки.

## Состояние в описании своего PR

Использовать короткий блок, дополняя обычное описание проблемы и проверок:

```text
Work-Item-ID: <стабильный идентификатор результата, одинаковый между запусками>
Acceptance: <проверяемый результат и граница этапа>
Owner / run: <облачный или локальный основной агент / текущий запуск>
Phase: implementing | awaiting-ci | blocked | ready | merged
Base main: <SHA, на котором основана проверенная ветка>
Head: <фактический SHA своей ветки>
Validated head: <SHA успешных проверок либо pending>
Next: <одно конкретное действие>
Blocker: <причина либо none>
Failure: <шаг / краткая причина / число одинаковых подряд падений, включая прошлые циклы>
```

Это журнал восстановления, а не lock. Два одновременных запуска могут прочитать
одинаковое состояние. Проверка expected head при merge защищает head PR, но не
делает чтение main и merge одной атомарной операцией. При обнаруженном
пересечении новые записи останавливают; отсутствие гонок не гарантируется.

При публикации через GitHub connector сверять не только дерево, но и родителей
commit. Для merge commit основной родитель передаётся в `parent_sha`, остальные
по порядку в `additional_parent_shas`; иначе включение main в историю ветки
не подтверждено даже при совпадении файлов.

## Сценарии восстановления

| Ситуация | Решение |
| --- | --- |
| Свой PR открыт, CI ещё выполняется | Сохранить head и следующий шаг; новый этап не начинать |
| Ответ после создания PR потерян | Найти PR по ветке, ID и результату; продолжить существующий |
| Ответ после push потерян | Сверить удалённый head и дерево с ожидаемыми; не создавать второй commit вслепую |
| Ответ после merge потерян | Подтвердить merged-состояние и результат в main; не повторять реализацию |
| Тот же результат уже включён другим PR | Проверить код/тесты и закрыть свой этап как уже выполненный |
| PR закрыт без merge | Выяснить причину и применимость текущему main до повторной работы |
| Несколько PR одного этапа или прошлый writer ещё активен | Остановить новую запись и установить владельца |
| Независимый чужой PR открыт | Проверить пересечения; сам по себе он не блокирует весь проект |
| Своя ветка изменилась неожиданно | Не перезаписывать; установить автора и состояние |
| main изменился до публикации или merge | Включить свежий main в свою ветку без force; повторить необходимые проверки |
| Зелёный CI относится к прежнему head | Дождаться всех обязательных проверок окончательного head |
| GitHub недоступен, выдача неполна или состояние противоречиво | Остановить публикацию/merge и новую реализацию до восстановления достоверной сверки |
| Scratch исчез | Восстановить checkout из GitHub, продолжить существующую ветку и PR |
| CI повторно упал по той же причине | Применить правило двух неудач из AGENTS; сохранить блокер без бесконечных повторов |
| Подтверждённого следующего этапа нет | Сообщить результат, остановить автономное продолжение; новых требований не придумывать |

## Разработка и работающая установка

Проверять отдельно четыре состояния:

| Состояние | Доказательство |
| --- | --- |
| GitHub main | Фактический текущий SHA и merged PR |
| Рабочая ветка | HEAD, base, `git status`, её PR и CI на этом HEAD |
| Запущенное приложение | Ревизия исходников/образов именно работающей установки |
| Общая БД | Фактическая ревизия Alembic и совместимость с целевой версией приложения |

Эти значения могут временно различаться. Автономная разработка не выполняет
deployment и не обращается к общей БД. Резервная копия и старый checkpoint
не доказывают текущую ревизию работающей БД. Локальное обновление продолжается
только в рамках отдельного запроса и с сохранением данных.
