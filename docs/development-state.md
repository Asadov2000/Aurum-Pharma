# Текущее состояние разработки

Дата последней широкой проверки: 2026-09-06, ветка
`codex/authorization-denial-audit` поверх commit `0d85434`.
Подробные результаты и доказательства находятся в
[`project-health-audit-2026-08-30.md`](project-health-audit-2026-08-30.md).

Этот файл хранит только оперативное состояние проекта. Код, миграции, тесты и
принятые ADR имеют приоритет. После крупного слияния или релизной проверки файл
нужно обновлять, а не использовать как вечную спецификацию.

Уточнение политики доступа (ADR-0033): двухфакторная защита добровольна для всех
аккаунтов и управляется в «Настройки → Безопасность». При первом входе
предлагается подключение с возможностью пропуска. Критические действия
принимают повторный пароль или недавнее реальное MFA. Незавершённая настройка
не блокирует вход; ранее подключённые факторы сохраняются.

## Проверенный фундамент

- Архитектура остается модульным монолитом: FastAPI/PostgreSQL/Redis/Celery/MinIO
  и React/TypeScript/Vite. Переписывание стека или выделение абстрактного
  `Aurum Core` сейчас не требуется.
- В текущей ветке 140 последовательных Alembic-миграций. Развертывание с нуля до
  `head` проверяется на отдельной одноразовой PostgreSQL БД.
- Полный backend-набор: 1101 тест пройден в Docker-окружении. Ruff, Black и Mypy
  успешны; два предупреждения очистки asyncpg-соединения не влияют на результат,
  но остаются техническим долгом тестовой инфраструктуры.
- Полный frontend-набор: 728 Vitest-тестов прошли. Typecheck, ESLint и production
  build успешны.
- Последний полный Playwright-набор: все 68 пользовательских сценариев
  завершились успешно; сценарию прихода один раз потребовался встроенный retry
  из-за смены результатов поиска поставщика. После ожидания точного сетевого
  ответа этот сценарий отдельно прошёл без retry.
- Frontend dependency audit: известных уязвимостей нет. Backend-образы после
  обновления toolchain используют `pip 26.2.1`; `pip-audit` уязвимостей не нашел.
- Dev- и production-образы backend собираются. Production-контейнер запускается
  от непривилегированного пользователя `10001:10001`.
- Реализован зашифрованный logical backup PostgreSQL и MinIO через Restic с
  отдельными read-only credentials, retention и изолированным restore drill.
  Интеграционный тест подтвердил данные, объекты, SHA-256, владельцев, ACL и RLS.
- Реализованы PostgreSQL WAL archive, проверяемый physical base backup, точный
  PITR drill и экспорт зашифрованного Restic repository в независимый WORM bucket.
  Uploader не получает ключ расшифрования или право удаления. Независимый online
  verifier принимает только provider-approved version IDs, проверяет весь
  repository, а offline signer без сети требует отдельный операторский digest и
  подписывает checkpoint Ed25519. Restore не выбирает `latest`; подмена, отсутствие
  authorization и новая версия после подписи проверяются CI.
- Base images закреплены по digest; CI проверяет production-образы и формирует
  CycloneDX SBOM. Публикация и подпись release images остаются отдельной задачей.
- В проверенной БД tenant-таблицы покрыты RLS. Это не отменяет обязательные
  тесты изоляции при каждом новом tenant-домене.
- Семь внутренних направлений пилотного hardening завершены отдельными ветками:
  POS/деньги, каталог/FEFO, приходы/поставщики, роли/сотрудники, онбординг,
  отчёты/аудит/recovery и устойчивость web-клиента к кратким сбоям связи.
- Юридический допуск теперь имеет машиночитаемый fail-closed manifest и CI-тест.
  Режим `Enforce` остаётся красным до получения внешних доказательств.
- `ConnectivityProvider` централизованно различает краткий сбой проверки,
  подтверждённую недоступность API и отсутствие сети. Новые серверные операции
  блокируются после подтверждения сбоя, а денежные команды не повторяются
  автоматически (`a375010`, ADR-0031).
- Одна касса в одном профиле браузера имеет только одну активную вкладку POS.
  Ожидающая вкладка автоматически получает управление после освобождения
  стандартной Web Lock; отдельный E2E проверяет этот сценарий (`400a0f4`,
  ADR-0032).
- Критические операции проведения прихода и подтверждения электронного возврата
  требуют недавнее подтверждение паролем или MFA. БД запрещает критические permissions без
  повторного подтверждения и опасные permissions без подтверждения параметров. Отклонённые попытки изменения
  ролей и полномочий записываются отдельной транзакцией в неизменяемый аудит без
  тела запроса и персональных данных.

## Быстрый цикл без ослабления CI

- Backend, frontend, dependency audit, Chromium E2E, production containers и
  verification tooling уже выполняются параллельно. Последний замер
  `origin/main` завершил успешные application-gates за 17-284 секунды; дальнейшее
  дробление тестов без отдельной worker-изоляции сейчас не оправдано.
- `scripts/task-scope.ps1` классифицирует изменения fail-closed, а
  `scripts/verify-change.ps1` запускает целевые проверки в коротком локальном
  цикле. Неизвестные пути и критические области повышаются до полного риска.
- Production-образы используют раздельный Buildx/GitHub cache для backend,
  gateway и recovery tooling. Ошибка экспорта необязательного cache не блокирует
  проверку, а сами образы по-прежнему полностью собираются, сканируются и
  проверяются перед merge.
- GitHub `CI gate` остаётся полным и обязательным для каждого pull request.
  Локальные `Quick`/`Auto` проверки ускоряют обратную связь, но не заменяют его.
- Тестовый Redis отделён через `TEST_REDIS_URL` и сервис `redis-test`; ошибки
  очистки auth-состояния больше не скрываются. Чистые frontend-тесты используют
  Node вместо DOM, а E2E проверяет одноразовый проект перед изменением данных.
  Контракт запуска и границы замеров описаны в [testing.md](testing.md).

## Открытые риски до пилота

### P0 - блокирует безопасный production

1. Создать внешний WORM bucket в юридически допустимом регионе, независимо
   развернуть recovery-host, сохранить ключи Restic/Ed25519 и provider credentials,
   подключить оповещения о свежести/free-space и измерить RPO/RTO на
   production-подобном объёме. WAL/PITR, signed checkpoint и exact restore готовы.
2. Внутренний TLS между приложением и PostgreSQL, Redis и MinIO реализован
   fail-closed и проверен Docker smoke test. До пилота отрепетировать его на
   staging, проверить ротацию сертификатов и подключить expiry-оповещения.
3. Выдать production-секреты во внешнем secret storage, выполнить staging
   deployment и измерить backup/restore на объёме, близком к пилоту.
4. Репозиторная модель угроз оформлена в
   `docs/security/A-Pharma-threat-model.md`. Перед первым пилотом остаётся
   выполнить независимый penetration test. Абсолютную неуязвимость обещать
   нельзя; требуется проверяемая защита и восстановление.

### P1 - надежность и эксплуатация

1. Сделать backend-тесты повторяемыми на уже использованной одноразовой БД либо
   явно пересоздавать БД перед полным прогоном. Сейчас тест ротации MFA надежно
   проходит на чистой БД, но может встретить старые зашифрованные тестовые строки
   при повторном запуске полного набора.
2. Дополнить существующие лимиты файла/строк/колонок измеряемым memory/CPU budget,
   Celery timeout и tenant concurrency limit для импорта каталога.
3. Зафиксировать единый JWT-контракт с обязательными `iss`, `aud`, `typ` и `jti`,
   затем внедрить его через совместимую миграцию сессий и токенов.
4. Подготовить подписанный Windows MSIX/AppInstaller, проверку издателя,
   anti-rollback и безопасный allowlist WebView2 до распространения desktop-версии.

## Порядок наведения порядка

Текущий приоритет пользователя: проверенный веб-пилот для кассира и владельца.
Полноценная автономная касса отложена до отдельного приложения. Устойчивость к
короткому обрыву связи не означает разрешение продавать без доступного сервера.
Edge writer не активировать до закрытия readiness-gates из ADR-0001..0005.

1. Касса, оплаты, смены и возвраты: внутренние инварианты и E2E проверены. До
   банковской интеграции отметка оплаты означает подтверждение кассира и сверку,
   а не подтверждение банка.
2. Каталог, партии, FEFO и сроки: внутренние инварианты и E2E проверены;
   официальный регуляторный master-каталог остаётся внешним gate.
3. Приходы и поставщики: повторное/параллельное проведение, происхождение и
   связанная деактивация проверены.
4. Роли и сотрудники: создание владельцем только своих сотрудников, границы
   делегирования, отзыв сессий и tenant-изоляция проверены.
5. Онбординг: путь создания аптеки и владельца проверен; реальные документы и
   разрешения остаются внешним gate.
6. Отчёты, аудит и восстановление: код, локальный restore и E2E проверены;
   внешний WORM storage и измеренные staging RPO/RTO остаются блокером.
7. Нестабильная сеть: web-клиент блокирует новые команды при недоступном API,
   сохраняет текущий чек и после восстановления перечитывает активные данные без
   автоматического повтора денежных команд. Полный offline POS не включён.
8. Юридический и пилотный допуск: закрыть применимые пункты
   `compliance/pilot-legal-gate.md`, внешние подтверждения и эксплуатационные P0
   (staging TLS/rotation, production secrets, staging restore, проверка
   безопасности).
   Успешные тесты кода сами по себе не означают юридический допуск.

После прохождения этих проверок возможен ограниченный веб-пилот одной аптеки.
Для будущего приложения отдельно нужны offline-auth, Edge-owned наличная продажа,
синхронизация, recovery-проверки и подписанный Windows-клиент.
Разбирать локальные ветки и worktree только после сохранения всех грязных
   изменений и подтверждения, что соответствующий код уже находится в `main`.

## Правило обновления

После каждого широкого аудита записывать дату, commit, точные результаты тестов
и только подтвержденные проблемы. Закрытый пункт удалять из `known-issues.md` и
переносить в историю PR/commit, чтобы список не превращался в архив.
