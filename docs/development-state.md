# Текущее состояние разработки

Дата проверки: 2026-08-25. Проверено относительно `origin/main` на commit
`82d76d3` с актуализированным production hardening.

Этот файл хранит только оперативное состояние проекта. Код, миграции, тесты и
принятые ADR имеют приоритет. После крупного слияния или релизной проверки файл
нужно обновлять, а не использовать как вечную спецификацию.

## Проверенный фундамент

- Архитектура остается модульным монолитом: FastAPI/PostgreSQL/Redis/Celery/MinIO
  и React/TypeScript/Vite. Переписывание стека или выделение абстрактного
  `Aurum Core` сейчас не требуется.
- В репозитории 110 последовательных Alembic-миграций. Развертывание с нуля до
  `head` прошло на отдельной одноразовой PostgreSQL БД.
- Полный backend-набор: 895 тестов успешно.
- Полный frontend-набор: 607 Vitest-тестов успешно; typecheck, ESLint и
  production build успешно.
- Полный Playwright-набор: 57 пользовательских сценариев завершены; один POS
  сценарий со сканером прошел только со второй попытки и отмечен ниже.
- Frontend dependency audit: известных уязвимостей нет. Backend-образы после
  обновления toolchain используют `pip 26.2.1`; `pip-audit` уязвимостей не нашел.
- Dev- и production-образы backend собираются. Production-контейнер запускается
  от непривилегированного пользователя `10001:10001`.
- Реализован зашифрованный logical backup PostgreSQL и MinIO через Restic с
  отдельными read-only credentials, retention и изолированным restore drill.
  Интеграционный тест подтвердил данные, объекты, SHA-256, владельцев, ACL и RLS.
- Base images закреплены по digest; CI проверяет production-образы и формирует
  CycloneDX SBOM. Публикация и подпись release images остаются отдельной задачей.
- В проверенной БД tenant-таблицы покрыты RLS. Это не отменяет обязательные
  тесты изоляции при каждом новом tenant-домене.

## Открытые риски до пилота

### P0 - блокирует безопасный production

1. Дополнить уже проверенный logical backup PostgreSQL механизмом WAL/PITR,
   независимой off-site WORM-копией, контролем свежести и измеренными RPO/RTO.
   MinIO versioning и локальный restore drill уже работают.
2. Завершить production transport security между приложением и PostgreSQL,
   Redis и MinIO. Внешний TLS уже не заменяет внутреннее шифрование.
3. Выдать production-секреты во внешнем secret storage, выполнить staging
   deployment и измерить backup/restore на объёме, близком к пилоту.
4. Перед первым пилотом выполнить отдельный threat model и независимый
   penetration test. Абсолютную неуязвимость обещать нельзя; требуется
   проверяемая защита и восстановление.

### P1 - надежность и эксплуатация

1. Устранить нестабильность Playwright-сценария POS со сканером: первый запрос
   `catalog/by-barcode` иногда превышает 15 секунд, повтор проходит.
2. Сделать backend-тесты повторяемыми на уже использованной одноразовой БД либо
   явно пересоздавать БД перед полным прогоном. Сейчас тест ротации MFA надежно
   проходит на чистой БД, но может встретить старые зашифрованные тестовые строки
   при повторном запуске полного набора.
3. Добавить жесткие лимиты размера, количества строк и времени обработки для
   импорта каталога, чтобы большой или специально подготовленный файл не мог
   исчерпать память и CPU.
4. Зафиксировать единый JWT-контракт с обязательными `iss`, `aud`, `typ` и `jti`,
   затем внедрить его через совместимую миграцию сессий и токенов.
5. Подготовить подписанный Windows MSIX/AppInstaller, проверку издателя,
   anti-rollback и безопасный allowlist WebView2 до распространения desktop-версии.

## Порядок наведения порядка

1. Влить актуализированный production hardening только после полного зеленого CI.
2. Реализовать WAL/PITR, off-site WORM и контроль свежести backup/drill.
3. Добавить внутренний TLS для PostgreSQL, Redis и MinIO.
4. Закрыть PR `#77`-`#85`, если повторная проверка подтверждает нулевой diff с
   текущим `main`.
5. Разобрать локальные ветки и worktree только после сохранения всех грязных
   изменений. Worktree `6390` содержит незавершенную работу по auth/MFA и не
   подлежит удалению без отдельной проверки и commit.
6. После P0 продолжить продуктовые разделы, offline/Edge и desktop-клиент без
   смены текущего технологического фундамента.

## Правило обновления

После каждого широкого аудита записывать дату, commit, точные результаты тестов
и только подтвержденные проблемы. Закрытый пункт удалять из `known-issues.md` и
переносить в историю PR/commit, чтобы список не превращался в архив.
