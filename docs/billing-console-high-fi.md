# Aurum Pharma: high-fi концепция биллинга «Консоль»

Статус: выбранное направление; клиентский обзор и read-only сводка сотрудников реализованы

Версия: 1.0

Дата: 2026-08-13

Связано: [финансовая спецификация](billing-financial-spec.md),
[low-fi сравнение](billing-ux-low-fi.md),
[интерактивный high-fi прототип](mockups/billing-console-high-fi.html)

## 1. Решение

«Консоль» становится базовым визуальным направлением биллинга Aurum Pharma.
Для рабочего места сотрудников используется высокая плотность данных. Клиентская
часть сохраняет те же токены и структуру, но получает больше свободного места и
меньше одновременных действий.

Клиентский обзор перенесён в production frontend на существующих read-only API
подписки и счетов. Для сотрудников Aurum добавлены отдельная сводка счетов,
серверные фильтры и capability `platform.billing.view`. Денежные команды на этих
экранах отсутствуют. Очередь подтверждений, выпуск счетов, корректировки и тарифы
остаются прототипами до внедрения неизменяемого финансового журнала и безопасных
идемпотентных команд.

## 3. Визуальная система

- Системный шрифт, без внешней загрузки.
- Фон `#f3f6f7`, белые поверхности, тонкие границы `#d7e1e4`.
- Основной цвет `#087a70`; красный используется только для риска и отказа.
- Радиус 6-7px, минимальные тени, без blur и декоративных градиентов.
- Суммы используют табличные цифры и формат `1 650,00 TJS`.
- Статус передаётся текстом, маркером и цветом, а не только цветом.
- На экране не более одного главного действия.

Прототип позволяет сравнить обычную, компактную и сенсорную плотность. Даже в
компактном режиме интерактивная цель не становится меньше `44px`; сенсорный режим
использует `48px`.

## 4. Клиентский интерфейс

### 4.1 Обзор

Первая область без прокрутки показывает доступ, оплаченный срок, ближайшую сумму,
состояние проверки и одно следующее действие. Ниже находятся следующий платёж,
текущий тариф и финансовая хронология.

Если подтверждение уже проверяется, повторная отправка отсутствует. Клиент видит
номер заявления и действие **«Посмотреть проверку»**.

### 4.2 Подтверждение оплаты

Реквизиты доступны только для чтения и копирования. Клиент указывает сумму, дату,
банковский референс и документ. Перед отправкой серверный preview показывает счёт,
сумму, референс и результат проверки файла.

Текст **«Отправить на проверку»** не означает получение денег. После первого
нажатия кнопка блокируется. При обрыве ответа интерфейс проверяет результат по
`operation_id` и не предлагает повторить команду.

## 5. Рабочее место Aurum Pharma

### 5.1 Сводка

Верхняя строка содержит задачи, просроченный SLA, блокирующий долг и конфликты.
Ниже видны срочные операции и состояние финансовых фоновых процессов. Тяжёлые
графики не используются.

Создание новой цены открывает версионированный сценарий. Активная цена не
редактируется: создаётся будущая версия с датой начала, областью применения,
причиной, preview влияния и сроком уведомления.

### 5.2 Проверка платежа

На широком экране рядом находятся очередь и рабочая область. На `1024px` очередь
скрывается, а проверка становится отдельной страницей. Основная область показывает
заявление, банковскую выписку, документ, серверное распределение, долг и доступ
после операции.

Подтверждение требует MFA. Финансовый диалог:

- показывает точный эффект до команды;
- не закрывается кликом по фону или `Escape`;
- удерживает клавиатурный фокус;
- блокирует кнопку до полного MFA-кода;
- после отправки запрещает повторное решение.

## 6. Матрица состояний

| Состояние | Что видит пользователь | Разрешённое действие |
| --- | --- | --- |
| Загрузка | Стабильные skeleton-блоки без ложных `0,00 TJS` | Ожидание или безопасная навигация |
| Слабая сеть | Время последней синхронизации и явное предупреждение | Только чтение, проверить сеть |
| Ошибка чтения | Причина и безопасный повтор read-запроса | Повторить загрузку |
| Файл в quarantine | Файл изолирован, просмотр и решение заблокированы | Ожидать или запросить другой файл |
| Возможный дубль | Причины совпадения без раскрытия другого tenant | Открыть внутреннюю связанную операцию |
| Нет банковского ID | Автоматическое подтверждение заблокировано | Ручная сверка или уточнение |
| Нужен второй сотрудник | Автор не может утвердить собственную операцию | Передать утверждающему |
| Неизвестный результат | `operation_id` и запрет повторной команды | Проверить статус |
| Решение принято | Фактический серверный результат | Только просмотр |
| Недостаточно прав | Недоступные поля и действия не рендерятся | Обратиться к уполномоченному сотруднику |

В интерактивном прототипе сценарии проверки переключаются селектором **«Сценарий
high-fi макета»**. Общие состояния загрузки, сети и ошибки переключаются в верхней
панели прототипа.

## 7. Адаптация

| Режим | Поведение |
| --- | --- |
| `1366px+` | Полная консоль, очередь и рабочая область рядом |
| `1024px` | Свёрнутая навигация, не более двух колонок, проверка без очереди |
| Узкое окно / 200% | Одна колонка, без горизонтальной прокрутки страницы |
| Сенсорный экран | Цели `48px`, увеличенные строки и отсутствие hover-only действий |

Вкладки и формы работают клавиатурой. Focus-ring всегда видим. Финансовые диалоги
возвращают фокус на вызвавшую кнопку после явного закрытия.

## 8. Граница реализации

До production-разработки необходимо отдельно утвердить:

1. capability matrix клиентских и platform-действий;
2. API preview и idempotency contract денежных команд;
3. состояния upload/quarantine и безопасный просмотр документов;
4. MFA и правила второго утверждающего;
5. версионирование цен и журнал доставки уведомлений;
6. визуальные regression-тесты для всех состояний из этой спецификации.
