# Аудит состояния Aurum Pharma — 2026-08-30

## Резюме

Проверен `origin/main` на commit `d2e44fe`. Проект имеет зрелый фундамент для
закрытого demo и дальнейшего пилота: модульный монолит, строгую tenant-изоляцию,
RLS, отдельные роли PostgreSQL, иммутабельные продажи и аудит, идемпотентные
кассовые команды, защищенную авторизацию, проверяемые backup/PITR-контракты,
production-контейнеры и широкий автоматизированный CI.

Критических уязвимостей в коде или известных уязвимостей в зафиксированных
Python/JavaScript-зависимостях на момент проверки не обнаружено. Это не означает
абсолютную неуязвимость. Проект пока нельзя считать готовым к публичному
production: основные блокеры находятся в инфраструктуре, эксплуатации,
независимой проверке безопасности и незавершенном production Edge/offline.

## Область проверки

- архитектурные границы backend/frontend и принятые ADR;
- авторизация, cookies, CORS, trusted hosts/proxies, security headers;
- tenant/RLS и привилегированные DB-роли;
- POS, платежные состояния, возвраты, аудит и идемпотентность;
- импорт и загрузка файлов;
- Docker, production Compose, backup/PITR/WORM и supply chain;
- lock-файлы, dependency audit и актуальность major-линий;
- миграции, unit/integration/E2E и CI;
- готовность ключевых сценариев продавца и владельца;
- соответствие оперативной документации фактическому `main`.

Предполагаемая модель развертывания: сейчас локальная закрытая разработка с
эпизодическим доступом через Tailscale; далее публичный многопользовательский
SaaS. Банковские интеграции пока не подключены. Production Edge должен включаться
только после выполнения его fail-closed readiness-контрактов.

## Подтвержденные сильные стороны

1. Production-конфигурация отказывается запускаться со слабыми секретами,
   небезопасными cookie, CORS, trusted hosts/proxies, Redis/DB URL и development
   Edge credentials: `backend/app/core/config.py`.
2. Access token хранится только в памяти frontend, refresh token — в `httpOnly`
   cookie с `Secure` вне development; refresh/logout проверяют Origin:
   `backend/app/domains/auth/router.py`, `frontend/src/stores/auth.ts`.
3. API-документация выключена вне development. Gateway скрывает `/metrics` и
   служебные API-маршруты, ограничивает request body и выставляет CSP, HSTS,
   COOP/CORP и остальные защитные заголовки: `backend/app/main.py`,
   `infra/share/Caddyfile`.
4. Production-контейнеры используют закрепленные digest, непривилегированного
   пользователя, read-only filesystem, `no-new-privileges` и drop capabilities.
   CI выполняет secret/config/image scan и формирует CycloneDX SBOM.
5. Импорт уже ограничен размером 10 МБ, 50 000 строками и 64 колонками;
   изображения — 5 МБ с декодированием и повторным кодированием.
6. Edge writer и положительный offline-auth по умолчанию fail-closed. Наличие PWA
   не выдается за полноценную автономную кассу.
7. На проверенном commit успешно завершились все восемь GitHub checks: backend,
   frontend, dependency audit, Chromium E2E, production containers, Windows и
   Ubuntu verification tooling и итоговый `CI gate`.

## Открытые риски

### P0 — блокирует публичный production

1. **Внешнее восстановление еще не доказано на реальной инфраструктуре.** Код
   WAL/PITR, WORM export, checkpoints и restore drill готов, но нужны отдельный
   bucket/host, независимые ключи, alerts и замер RPO/RTO на staging-объеме.
2. **Внутренний transport security не завершен.** PostgreSQL, Redis и MinIO между
   production-компонентами должны работать по TLS с проверкой сертификатов.
3. **Нет выданных production-секретов и production-like staging rehearsal.**
   Секреты должны поступать из внешнего secret storage; нужен полный deploy,
   backup и restore drill до первого пилота.
4. **Нет независимого penetration test.** После закрытия инфраструктурных P0
   требуется внешняя проверка web/API, tenant isolation, POS и восстановления.

### P1 — закрыть до расширенного пилота

1. **Release artifacts пока не публикуются и не подписываются.** Нужны registry,
   digest-only deployment, Cosign/OIDC, provenance и обязательная проверка
   подписи перед запуском.
2. **JWT-контракт неполный.** Токен имеет `sub`, `iat`, `exp`, но пока не требует
   `iss`, `aud`, `typ` и `jti`: `backend/app/core/security.py:328`. Внедрять
   отдельной совместимой задачей с ротацией/переходным окном и тестами.
3. **Хеширование паролей зависит от устаревшей связки Passlib 1.7 + bcrypt 3.2.**
   Известных CVE аудит не нашел, но поддержка заморожена. Нужен переход на
   Argon2id через актуальную библиотеку с проверкой старого bcrypt и
   rehash-on-login, без принудительного сброса паролей.
4. **Импорт ограничен, но пиковая стоимость обработки остается высокой.** Файл
   читается в память, затем до 50 000 строк разбираются целиком. Нужны измеряемый
   memory/CPU budget, timeout Celery, конкурентный лимит на tenant и тесты
   специально тяжелых XLSX/CSV.
5. **Production offline POS еще не готов.** Контракты handover, bootstrap,
   offline-auth и cash kernel существуют, но активация намеренно запрещена до
   mTLS, защищенной локальной БД, trusted time, signed bootstrap и recovery drill.

### P2 — инженерная зрелость

1. **Нет метрики покрытия и истории тренда.** Большой набор тестов полезен, но
   без coverage невозможно автоматически увидеть непроверенный новый код.
   Добавить отчет покрытия без немедленного жесткого глобального процента, затем
   ввести threshold только для нового/измененного кода.
2. **E2E gate использует только Chromium.** Это соответствует WebView2 и
   основному desktop/web-профилю, но для браузерной версии нужен хотя бы
   scheduled smoke в Firefox; WebKit добавлять только если он войдет в список
   поддерживаемых браузеров.
3. **Есть исторические коллизии ADR-номеров:** два `0019` и два `0021`.
   Переименование принятых ADR может сломать ссылки, поэтому существующие имена
   сохранить, создать ADR-index со стабильными slug и запретить новые дубликаты.
4. **Версии библиотек требуют управляемой модернизации.** Известных уязвимостей
   нет; major-обновления React, Vite, Redis, Celery, Alembic и других компонентов
   нельзя смешивать с функциональной разработкой. Обновлять небольшими группами
   через Renovate/Dependabot и полный CI.
5. **Оперативная документация отставала от `main`.** Числа и очередь обновлены в
   этом изменении; далее это должно проверяться после каждого широкого merge.

## Приоритет пользовательских сценариев

### Продавец

1. Вход и открытие смены без ложных блокировок.
2. Быстрый поиск/сканирование, FEFO, остаток и срок годности.
3. Наличная продажа и подтвержденные card/QR состояния без двойного списания.
4. Печать/повтор чека, корректный возврат новой связанной операцией.
5. Понятное поведение при слабой связи; после Edge — безопасная cash-only работа.

### Владелец

1. Изоляция своей аптеки и филиалов, конструктор прав в пределах делегирования.
2. Каталог, поставщики, приход, партии, списание и карантин возврата.
3. Смены, чеки, отчеты и аудит с объяснимыми расхождениями.
4. Настройка способов оплаты, сотрудников, устройств и безопасности.
5. Billing без скрытого изменения цены задним числом и с версионной историей.

## Решение по текущему коду

Фундамент переписывать не нужно. Массовое обновление стека также не требуется.
Следующие изменения должны идти небольшими независимыми PR с полным `CI gate`.
Сначала закрываются инфраструктурные P0, затем JWT/пароли/import limits, после
чего production Edge и Windows-клиент допускаются к пилотной проверке.
