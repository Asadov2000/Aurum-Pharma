# Локальный Edge read model: контрольный замер 2026-09-23

## Методика

`scripts/benchmark-edge-read-model.ps1` создаёт уникальную внутреннюю Docker-сеть
и одноразовый PostgreSQL без host ports и named volumes. Общая dev/demo БД,
Compose-проекты и `.env` не используются. Перед созданием клиента Python-контроллер
принимает только фиксированные host, имя БД и роли `aurum_app`/`aurum_support`.
Стенд всегда удаляется в `finally`.

Миграции поднимаются до `0150`. Синтетическая проекция содержит 100 000 товаров,
по одному штрихкоду на товар и 250 000 партий. Это repository microbenchmark:
он измеряет SQL-запросы `SyncEdgeRepository` и преобразование ответа
`LocalReadModel` под RLS-контекстом аптеки, филиала и узла:

- поиск одного товара по фрагменту названия;
- точный поиск карточки по штрихкоду;
- первая страница партий вместе с общей сводкой остатков, отдельно с нулевыми
  остатками и без них.

Первый вызов фиксируется как `first_query_ms`. Это только первый запрос в данном
запуске, без утверждения о пустом кэше процесса, PostgreSQL или ОС. Следующие
30 вызовов дают p50/p95/max. Reader-соединение открывается до массовой вставки и
остаётся в отдельном pool; installer записывает данные через другое физическое
соединение. После `ANALYZE` и 30 секунд ожидания benchmark подтверждает прежний
PostgreSQL backend PID и ограничивает первое чтение `statement_timeout`:
300 мс для каталога и партий, 150 мс для штрихкода.

Перед замером роль `aurum_app` видит все строки в правильном RLS-контексте.
Затем benchmark по отдельности подменяет tenant, branch и node; во всех трёх
отрицательных сценариях строки проекции обязаны быть невидимыми.

```powershell
.\scripts\benchmark-edge-read-model.ps1
```

## Результаты

База: рабочая ветка от `f91c35f`, backend image
`sha256:ad06d823e8e76eb8cd0c893b6c65261fd1faa67997d803d65e7ba4fbe1cc6699`.
PostgreSQL ограничен 4 CPU и 8 GiB; Docker Desktop запущен на машине разработчика.
Ниже приведён исходный успешный прогон. Подготовка данных заняла 259,494 секунды,
стабилизация — 30,031 секунды. Его повторные прогоны не подтвердили устойчивость:
первая страница партий превышала 300 мс (коды 64 и 66). В медленном прогоне
наблюдались ожидания `DataFileRead` и `DataFileWrite`. После упорядоченной записи
партий два из трёх прогонов прошли, третий снова превысил 300 мс. При буфере
PostgreSQL 512 МБ следующие три последовательных прогона прошли лимиты: первое
чтение каталога 42,750–60,009 мс, штрихкода 34,228–40,428 мс, партий без
нулевых остатков 17,057–18,499 мс, с нулевыми 11,123–15,160 мс. Steady-state
p95 партий во всех трёх прогонах составил не более 11,512 мс.

## Вывод и границы доказательства

Все четыре steady-state операции ниже своих справочных ориентиров. Предрасчитанная
сводка сохраняет одинаковые суммы для обоих режимов `show_empty`, а количество
партий и заблокированных партий учитывает выбранный режим.

Старый probe совмещал массовую установку и чтение в одном engine/pool, хотя Edge
worker и API работают разными процессами. Исправленный стенд разделяет writer и
reader и при этом сохраняет reader, открытый до установки. Он выявил дорогую
сортировку широких JSONB-строк в прежнем page-query.
Миграция 0150 расширяет частичный индекс доступных партий полем `batch_id`, а
repository сначала получает идентификаторы страницы и затем читает максимум 20
полных строк. На одном прогоне первые запросы прошли лимиты, но повторные
прогоны показали задержку при загрузке полной страницы. На уже прогретой БД
`EXPLAIN` показывал чтение по первичному ключу быстрее 1 мс; это не объясняло
периодический провал первого вызова. При медленном первом чтении отдельный
observer зафиксировал ожидания дисковых чтений и записей. Установка теперь пишет
партии в порядке `batch_id`, а изолированный стенд задаёт PostgreSQL буфер
512 МБ при общем лимите 8 ГБ. Для реального Edge нужна проверка такой настройки
на целевом ПК, в том числе вместе с backend и Windows-клиентом.

Benchmark использует тестовый source verifier. Он не устанавливает полный
подписанный snapshot, не проверяет криптографию и active pointer, не измеряет
HTTP, UI-навигацию, параллельную кассу, синхронизацию или 30-дневный backlog.
`acceptance_claimed=false`: Linux-контейнерный замер не заменяет acceptance на
обычном аптечном ПК с Windows 11, 4 CPU, 8 GB RAM и SSD. Следом нужны холодная
полная криптографическая установка и Windows WAN/restart/restore прогон.
