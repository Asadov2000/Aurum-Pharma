# Aurum Pharma — Спецификация v3

> **Версия:** 3.0
> **Дата:** май 2026
> **Статус:** актуальная, для разработки Этапа 1
> **Заменяет:** v1, v2

---

## 0. Введение

### 0.1 Что это

**Aurum Pharma** — SaaS-система автоматизации аптек для Республики Таджикистан. Целевой пользователь — аптечные сети (от 1 до ~30 точек). Сравнимый продукт — 1С:Аптека, но веб, мульти-тенантный, по подписке.

### 0.2 Этапы продукта

| Этап | Цель | Срок |
|---|---|---|
| **Этап 1 (MVP)** | Минимум жизнеспособный для первых 5–10 пилотных клиентов в Душанбе | **5–6 месяцев** |
| **Этап 2** | Расширение функционала и снятие технического долга. Платный запуск | 3–4 месяца |
| **Этап 3** | Продвинутые функции: офлайн, фискализация, мульти-сеть, локализация | 6+ месяцев |

### 0.3 История версий

- **v1** — первичная спека, Этап 1 в 6 месяцев
- **v2** — наращивание scope до 17 блоков, срок раздулся до 11–14 месяцев из-за gold-plating
- **v3 (текущая)** — ревизия после code review. Возврат к 5–6 месяцам через жёсткое урезание scope. Заморожены: полный офлайн, расширенная безопасность, омниканальная поддержка, расширенные импорты, per-user override прав, временная выдача прав, своя метрика-инфраструктура.

### 0.4 Ключевые архитектурные инварианты

1. **Мульти-тенантность через PostgreSQL Row Level Security** (а не через приложение)
2. **Иммутабельные продажи**: completed-чек не редактируется, только возврат новым чеком
3. **Audit-log через триггеры PostgreSQL** (а не через приложение)
4. **Trunk-based development** + по одному домену за раз
5. **Strict TypeScript, strict mypy, реальный PostgreSQL в тестах**

## 1. Иерархия ролей

### 1.1 Уровни

В Этапе 1 есть **2 системные support-роли** (`developer`, `administrator`) и **тенантные роли** внутри аптеки. Базовые роли аптеки (`Владелец`, `Кассир`) создаются из глобальных шаблонов. Владелец может создавать и редактировать кастомные роли своего тенанта, но без per-user override.

| Уровень | Роль | Описание | Кому |
|---|---|---|---|
| 1 | **Developer** | Все права, включая глобальные (master-каталог, кросс-тенантная аналитика) | Команда разработки Aurum |
| 2 | **Administrator** | Все права в любом тенанте, кроме разработческих | Support-команда Aurum (по мере найма) |
| 3 | **Владелец / Owner** | Все права в своём тенанте, кроме глобального support-доступа | Владелец аптеки/сети |
| 4 | **Кассир / Seller** | Касса + поиск товаров + просмотр собственного аудита | Продавцы на точках |

### 1.2 Назначение пользователей

- **Уровни 1–2** (developer/administrator) — не привязаны к конкретным тенантам, работают через support pool БД (BYPASSRLS)
- **Уровни 3–4** (`Владелец`/`Кассир` и кастомные роли) — tenant-scoped роли с `role.tenant_id`, назначаются через `user_assignment`
- **Branch-level assignment**: владелец обычно назначается на весь тенант (`branch_id=NULL`), кассир и кастомные роли могут быть привязаны к конкретной точке
- **Role builder**: пользователь может создать только роль строго слабее своего уровня, только с теми permissions, которыми владеет сам, и только с permissions, чей `min_level_required` подходит уровню создаваемой роли. `developer`/`administrator` считаются support-пользователями и могут создавать роли ниже своего уровня.

### 1.3 Что НЕ входит в Этап 1

- ❌ Override прав отдельному пользователю
- ❌ Временная выдача прав на период

Эти возможности — Этап 2.

## 2. Аутентификация

### 2.1 Способы входа

| Способ | Использование |
|---|---|
| **Email + 6-значный код** | Основной способ. Код приходит на email, валиден 10 минут |
| **Email + код + пароль** | Опционально: владелец может потребовать пароль для всех сотрудников |
| **PIN на кассе** | Опционально: после входа продавца на смену переключение между кассирами — по 4-значному PIN. Включается в `tenant_settings.pin_mode_enabled` |
| **TOTP (2FA)** | Только для Уровней 1–2. Этап 2 — для Уровней 3–4 |

### 2.2 Токены

- **Access token (JWT)**: 15 минут TTL. Содержит `user_id`, `tenant_id`, флаги `is_developer/is_administrator`. **НЕ содержит список permissions** (они кешируются в Redis, ключ `auth:perms:{user_id}:{tenant_id}`, TTL 5 минут)
- **Refresh token**: 7 дней TTL. Хранится hash (sha256) в БД таблице `session`. Ротация при каждом использовании
- **Refresh-токен в Этапе 1 хранится в localStorage** — известный риск XSS, перенос в httpOnly cookie запланирован на Этап 2

### 2.3 Rate limiting

- Запрос email-кода: не более 1 в минуту и 10 в час на email
- Попытки логина: 5 неудач за 15 минут блокируют email+IP на 15 минут
- Реализация: проверка через `login_attempt`-таблицу в БД (не Redis, чтобы перезапуск Redis не сбрасывал блокировки)

### 2.4 Сессии

- Идемпотентный logout: revoke refresh-токена по hash, очистка Redis-кеша
- Параллельные сессии: разрешены (планшет + телефон + 2 кассы)
- Принудительный logout всех сессий пользователя — через permission `users.block`

## 3. Мульти-тенантность

### 3.1 Модель

**Shared Database, Shared Schema, RLS-based isolation.**

- Одна БД на весь продукт
- Каждая бизнес-таблица имеет `tenant_id`
- RLS-политика `tenant_isolation` на каждой такой таблице:
  ```sql
  USING (tenant_id = current_tenant_id() OR is_support_session())
  ```
- `current_tenant_id()` читает GUC `app.tenant_id`
- `is_support_session()` читает GUC `app.support_session`
- GUC устанавливаются в middleware из JWT при каждом запросе

### 3.2 Два пула соединений

| Пул | Роль БД | RLS | Кто использует |
|---|---|---|---|
| `aurum_app` | `aurum_app` | Включён | Пользователи Уровней 3–4 (owner, seller) |
| `aurum_support` | `aurum_support` | BYPASSRLS | Пользователи Уровней 1–2 (developer, administrator) |

Middleware выбирает пул в зависимости от пользователя. Этот выбор **критичен** — если ошибиться, developer не сможет помочь клиенту, потому что RLS отрежет ему доступ.

### 3.3 Создание тенанта

В Этапе 1 — **только через support** (developer/administrator). Сценарий: владелец заполняет форму запроса на сайте → support получает email → создаёт тенанта вручную через admin-эндпоинт → отправляет владельцу приглашение по email.

Самообслуживание (signup-форма) — Этап 2.

### 3.4 Drug catalog mode

В `tenant.drug_catalog_mode`:
- `autonomous` — тенант сам ведёт свой каталог (Этап 1, единственный режим)
- `connected` — тенант использует общий master-каталог Aurum как референс (Этап 2)

## 4. Каталог permissions

### 4.1 Принципы

- Каждый permission — строка-код вида `<group>.<action>`, например `pos.sell`, `catalog.update`
- Permission имеет `min_level_required` — минимальный уровень роли, которая может его получить
- Permission имеет флаг `is_dangerous` — для UI-предупреждений и аудита

### 4.2 Группы и коды (45 permissions для Этапа 1)

#### users (5)
- `users.view` — просмотр списка сотрудников
- `users.invite` — приглашение нового сотрудника
- `users.update` — изменение профилей
- `users.block` — блокировка
- `users.delete` — soft-delete

#### roles (3)
- `roles.assign` — назначение роли пользователю на точке
- `roles.create` — создание кастомной роли внутри аптеки
- `roles.update` — изменение кастомной роли внутри аптеки

#### branches (4)
- `branches.view`
- `branches.create`
- `branches.update`
- `branches.delete`

#### registers (4)
- `registers.view`
- `registers.create`
- `registers.update`
- `registers.delete`

#### catalog (4)
- `catalog.view`
- `catalog.create`
- `catalog.update`
- `catalog.delete`

#### batches (4)
- `batches.view`
- `batches.create`
- `batches.update`
- `batches.write_off`

#### suppliers (3)
- `suppliers.view`
- `suppliers.create`
- `suppliers.update`

#### incoming (3)
- `incoming.view`
- `incoming.create`
- `incoming.return`

#### pos (5)
- `pos.shift_open`
- `pos.shift_close`
- `pos.sell`
- `pos.refund`
- `pos.handle_prescription`

#### sales (2)
- `sales.view.own` — просмотр только своих чеков
- `sales.view.tenant` — просмотр всех чеков аптеки

#### reports (2)
- `reports.view`
- `reports.export`

#### audit (3)
- `audit.view.own` — свой персональный аудит
- `audit.view.tenant` — аудит всех в своём тенанте
- `audit.view.global` — кросс-тенантный аудит (только developer)

#### settings (1)
- `settings.update` — настройки своего тенанта

#### tenant (2)
- `tenant.view`
- `tenant.export.full` — полный экспорт данных тенанта

### 4.3 Базовые наборы permissions по ролям и шаблонам

| Permission | Developer | Administrator | Owner | Seller |
|---|:-:|:-:|:-:|:-:|
| Все min_level=1 | ✅ | ❌ | ❌ | ❌ |
| Все min_level=2 | ✅ | ✅ | ❌ | ❌ |
| Все min_level=3 (кроме global) | ✅ | ✅ | ✅ | ❌ |
| `catalog.view`, `batches.view`, `pos.*`, `audit.view.own` | ✅ | ✅ | ✅ | ✅ |

В текущем коде `developer` и `administrator` остаются системными ролями (`tenant_id=NULL`), а `Владелец` и `Кассир` являются tenant-scoped ролями, создаваемыми из `role_template`. Кастомная роль хранит свой набор `role_permission`.

Для роли уровня `L` разрешены только permissions с `permission.min_level_required >= L`. Например, роль уровня 4 (`Кассир`) не может получить `users.invite`, даже если владелец сам имеет это право.

### 4.4 Расчёт эффективных прав

В Этапе 1 без override — права = `role.permissions` напрямую. Расчёт делается один раз при логине, кешируется в Redis с TTL 5 минут, инвалидируется при изменении назначения роли.

В Этапе 2 добавится `user_permission_override` (granted/revoked per-user per-branch), формула станет `role.permissions ∪ granted − revoked`.

## 5. Каталог ЛС

### 5.1 Структура

- `tenant_catalog` — товарные позиции конкретного тенанта (то, что он продаёт)
- `master_catalog` — заготовка под общий референсный каталог. **В Этапе 1 не используется** (тенанты ведут полностью свой каталог), но таблица создаётся для будущего расширения

### 5.2 Поля карточки tenant_catalog (Этап 1)

- Название (бренд) — обязательно
- МНН (международное непатентованное наименование) — необязательно
- Производитель
- Форма выпуска (таблетки/сироп/мазь/раствор/...)
- Дозировка (как текст: "500мг", "5мл/доза")
- Объём упаковки (как текст: "30 шт", "100 мл")
- ATX-код — необязательно
- Штрихкод (один или несколько, EAN-13 / GS1-128) — отдельная таблица `barcode`
- Тип отпуска: рецептурный / безрецептурный / специальный
- Тип хранения: обычное / холод (2–8°C) / морозильник
- Категория (свободный текст для группировки)
- Базовая цена продажи (опционально, может выставляться при приходе)
- Активна / архивна

### 5.3 Поиск

- По названию (бренд + МНН) — fuzzy search через `pg_trgm`
- По штрихкоду — точное совпадение
- По производителю — точное совпадение
- По категории — точное совпадение
- Комбинированные фильтры через querystring

Скорость: <200мс на каталоге до 50К позиций (типичный размер у одной аптеки — 5–15К).

### 5.4 Импорт каталога (Excel/CSV)

Из 4 путей импорта (Excel/CSV / 1С:Аптека / локальные ERP / ручной) в Этапе 1 — **только Excel/CSV**.

- Шаблон скачивается с сайта
- Поддержка кодировок: UTF-8, Windows-1251
- Маппинг колонок: автоматический (по заголовкам) + пользователь может скорректировать
- Dry-run: превью первых 50 строк, статистика (всего N, ошибок M, дубликатов K)
- После подтверждения — фоновая Celery-задача с прогрессом
- Идемпотентность: при повторе — выбор «пропустить дубликаты / обновить / создать копии»
- Откат: кнопка «Откатить импорт» доступна 24 часа (soft delete всех созданных в импорте записей)

### 5.5 Что НЕ входит в Этап 1

- ❌ Импорт из 1С:Аптека (XML/DBF) — Этап 2
- ❌ Импорт из локальных РТ-ERP — Этап 3
- ❌ Контроль цен (max наценка, RRC) — Этап 2
- ❌ Recall (отзыв партии регулятором) — Этап 2
- ❌ Автозаполнение по штрихкоду из публичных баз — Этап 3

## 6. Партии и сроки годности

### 6.1 Модель

- `batch` — партия товара (FEFO — First Expired First Out)
- `batch_movement` — движения партии (приход, продажа, списание, корректировка, возврат)
- Текущий остаток партии = сумма движений (или денормализованное поле `qty_remaining`, обновляемое триггером)

### 6.2 Сроки годности

В `tenant_settings.expiry_thresholds` (JSONB):
```json
{"yellow": 6, "orange": 3, "red": 1}
```
Это месяцы до истечения, при которых система помечает партию соответствующим цветом.

### 6.3 Продажа просроченного

Режим в `tenant_settings.expired_sale_mode`:
- `strict` — продажа просроченного полностью заблокирована
- `warning` — продажа разрешена, но требует подтверждения с указанием причины
- `off` — без контроля

### 6.4 Списание партии

Через `pos.write_off` permission. Поля:
- Партия и количество
- Причина (просрочка / повреждение / порча / кража / прочее)
- Свободный комментарий

Создаётся `batch_movement` с типом `write_off` и `write_off`-запись с актом (опциональная подпись/печать).

### 6.5 Что НЕ входит в Этап 1

- ❌ Recall (массовое блокирование партий)
- ❌ Резервирование партий (предзаказы) — Этап 2

## 7. Поставщики и приход

### 7.1 Модель

- `supplier` — поставщик с реквизитами
- `incoming_document` — приход (накладная)
- `incoming_item` — позиции прихода (создают `batch` при подтверждении)

### 7.2 Workflow прихода

В Этапе 1 — только **single-step**: оператор вводит документ, проверяет позиции, нажимает «Принять» → создаются партии. Without два-этапного «приёмка→оприходование».

### 7.3 Возврат поставщику

Через `incoming.return` permission. Отдельный документ `supplier_return`, привязан к исходному `incoming_document`. Списывает количество с партии (создаёт `batch_movement` типа `supplier_return`).

### 7.4 Что НЕ входит в Этап 1

- ❌ Two-step workflow (приёмка / оприходование) — Этап 2
- ❌ Кредиторская задолженность поставщикам — Этап 2
- ❌ Заказы поставщикам — Этап 3

## 8. Касса (продажи)

### 8.1 Модель смены

- Продавец **открывает смену** (`pos.shift_open`) — указывает начальную наличность в кассе. Создаётся `shift`-запись
- В рамках смены пробиваются продажи (`sale`)
- **Закрытие смены** (`pos.shift_close`) — Z-отчёт: общая сумма по способам оплаты, ожидаемая наличность vs фактическая, расхождения

### 8.2 Модель продажи

- `sale.status`: `draft` (в процессе ввода) / `completed` (выбит чек) / `voided` (отменён возвратом)
- `sale_item` — позиции продажи (партия, количество, цена)
- `sale_payment` — оплаты (одной продаже может соответствовать несколько оплат — смешанная: часть наличными, часть картой)

### 8.3 Иммутабельность

Это **критический инвариант**. После того как `sale.status = 'completed'`:

- ❌ Нельзя редактировать `sale_item`
- ❌ Нельзя редактировать `sale_payment`
- ❌ Нельзя удалить `sale`
- ❌ Нельзя изменить `sale.total_amount`

**Исправление ошибки** = создание новой `sale` типа «возврат»:
- `parent_sale_id` ссылается на исправляемую
- На исходной продаже выставляется `voided_at` и `voided_by_sale_id`
- В отчётах: продажа + её возврат = ноль

Сервис должен **явно отклонять** любые UPDATE на completed-продажах. Это enforced на уровне service.py, а не БД-триггера (мы хотим понятные ошибки клиенту, не loud-падения).

### 8.4 Способы оплаты

- Наличные
- Карта (без эквайринг-интеграции в Этапе 1 — продавец вручную проводит карту на стороннем POS-терминале и фиксирует факт в Aurum)
- Безналичный (счёт-фактура для юр.лиц)
- Смешанная (часть наличными, часть картой)

### 8.5 Прескрипционные ЛС

- При продаже товара с `dispensing_type='prescription'`:
  - На чеке печатается напоминание о лицензии (текст из `tenant_settings.prescription_warning_text`)
  - Опционально: продавец заполняет `prescription_log` (номер рецепта, врач, пациент) — настраивается в `tenant_settings`

### 8.6 Возвраты

В `tenant_settings.refund_reason_mode`:
- `required` — выбор из списка причин обязателен
- `required_with_text` — список + обязательный текстовый комментарий
- `optional` — необязательно
- `off` — без причины

### 8.7 Печать чека

- Два варианта одновременно: HTML-печать через браузер + термопринтер (через WebUSB/Bluetooth — настраивается в `register.printer_config`)
- Поддержка термопринтеров: 58mm, 80mm
- Формат: текстовый чек с шапкой тенанта, позициями, итогом, инфо о продавце, штрих-кодом чека

### 8.8 Что НЕ входит в Этап 1

- ❌ Офлайн-режим (касса требует стабильного подключения)
- ❌ Эквайринг карт (фискальная интеграция с POS-терминалом)
- ❌ SMS-чек
- ❌ Программа лояльности (бонусы, скидки клиентам)
- ❌ Бронирование (предзаказ через сайт)

## 9. Отчёты

### 9.1 Базовый набор Этапа 1 (7 отчётов)

1. **Продажи за период** — выручка, чеки, средний чек, разбивка по дням
2. **Топ-N товаров** — по выручке и количеству

## 10. Аудит-лог

### 10.1 Механика (Этап 1)

**Триггеры PostgreSQL** на тенантных таблицах. При INSERT/UPDATE/DELETE пишется запись в `audit_log`:
- `tenant_id`, `user_id` (из GUC), `action`, `table_name`, `record_id`
- `old_values`, `new_values` (JSONB, только изменённые поля)
- `created_at`

Это **дешевле, надёжнее и проще** чем application-level audit. Минус: не логирует «просмотры» — для этого добавляются отдельные явные вызовы из сервисов (например, просмотр закупочной цены, импersonate, экспорт).

### 10.2 Permissions

- `audit.view.own` — пользователь видит свой персональный аудит
- `audit.view.tenant` — владелец видит всех в своём тенанте (включая суппорта если он что-то делал в этом тенанте)
- `audit.view.global` — только developer, кросс-тенантный аудит

### 10.3 Partitioning

Партиционирование `audit_log` **по месяцам** добавляется при достижении ~10М записей (ожидаемо через 12–18 месяцев после запуска).

### 10.4 Защита

- В Этапе 1 — обычная таблица, RLS-политика как у других тенантных таблиц
- **Этап 2:** secure-таблица с `INSERT-only` permission для роли БД (никаких UPDATE/DELETE даже от приложения)
- **Этап 3:** криптоподпись + hash-chain (антирепудиация)

## 16. Тестирование

### 16.1 Стратегия

Подход «дешёвое и надёжное» вместо «всё подряд».

| Тип | Где применяется | Инструмент |
|---|---|---|
| **Unit** | Бизнес-логика сервисов с чистыми функциями | pytest |
| **Integration** | Эндпоинты + БД-операции | pytest + httpx + реальный PG в Docker |
| **Property-based** | Денежные расчёты, расчёт остатков, FIFO/FEFO-логика | Hypothesis |
| **E2E** | 10–15 критичных flow | Playwright |
| **Tenant isolation** | Каждая тенантная таблица | pytest, отдельный набор |

### 16.2 Минимум для нового домена

- 1 happy-path integration test
- 1 тест бизнес-правила (или граничного условия)
- 1 тест изоляции тенантов (если домен имеет тенантные таблицы)

### 16.3 Критичные E2E (~10–15)

1. Полный логин-flow (email-code → login → /me → refresh → logout)
2. Создание тенанта + назначение владельца
3. Импорт каталога Excel (happy path)
4. Создание прихода + проверка появления партии
5. Открытие смены → продажа → закрытие смены
6. Продажа просроченного товара (warning mode)
7. Возврат товара (новый sale + parent_sale_id)
8. Иммутабельность: попытка изменить completed-продажу → 409
9. Tenant isolation: пользователь тенанта A не видит данные тенанта B
10. Settings: изменение `expiry_thresholds` → обновление цветов на партиях
11. Аудит: изменение цены товара → запись в audit_log
12. Назначение роли seller на конкретную точку
13. Setup wizard: проход 8 шагов до старта trial

### 16.4 Покрытие

- **Прицельно:** изоляция тенантов 100%, бизнес-правила денежных расчётов 100%
- **Общее:** не гонимся за процентом. Тесты пишутся под критичные пути

### 16.5 Что НЕ делаем в Этапе 1

- ❌ Mutation testing (mutmut) — Этап 2
- ❌ Fuzzing API — Этап 2
- ❌ Contract testing (Pact) — Этап 2
- ❌ Snapshot testing UI — Этап 2
- ❌ Performance benchmarks системные — Этап 2
- ❌ QA-инженер в команде — после набора 10+ клиентов (соло-разработчик пишет тесты сам)

## 17. Запуск и поддержка

### 17.1 Онбординг

**Setup wizard (8 шагов):**
1. Профиль аптеки (название, контакты)
2. Первая точка (адрес, тип, лицензия)
3. Реквизиты для чека
4. Первый сотрудник (себя приглашаешь как owner — это уже done через support, тут показывается чек-марк)
5. Загрузка каталога (≥100 товаров — блокирующее условие старта trial)
6. Настройки кассы (печать, режимы)
7. Регуляторика (текст напоминания о лицензии)
8. Готово

**Чек-лист первых задач:**
- Загрузить каталог (≥100 товаров)
- Создать первый приход и партию
- Сделать тестовую продажу
- Пригласить второго сотрудника
- Открыть смену
- Распечатать тестовый чек

**Trial — двухфазная модель:**
- **Фаза 1 — «настройка»** (cap 60 дней): касса в демо-режиме (на чеках «ТЕСТ», `is_test=true`, партии не списываются)
- **Триггер старта trial:** владелец нажимает «Готов начать» (доступно при ≥100 товаров) ИЛИ автоматически через 60 дней
- **Фаза 2 — «trial»** (14 дней): полная функциональность, реальные продажи
- **После trial:** переход в платный план или grace period

### 17.2 Тарификация

- **Этап 1: 1 плоский план** «Aurum Pharma» — **$50-эквивалент/мес за точку**, оплата в TJS (фиксированная цена)
- Без лимитов на количество сотрудников

**Изменение количества точек:**

**Митигация валютного риска:** в договоре право индексации цен раз в 6–12 месяцев с уведомлением за 30 дней.

## 20. Глоссарий

- **Тенант** — изолированная организация-клиент (аптечная сеть)
- **Точка** — `branch`, физический магазин аптеки. Тенант может иметь от 1 до десятков точек
- **Касса** — `register`, POS-терминал на точке. Точка может иметь несколько касс
- **Смена** — `shift`, рабочая сессия продавца на конкретной кассе
- **Партия** — `batch`, конкретная поставка товара с конкретным сроком годности
- **FEFO** — First Expired First Out, приоритет продажи партий с ближайшим истечением
- **RLS** — Row Level Security, изоляция строк БД на уровне политик
- **Master-каталог** — общий справочник ЛС, поддерживаемый Aurum (используется в Этапе 2+)
- **Tenant-каталог** — товарный справочник конкретного тенанта
- **Trial** — пробный период, 14 дней с полной функциональностью
- **Setup phase** — фаза настройки до старта trial (до 60 дней), касса в демо-режиме
- **Grace period** — 7 дней после окончания подписки, полный доступ, ожидание оплаты
- **Read-only mode** — режим после grace, касса не работает, можно только экспортировать данные

## 21. Что обновить в коде при изменении этого документа

Этот документ — **источник истины** для функциональной части. При его изменении:

1. Обновить `docs/db-schema-v2.md` если изменилась структура данных
2. Обновить `docs/handoff.md` если изменился порядок доменов или сроки
3. Обновить `CLAUDE.md` если изменились архитектурные правила

Любое противоречие между этими 4 документами — **повод спросить пользователя**, а не выбирать наугад.
