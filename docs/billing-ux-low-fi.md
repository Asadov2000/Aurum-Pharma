## 1. Решение

Биллинг разделяется на два интерфейса с разными задачами и правами:

1. Клиент аптеки видит раздел **«Тариф и оплата»** внутри tenant-контекста.
2. Сотрудник Aurum Pharma видит отдельное platform-рабочее место **«Биллинг»**.

Текущий `BillingPage` является переходной клиентской реализацией. Текущий
`AdminBillingDrawer` не развивается: после готовности целевого API его заменит
отдельное рабочее место. До переключения legacy API остаётся доступным за feature
flag, но не считается production-источником финансовой истины.

Feature flag на уровне route динамически импортирует и монтирует только одно
поколение UI. Legacy и новый billing никогда не выполняют запросы параллельно.
Dual-write и fallback денежных команд запрещены: перед включением нового staff UI
legacy write endpoints отключаются сервером. Аварийный откат допускается только
для чтения; возврат legacy-мутаций требует отдельного контролируемого решения.

## 2. Общие правила

- На первом экране всегда видны статус, срок, сумма и одно главное действие.
- Одновременно показывается только один primary CTA. Остальные действия вторичны.
- Статус передаётся текстом и значком, а не только цветом.
- Подтверждённые деньги используют success; danger предназначен только для
  просрочки, блокировки и необратимых рисков.
- Суммы используют TJS и табличные цифры. Технические UUID клиенту не видны.
- Недоступные действия, вкладки, колонки и фильтры не рендерятся.
- Финансовые команды запрещены offline. Неопределённый результат проверяется по
  серверному operation ID до предложения повторить действие.
- Состав видимых фильтров можно настраивать, но их значения и банковские данные
  не сохраняются в браузере.
- Интерфейс использует текущие токены Aurum Pharma, радиус до 8px, тонкие границы,
  системные шрифты и только короткие CSS-переходы.

## 3. Клиент «Тариф и оплата»

### 3.1 Навигация

- **Обзор**
- **Счета**
- **Платежи**
- **Реквизиты**

Вкладки загружаются лениво. При отсутствии permission вкладка полностью скрыта.

### 3.2 Обзор

Порядок сверху вниз:

1. Строка критического состояния доступа.
2. Текущий тариф: период, филиалы, стоимость, оплачено до.
3. Следующий платёж: сумма, срок, расшифровка.
4. Последний счёт и последнее подтверждение перевода.
5. Частичная оплата или переплата, если они существуют.
6. Будущая версия цены, если уведомление уже допустимо доставлено.
7. Финансовый контакт и поддержка.

Приоритет главного действия:

| Приоритет | Условие | Статус для клиента | Главное действие |
| --- | --- | --- | --- |
| 1 | `readonly` и нет заявления на проверке | Доступ ограничен | Восстановить доступ |
| 2 | Требуется уточнение | Нужны данные | Ответить на запрос |
| 3 | Результат операции неизвестен | Проверяем операцию | Проверить статус |
| 4 | Заявление проверяется | Платёж проверяется | Посмотреть проверку |
| 5 | Заявление отклонено | Нужно исправить | Исправить подтверждение |
| 6 | Есть блокирующая задолженность | Требует оплаты | Оплатить задолженность |
| 7 | До конца trial не более 7 дней | Скоро первый платёж | Подготовить оплату |
| 8 | Всё покрыто | Подписка активна | Посмотреть следующий платёж |

Пока заявление проверяется, интерфейс не предлагает отправить тот же платёж
повторно. Уведомление о новой цене всегда ниже долга и проверки платежа.

### 3.3 Счета

Верхняя строка показывает общий остаток и ближайший срок. Реестр содержит:

- номер документа;
- тип документа;
- период;
- дату выпуска;
- срок;
- сумму;
- остаток;
- независимые состояния документа, расчёта и взыскания.

Настраиваемые фильтры: номер, тип, состояние расчёта, состояние взыскания и
период. Используется серверная пагинация. Детали открываются справа на широком
экране и отдельной страницей на `1024x768` или при масштабе 200%.

Детали показывают неизменяемые строки расчёта, филиалы, скидки, корректирующие
документы, платежные allocations, остаток и сохранённый PDF.

### 3.4 Платежи

Порядок:

1. Переплата, если она есть.
2. Заявления, требующие действия клиента.
3. Заявления на проверке.
4. Подтверждённые платежи.
5. Refund и reversal как отдельные понятные операции.

Главный CTA: **«Отправить подтверждение оплаты»**. Он скрывается, если у
пользователя нет права создания заявления.

### 3.5 Отправка подтверждения

Поток состоит из трёх шагов:

1. Выбор счёта, просмотр остатка и реквизитов Aurum Pharma.
2. Сумма, дата, банковский референс и загрузка документа.
3. Проверка всех данных и отправка.

Файл загружается через серверную upload-сессию с явными состояниями:
`создана`, `загружается`, `приостановлена`, `проверяется`, `готова`, `отклонена`,
`истекла`, `отменена`. После перезагрузки состояние читается с сервера.

### 3.6 Реквизиты

Клиент редактирует только данные организации и финансовые контакты. Банковские
реквизиты Aurum Pharma доступны только для чтения. Подтверждённые изменения
сохраняются в истории.

## 4. Рабочее место Aurum Pharma «Биллинг»

### 4.1 Навигация

- **Сводка**
- **Очередь платежей**
- **Клиенты**
- **Счета**
- **Корректировки**
- **Тарифы**
- **Аудит**

Каждая вкладка проверяет отдельную platform capability. Единой широкой кнопки
`platform.billing.manage` в целевой модели нет.

### 4.2 Сводка

Первый viewport содержит:

- ожидающие проверки;
- клиентов в grace и readonly;
- блокирующую задолженность;
- нераспределённые деньги;
- срочные задачи по SLA;
- аномалии и конфликты.

Главный CTA: **«Проверить следующий платёж»**. Тяжёлые графики не используются;
возраст долга показывается компактными полосами и таблицей.

### 4.3 Очередь платежей

На широком экране:

1. Реестр очереди.
2. Заявление и банковский документ.
3. Серверный preview распределения.
4. Журнал решения.

На `1024x768` проверка открывается отдельной страницей. Действия:
`Подтвердить`, `Запросить уточнение`, `Отклонить`, `Передать на дополнительную
проверку`. Подтверждение показывает точный эффект и требует MFA.

Обязательные состояния: quarantine, антивирусная проверка, подозрение на дубль,
нет банковского ID, конфликт сотрудников, решение уже принято, требуется второй
утверждающий, нераспределённый остаток и неопределённый результат.

### 4.4 Клиенты

Реестр фильтруется по доступу, долгу, тарифу и филиалам. Карточка клиента содержит
подписку, доступ, долг, кредит, филиалы и единую финансовую хронологию. Главное
действие определяется проблемой клиента; постоянной универсальной кнопки нет.

### 4.5 Счета

Фильтры используют независимые состояния документа, расчёта и взыскания. Счёт
выпускается только из серверного preview. Произвольный ручной ввод итоговой суммы
запрещён. Credit/debit note видны рядом с исходным документом.

### 4.6 Корректировки

Разделяет:

- ожидают моего решения;
- ожидают второго утверждения;
- история скидок, кредита, списаний, reversal и refund.

Мастер: основание, серверный расчёт эффекта, preview долга и доступа, MFA,
approval. Создатель не может быть вторым утверждающим.

### 4.7 Тарифы

Показывает активную цену, запланированные версии, архив и preview влияния.
Создание проходит как `draft -> preview -> approval -> notification -> scheduled`.
Редактирование active-версии отсутствует.

### 4.8 Аудит

Неизменяемая хронология фильтруется по клиенту, операции, сотруднику, периоду и
результату. Технические детали показываются только при отдельном разрешении.
Исходная и обратная операции связаны визуально.

## 5. Адаптивность и производительность

- Базовые проверки: `1024x768`, `1366x768`, `1920x1080`, узкое окно desktop и
  масштаб Windows 125-200%.
- На 1024px сводки имеют не более двух колонок, вторичные поля таблиц скрываются.
- При 200% критические действия и суммы переходят в одну колонку без
  горизонтальной прокрутки.
- Touch-цели не меньше 44px, в сенсорной плотности 48px.
- Вкладки управляются стрелками, формы имеют последовательный Tab-порядок,
  focus-ring и корректный возврат фокуса.
- Escape закрывает только безопасные слои; финансовое подтверждение требует
  явной кнопки.
- Реестры используют серверную пагинацию, `keepPreviousData` и отмену устаревших
  запросов.
- Query keys имеют отдельные namespaces поколения API (`legacy`/`v2`), tenant или
  platform scope, actor и permission revision. `keepPreviousData` действует
  только внутри неизменного scope. При смене tenant, пользователя, permissions
  или feature flag запросы отменяются, а соответствующий финансовый кеш
  удаляется до монтирования следующего UI.
- Детали, PDF viewer и staff-вкладки загружаются отдельными lazy chunks.
- Не используются blur, внешние шрифты, canvas-графики и постоянные анимации.

## 6. Стратегия перехода

1. Согласовать этот low-fi прототип без изменения production UI.
2. Разделить целевые capabilities и принять API-схемы.
3. Добавить новый billing API рядом с legacy за feature flag.
4. Реализовать клиентский read-only обзор и реестр счетов с изолированным v2
   query namespace.
5. Реализовать заявление об оплате и защищённую upload-сессию.
6. Реализовать staff-очередь и карточку проверки.
7. До включения staff UI сервером отключить legacy write endpoints; dual-write и
   fallback мутаций не допускаются.
8. Добавить тарифы, корректировки и аудит.
9. Переключить чтение после сверки; удалить drawer только отдельным изменением.

## 7. Критерии согласования макета

- Владелец аптеки за 10 секунд называет статус, сумму, срок и следующий шаг.
- Сотрудник открывает следующую проверку без ввода tenant UUID.
- Нет экрана, где одновременно конкурируют две primary-кнопки.
- Ни один экран не обещает подтверждение денег до банковской сверки.
- Все P0/P1 состояния финансовой спецификации представлены отдельным UI-state.
- Макет остаётся читаемым на `1024x768`, touch и масштабе 200%.
