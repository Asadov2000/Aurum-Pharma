# Зашифрованная репетиция восстановления read-only Edge

Запуск: `pwsh -NoProfile -File scripts/smoke-edge-cold-read.ps1 -VerifyRestore`.
Нужны уже собранные backend и backup образы; скрипт не устанавливает зависимости.
Имена можно передать через `-BackendImage` и `-BackupImage`. Этот же запуск входит
в обязательный CI gate, в job `production-containers` после сборки образов.

Это тестовый инструмент, а не команда резервного копирования аптечного ПК.
Он работает только с синтетической БД `aurum_edge_read_benchmark_test` по адресу
`edge-benchmark-postgres` в уникальных внутренних Docker-сетях. Общая dev/demo БД
не подключается. Продажи, автономный вход и writer-права не включаются.

## Что проверяется

1. Установка и проверка подписанного снимка, обрыв установки до commit,
   перезапуск БД и read-only API — прежний сценарий cold smoke.
2. Consistent `pg_dump` и его SHA-256 создаются во временной памяти отдельного
   контейнера. Уже поставляемый Restic шифрует их; выполняется полное чтение
   repository через `check --read-data`.
3. На Windows/Linux-хост копируется только tar зашифрованного repository;
   SHA-256 сверяется до и после переноса. Передача использует native byte streams
   через `docker exec`: `docker cp` не видит tmpfs на проверенном Docker Desktop,
   а текстовый pipeline PowerShell может изменить бинарные данные.
   Случайный ключ репетиции хранится
   отдельным временным файлом и подключается read-only, не входит в архив
   и не выводится в логи. Его ACL/TPM-защита не являются предметом этой репетиции.
4. Исходные PostgreSQL, Redis, API и backup-контейнер останавливаются. Создаются
   новые PostgreSQL и recovery-контейнер в другой внутренней сети.
5. Восстановление с неверным ключом обязано отказать. В отдельной копии
   repository обнуляется один ciphertext data pack; полная проверка и попытка
   восстановления без кеша обязаны отказать. Их результат не передаётся в БД.
6. Из исправного repository восстанавливается точный snapshot ID, полученный
   после backup. До `pg_restore` проверяется SHA-256 dump. Подписанный снимок,
   его scope и ревизия проверяются read-only API, затем читаются четыре товара
   и пять партий, включая повторное чтение после перезапуска API.

Открытый dump, расшифрованный результат, cache и repository остаются в tmpfs
контейнеров. На выходе удаляются только ресурсы с метками и префиксом этого
запуска и его точные временные файлы. Ошибка проверки или очистки завершает
скрипт с отказом. Скрипт выводит длительность восстановления до первого
подтверждённого чтения; это время синтетической репетиции на одном хосте.

Отдельная Windows-проверка передачи на PowerShell 5.1 и PowerShell 7 прошла
с бинарным набором 262 144 байта, содержащим все значения 0–255: исходный
и возвращённый размер/SHA-256 совпали. Контейнер работал без сети, с read-only
rootfs, без capabilities; записанный файл принадлежал UID 10001 и имел mode 0600.
Linux проверяется полным сценарием в CI, а не выводится из Windows-результата.

## Чего результат не подтверждает

Не реализованы автоматическое расписание и хранение второй копии на отдельном
носителе, защищённое хранение/перенос ключа устройства, независимая защита от
отката, fencing старого writer и восстановление на запасном физическом ПК.
Repository может содержать старый корректно подписанный снимок: шифрование
само по себе не подтверждает его актуальность.

SHA-256 и точный snapshot ID задаются контроллером этой же репетиции; это не
production trust-anchor. Контроллер не получает их из неизвестного внешнего
архива. Приёмка tenant/branch/node, версии схемы и writer epoch **до изменения
рабочей БД** требует отдельного production restore-процесса. Здесь target БД
одноразовая; после восстановления её read-only API проверяет подписанный scope.
Цели RPO/RTO из ADR 0043, месяц автономной работы и устойчивость к физическому
отключению питания остаются отдельными условиями приёмки.
