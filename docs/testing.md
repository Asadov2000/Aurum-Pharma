# Воспроизводимые тесты и быстрый локальный цикл

Полный GitHub `CI gate` обязателен для каждого PR. Локально используйте
`scripts/verify-change.ps1 -Mode Quick` во время разработки,
`-Mode Auto -PlanOnly` для плана и `-Mode Auto` перед commit. Не запускайте
несколько тяжёлых сборок и полных наборов одновременно на Docker Desktop:
конкуренция за ресурсы и повторные попытки могут увеличить общее время.

## Backend: отдельная БД и Redis

`TEST_DATABASE_URL_*` должны указывать только на подготовленную тестовую БД.
Общую dev-БД нельзя очищать или пересоздавать для проверок. Имеющиеся
SQL/RLS-тесты используют реальные роли и сохраняют свои проверки изоляции.

Тесты намеренно не наследуют `REDIS_URL` приложения. Они берут
`TEST_REDIS_URL`, а внутри Docker по умолчанию используют
`redis://redis-test:6379/0`. Выделенный сервис включается явно:

```powershell
docker compose up -d redis-test
```

Для pytest на хосте задайте адрес опубликованного тестового порта:

```powershell
$env:TEST_REDIS_URL = 'redis://localhost:16379/0'
```

Сервис не использует dev-том и не сохраняет Redis-данные на диск. В CI
`TEST_REDIS_URL` явно указывает на Redis текущего job. Ошибка подключения или
очистки должна останавливать тест, а не оставлять незаметно старое состояние.
Fixtures очищают тестовые auth-кэши и ограничения попыток, восстанавливают
изменённые настройки Celery даже при исключении. Локально pytest остаётся
последовательным: несколько процессов не должны использовать общие сервисы.

## Две изолированные группы backend в CI

Каждая группа выполняется на отдельном GitHub runner со своими PostgreSQL,
Redis и MinIO. Изолируется весь PostgreSQL-сервер, поскольку проверки ролей
меняют состояние кластера. Bootstrap, миграции, SQL/RLS, проверки Edge и
статический анализ сохраняются в каждой группе. `fail-fast: false` позволяет
получить результаты обеих групп даже при ошибке одной.

Плагин `tests.sharding` подключается явно только в CI-команде. Он собирает
полный набор, распределяет целые файлы по числу тестов и сохраняет исходный
порядок внутри каждой группы. Список файлов вручную не поддерживается:
новые тесты автоматически входят в распределение. Отбор через `-k`, `-m`
и другие сокращающие набор параметры в этом режиме запрещён.
Сценарии с генерируемыми при импорте параметрами должны иметь постоянный
`pytest.param(..., id="...")`: случайные UUID в имени теста делают коллекции
разных процессов несопоставимыми. Сами тестовые данные могут оставаться случайными.

Каждая группа публикует полный список обнаруженных тестов, выбранные тесты
и JUnit-отчёт. Помимо успешного статуса всех jobs, `CI gate` проверяет:

- наличие всех групп и одинаковый исходный набор;
- отсутствие пропусков и пересечений между группами;
- соответствие количества выполненных тестов выбранному набору;
- отсутствие ошибок и падений в отчётах.

Отчёты имеют отдельное имя для каждой группы. При повторе упавшей job её
артефакт заменяется; успешная группа того же CI run сохраняет свой отчёт.
Пропущенная, отменённая или упавшая job не может дать зелёный gate.

Для сравнения одного и двух процессов запустите workflow `CI` вручную на
одном commit с `backend_shards=1`, затем с `backend_shards=2`. Сравнивайте
время самого длинного backend job и отдельно шаги Pytest: подготовка сервисов
и проверки миграций входят в общее время и повторяются в каждой группе.
Параллельный режим расходует больше runner-минут. Локальную скорость или
скорость всего CI нельзя выводить только из сокращения времени Pytest.

## Frontend и браузер

Компоненты продолжают тестироваться в `jsdom`. Файлы с чистой логикой без DOM
помечаются `@vitest-environment node`; число проверок и изоляция файлов сохраняются.
Общие настройки `forks` и последовательного выполнения остаются прежними.

Локальный замер 11 выбранных файлов / 54 тестов: два запуска до изменения
15,536 и 14,858 секунды; после — 7,448 и 6,900 секунды полного времени команды.
Среднее уменьшилось на 52,8% только для этой группы. Этот результат нельзя
переносить на весь набор или CI без отдельного измерения.

Для браузера используйте `pnpm e2e:isolated`; подготовка данных проверяет
принадлежность PostgreSQL/Redis одноразовому Compose-проекту. Подробности —
в [e2e.md](e2e.md). Повторы не исправляют дефекты: в CI тест, прошедший только
при повторе, остаётся блокирующим.

Границы фоновых задач проверяются отдельно:
`scripts/test-worker-broker-boundaries.ps1` создаёт собственные Redis и сети,
проверяет ACL всех ролей, настоящую доставку Celery и восстановление после потери
процесса. `scripts/test-production-internal-tls.ps1` запускает тот же Redis startup
с TLS. Domain pytest использует отдельный `TEST_REDIS_URL`; настройки шести Celery
apps перенаправляются fixture без ослабления runtime-проверки broker identity.
В E2E `otp-mail-delivery.spec.ts` ждёт письмо от настоящего beat/mailer через Mailpit
и входит с полученным кодом. Коды, письма и токены исключены из трассировок теста.

При следующих оптимизациях сравнивайте одинаковые наборы на одинаковой машине,
отдельно учитывайте сборку, подготовку, выполнение и повторы. Сначала проверяйте
воспроизводимость; затем меняйте параллельность или время жизни общих fixtures.

## Полная запись каталога

Контрольные результаты и ограничения измерения:
[`catalog-import-benchmark-2026-09-08.md`](catalog-import-benchmark-2026-09-08.md).

`scripts/benchmark-catalog-write.ps1` проверяет реальный путь Redis → Celery →
MinIO → PostgreSQL. Каждый запуск создаёт отдельные контейнеры, внутреннюю сеть,
БД `aurum_catalog_benchmark_test`, новые секреты и синтетические данные. Существующие
Compose-проекты, `.env`, dev/demo БД и хранилище не используются. Backend-образ
должен быть уже собран; исходники приложения подключаются только для чтения.

```powershell
.\scripts\benchmark-catalog-write.ps1 -Rows 15000 -Format csv
.\scripts\benchmark-catalog-write.ps1 -Rows 50000 -Format xlsx
```

По умолчанию последовательно проверяются создание, пропуск и обновление тех же
товаров с теми же штрихкодами. Дополнительный `-Cases create,skip,update,create_copy`
создаёт копии с новыми штрихкодами; конфликт существующего кода проверяется pytest.

Каждая фаза измеряется от отправки сообщения до наблюдения зафиксированного
результата. Подготовка файла, загрузка и сверка БД измеряются отдельно. В JSON
выводятся количества, время, статус, идентификатор образа, отпечаток исходников
и пик памяти всего контейнера worker. Строки файла и секреты не выводятся.
Для повторяемости выполняйте отдельные последовательные запуски без других
нагрузочных тестов на том же Docker Engine; сохраняйте каждый результат.

Ограничения worker соответствуют production: 1 CPU, 768 MiB, concurrency 1,
тайм-ауты 120/150 секунд. Ошибка или тайм-аут не становятся успешным результатом
даже при подтверждённом полном откате. Неуспешная очистка стенда также завершает
команду ошибкой. Состояние `importing` после hard timeout может сохраняться до
штатного восстановления через API после deadline; benchmark его не сокращает.

CI запускает 300 строк как функциональную проверку всего пути. Этот небольшой
сценарий не заменяет отдельные замеры 15 000 и 50 000 строк или проверку staging.
Семантика пакетов и границы гарантий описаны в
[ADR-0037](adr/0037-batched-catalog-import.md).
