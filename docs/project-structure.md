# Структура проекта и вход для разработчика

Этот документ — карта ответственности папок. Правила разработки находятся в
[AGENTS.md](../AGENTS.md), текущее поведение — в коде и тестах, архитектурные
решения — в [ADR](adr/README.md). Последовательность будущих работ:
[implementation-roadmap.md](implementation-roadmap.md).

## 1. Принцип организации

Один репозиторий, общий backend и общий рабочий frontend. Публичный сайт
собирается отдельно; Windows-host добавляет только интеграции ОС и оборудования.
Cloud и Edge — профили существующего backend, не две копии бизнес-логики.
Папки создаются вместе с первой реализацией и тестами, а не ради пустого каркаса.

Текущие `frontend/` и `backend/` не переносим в `apps/` и не создаём абстрактный
`core/` или общий пакет компонентов без конкретного повторного использования.
Это сохраняет историю, пути тестов, Docker-сборки и привычный вход в проект.

│  │  ├─ downloads/         способы установки и честный статус выпусков
│  │  └─ assets/            публичные локальные стили и изображения
│  ├─ scripts/              build / serve / test средствами Node
│  ├─ tests/                тесты публичной сборки и локальной раздачи
│  ├─ package.json          команды сайта, без новых зависимостей
│  └─ dist/                 результат сборки, не отслеживается Git

`website/` добавляется первым блоком нового плана. Обозначение «новый» не
означает, что сайт опубликован на домене. Проверенный выпуск определяется PR,
CI и результатом развёртывания.

Windows host уже появился в `desktop/`. Оставшиеся планируемые пути:

| Путь | Когда появляется | Ответственность |
|---|---|---|
| `desktop/` — упаковка и installer-тесты | На этапе установщика | Точные подпапки выбираются под согласованный формат installer; без новой копии POS |
| `infra/` — Cloud/Edge release-конфигурации | По мере готовности deployment | Дополняют существующие конфигурации, не копируют dev-секреты |
| `scripts/` — сборка и выпуск клиента | На этапе установщика | Сборка, подпись и проверка артефактов по общим правилам CI |

План Windows уже описан в
[desktop-host-implementation.md](desktop-host-implementation.md), контракт — в
[desktop-bridge.md](desktop-bridge.md). Этот документ не заменяет blueprint и не
вводит новый формат упаковки без его проверки.

## 3. Границы компонентов

- **Website:** публичный текст, локальные assets и ссылка на приложение из
  конфигурации. Нет формы авторизации, API-клиента аптеки, cookies сессии,
  токенов, данных аптек, записи обращений или сторонней аналитики в первом
  блоке. Сайт не импортирует приватный код `frontend/src`.
- **Frontend:** интерфейс и доступность действий, но не окончательное решение
  о правах. Сотрудник может иметь несколько ролей; сервер проверяет действие
  в конкретной точке. По названию роли UI не делится на отдельные приложения.
- **Backend:** `repository.py` работает с БД, `service.py` с бизнес-правилами,
  `router.py` с HTTP, `schemas.py` с внешними данными. Новую функцию размещать
  в ответственном домене. Sync принадлежит существующему
  `backend/app/domains/sync/`, а не Windows-host.
- **Desktop:** вызывает только известные команды bridge; не хранит независимый
  журнал продаж и не реализует собственные правила денег, остатков или ролей.
  Доверенный локальный UI и внешняя публичная страница — разные границы.
- **Infra/scripts:** конфигурация, установка, эксплуатация и проверки;
  бизнес-правила туда не переносятся.

## 4. Окружения, адреса и данные

| Окружение | Адреса / хранение | Правило |
|---|---|---|
| Текущий dev/demo | Приложение `localhost:5173`, сайт `127.0.0.1:4174` | Вход по умолчанию `http://localhost:5173/login`; разные процессы; сайт не меняет существующий launcher приложения |
| Будущий production | Основной домен → website; `app` → frontend и API | Production build сайта требует явный `APP_URL`; локальный адрес не становится production default |
| Будущий ПК аптеки | Локальная служба и БД, общий узел точки | Подключение клиента к API, не к PostgreSQL; доступ к Cloud исходящий |

Исходники, установленная программа и рабочие данные — три разных вещи.
Клиенту передаётся подписанный пакет, не Git-репозиторий. Служебные данные
Windows, журналы и БД должны находиться вне каталога установки, с разными ACL;
пользовательские настройки — отдельно от финансовых данных. Точные пути и
системные учётные записи утверждаются при проектировании установщика.

В Git запрещены БД аптек, выгрузки клиентов, пароли, ключи подписи, generated
installer, `node_modules/`, `dist/`, отчёты тестов и локальные `.env`.
`.codex/`, `.tmp/` и другие временные рабочие папки не являются архитектурными
модулями. Существующие данные общей dev-БД нельзя очищать ради новой структуры.

## 5. Первые шаги нового разработчика

1. Прочитать [AGENTS.md](../AGENTS.md), затем
   [ai-context-index.md](ai-context-index.md) и относящуюся к задаче часть
   [development-state.md](development-state.md).
2. Проверить `git status --short`, текущую ветку и последний commit. Не принимать
   исторические названия веток из документов за состояние checkout.
3. Найти домен через `rg`, прочитать его интерфейс, важные тесты и релевантный ADR.
   Точные версии брать из lock-файлов и Dockerfiles, не из текстовой карты.
4. Использовать команды запуска из [README](../README.md). Для существующей
   общей среды выбирать launcher с `SkipSeed`; отдельную новую тестовую среду
   готовить по [testing.md](testing.md), не очищая dev/demo.
5. Создать `codex/<задача>`, записать краткие критерии приёмки и получить план:

   ```powershell
   .\scripts\verify-change.ps1 -Mode Auto -PlanOnly
   ```

6. Менять только ответственный компонент; сохранять backend-инварианты и
   роли, добавлять необходимые сценарии сбоя. Проверки и CI:
   [testing.md](testing.md), [e2e.md](e2e.md), раздел 6 `AGENTS.md`.
7. Точные файлы добавить в commit, создать PR, дождаться обязательного CI gate.
   Новый разработчик должен суметь запустить затронутую часть по её инструкции,
   понять ограничения и найти подтверждение результата в PR.

## 6. Как не размножать документацию

| Вопрос | Единственный основной источник |
|---|---|
| Постоянные правила работы | `AGENTS.md` |
| Короткий запуск | `README.md` |
| Где находится код | Этот документ |
| В каком порядке развиваем продукт | `implementation-roadmap.md` |
| Почему выбрана архитектура | Соответствующий `docs/adr/*.md` |
| Что сейчас реализовано и проверено | Код, тесты, `development-state.md`, результат конкретного PR |
| Как развёртывать и восстанавливать | `docs/runbooks/` |
| Какие внешние условия не закрыты | `docs/compliance/`, `known-issues.md` |

В новых документах ставить ссылку на основной источник вместо копирования
длинной инструкции. ADR не переименовывать задним числом. Изменение API
сопровождать схемой и тестом; инструкцию запуска — проверяемой командой;
заявление о готовности — конкретным результатом проверки.
