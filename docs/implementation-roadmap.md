# План развития Aurum Pharma

Статус: последовательность работ и критерии приёмки, а не отчёт о готовности.
Направление согласовано 2026-09-12; порядок работ обновлён 2026-09-23 после
PR №192 (`main 514fe26`). Текущий результат проверять по коду, CI и
[development-state.md](development-state.md).

## 1. Цель и исходное состояние

Развивать одну платформу с общими правилами продаж, складского учёта и доступа:
публичный сайт, рабочее веб-приложение и устанавливаемый Windows-клиент.
Пользователь получает функции по совокупности ролей и разрешённых точек.
«Касса», «Склад» и «Управление» — представления задач, а не отдельные продукты
и не жёсткие типы аккаунтов.

Сейчас разработка и demo работают на ПК владельца проекта. Облачного рабочего
окружения, распространяемого Windows-приложения и готового установщика нет.
Production-конфигурация и отдельные механизмы Edge существуют в репозитории;
это не означает, что они уже развёрнуты или дают автономную кассу.

Уже реализованы касса, роли, каталог и его Excel/CSV-импорт, поставщики,
сохраняемые черновики приходов, создание товара из прихода, отчёты, аудит,
защита от части сетевых сбоев и механизмы резервного копирования. Их не нужно
переписывать заново. Импорт **накладных** Excel/CSV уже создаёт проверяемый
черновик прихода; шаблоны поставщиков и распознавание фото/PDF остаются
отдельными этапами.

Текущий блок — проверка локального Edge: индексированные данные уже доступны
только для чтения. Автономные продажи и готовый установщик ещё не выпущены.

### Ближайший порядок работ

В [поштучной продаже](unit-sales.md) реализован отдельный физический путь v3:
выбор штук, блистеров и пачек, списание из принятого физического остатка,
атомарное наличное проведение, исторический чек и проверка результата после
потери ответа. Для таких продаж подключены расчёт и подтверждение наличного
возврата по исходной цене и скидке. Новая связанная операция объединяет
карантин товара, выплату и возвратный чек; повтор не создаёт вторую выплату.
Если историческая сумма выбранного возврата равна нулю, отдельный приём
сохраняет товар в карантине без выплаты, новой продажи и номера чека.
Для него не нужна открытая кассовая смена; результат восстанавливается
по сохранённой операции без повторного приёма товара.

В разделе «Партии» отдельное представление физических партий показывает остаток
закрытых и вскрытых упаковок выбранной точки без закупочной стоимости.
Сотрудник с `batches.view` и `batches.update` может заблокировать всю партию
или снять блокировку через существующий механизм 0180. Количество, деньги
и завершённые продажи при этом не меняются; устаревшая ревизия требует
повторного подтверждения по обновлённым данным. Общая БД и миграции при
разработке этого интерфейса не изменяются.

В разделе «Партии → Возвраты покупателей» отдельная очередь показывает
подтверждённые физические возвраты с выплатой и без неё. Количество отображается
в базовых единицах исходной упаковки; части одной партии объединяются в строку.
Просмотр использует разрешение `customer_returns.view`, не требует права
оформлять возврат и не раскрывает себестоимость. Окончательное действие по всему
объёму строки оформляется с отдельным `customer_returns.resolve`: фактическая
утилизация, передача поставщику или уполномоченной организации. Журнал `0198`
сохраняет неизменяемое решение, исключает строку из ожидающей очереди и позволяет
читать историю и восстановить ту же операцию после потери ответа. Решение не
изменяет деньги, доступные остатки и исходные чеки; частичные решения запрещены.

Для смешанной корзины добавлена внутренняя проверка обоих видов остатков,
рецептов и подтверждения суммы; она не проводит продажу и не резервирует товар.
Отдельные неизменяемые документы v4 сохраняют оба вида строк и общий чек,
с проверкой сумм и исходных количеств. Внутренний наличный координатор и
ограничения БД 0188 связывают оба списания, один платёж и исторический чек в
одной транзакции; повтор не списывает товар заново, ошибка откатывает всю операцию.
Отдельный HTTP API смешанной наличной оплаты сохраняет подтверждение, завершает
продажу и восстанавливает исходный результат без повторного списания. Проверяются
права действующего кассира и филиала; чтение работает после закрытия смены и в
режиме организации только для чтения. Касса подключена: обычные пачки и физические
позиции оплачиваются вместе наличными, с проверкой рецепта до начала операции
и отдельной устойчивой очередью восстановления. Чисто физическая корзина использует
ту же проверку актуальных условий отпуска и сохранение общего рецепта до начала
оплаты; восстановление начатой операции не записывает рецепт повторно. Тестовый режим смешанного
проведения явно запрещён до реализации симуляции обоих складов. Чистый физический
путь также отклоняет учебную оплату на сервере и в БД (`0197`); интерфейс обоих
путей разрешает новую оплату только при явном `is_test=false`. Сохранённая история
не меняется, чтение для восстановления доступно. Учебная симуляция этим не реализована.
Детали и печать поддерживают чтение v4: позиции выводятся один раз в исходном
порядке. Смешанный возврат использует отдельную форму и API; общий серверный
расчёт прежнего возврата по-прежнему отклоняет смешанный чек.
Для смешанного возврата используется чистый расчёт из исходного чека v4:
отдельные доверенные курсоры дробных пачек и физических единиц, сохранённые
скидки, точное распределение копеек и общий порядок строк. Он не выполняет
выплату или приём товара; эти действия выполняют отдельные координаторы ниже.
Внутренний журнал смешанного возврата сохраняет подготовительный приём обоих
видов товара одной транзакцией: доверенные курсоры, защита повторов, исходные
цены и физические части себестоимости, RLS и неизменяемая история в БД.
Внутренний наличный координатор 0190 связывает этот журнал, один платёж и новый
неизменяемый возвратный чек v4 одной транзакцией. Проверяются исходная продажа,
права кассира, его открытая смена на исходной кассе, причины возврата и доверенные
курсоры; повторы возвращают сохранённый результат без повторной выплаты.
Доступный остаток не увеличивается. Отдельный HTTP API смешанного наличного
возврата предоставляет доступные количества, исторический расчёт, проведение
и чтение сохранённого результата. Обязательные сумма и ревизия защищают от
устаревшего подтверждения; чтение после закрытия смены или в режиме только
чтения не повторяет выплату. Отдельная форма смешанного возврата в истории продаж
различает дробные пачки и целые физические форматы, требует проверенный расчёт
и свою открытую смену на исходной кассе. При потере ответа сохраняется исходный
UUID и точный запрос; открытие формы только проверяет результат. Просмотр и печать
нового чека используют сохранённые количества, названия, цены и распределённые суммы.
Смешанный приём с нулевой суммой использует отдельный API и неизменяемую запись
0191, связанную с журналом 0189. Исторический расчёт должен дать ровно 0,00 TJS;
проверяются актуальная причина и ревизия. Смена не требуется: нет платежа,
новой продажи, чека выплаты или увеличения доступного остатка. Форма сохраняет
этот запрос под тем же барьером незавершённой операции, что и денежный возврат;
потеря ответа восстанавливается чтением, повтор сохраняет исходный UUID.
Карантин представлен журналом 0189, как отдельный физический журнал в v3:
старый `customer_return_quarantine_item` требует прежнюю `SaleItem` и не покрывает
физические строки. Буквальное описание этой таблицы в ADR 0028 требует отдельной
синхронизации; обработка смешанного карантина старым механизмом disposition
ещё не реализована. Текущая стоимость обычной партии не подменяет отсутствующий
исторический снимок её себестоимости: `physical_cost_amount` содержит только
известную физическую часть, а не полную себестоимость или прибыль.
Смешанный карантин доступен отдельной очередью в разделе возвратов покупателей:
подтверждённые денежные и нулевые приёмы показывают оба вида товара. Обычные
пачки сохраняют дробное количество, физические части объединяются по исходной
строке и партии и показываются в исторических базовых единицах. Просмотр
использует `customer_returns.view` с проверкой точки внутри проекции БД 0192;
неподтверждённый внутренний журнал не попадает в очередь. Поиск, фильтр по точке,
страницы и мобильные карточки не раскрывают себестоимость и не меняют остатки.
ADR 0028 запрещает возврат такого товара в продажу; окончательные решения
оформляются отдельным журналом и интерфейсом ниже.
Подготовлен чистый контракт окончательного решения по [ADR 0051](adr/0051-mixed-quarantine-disposition.md):
цель включает приёмку, исходную строку и партию, а количество берётся целиком
из доверенного исторического источника. Канонический хеш отделён от ключа
повтора. Сам чистый контракт не проверяет полномочия и не записывает действие.
Внутренний обработчик 0193 отдельно проверяет `customer_returns.resolve`, выводит
подтверждённый источник и полный объём в БД, сохраняет неизменяемое решение и
возвращает исходного автора при повторе. Склад, выплаты и продажи не меняются.
Проекция 0192 исключает решённые цели, сохраняя контракт ожидающих `pending`;
отдельная функция истории проверяет `customer_returns.view`. HTTP
`/customer-returns/mixed/dispositions` подключает запись с отдельным `resolve`
и просмотр истории с `view`, страницами и фильтром по точке. Повтор POST с тем же
UUID и содержимым возвращает прежнее решение, не меняя склад или выплаты.
Интерфейс подключает подтверждение всего объёма и историю решений. Миграция 0194
добавляет GET `/customer-returns/mixed/dispositions/operations/{decision_operation_id}`
с обязательной точкой: текущий `resolve` проверяется до поиска, без `view` или
`pos.refund`; чтение работает при readonly/archived и не повторяет действие.
Перед отправкой сохраняются точный запрос с UUID и минимальный снимок цели с
историческим количеством/единицей. Одна запись и Web Lock на tenant/user
блокируют параллельные новые решения всех точек. Открытие только читает статус,
повтор явный с тем же UUID; очистка требует свежего совпадающего подтверждения.
Повреждение и конфликт оставляют барьер и требуют разбора с администратором,
без отказа от операции или сброса. Вход через «Партии» сохраняет `batches.view`;
при оставшемся `resolve` без `view` доступно лишь восстановление сохранённого
решения, без очереди и истории. История отображается по текущему часовому поясу
аптеки из nullable metadata вне неизменяемого результата.
Сводка продаж (общая, дневная и XLSX) и Z-отчёт учитывают скидки из сохранённых
физических и смешанных чеков, включая собственные снимки денежных возвратов.
Прежние документы используют `SaleItem`; источники не суммируются между собой.
Валовые суммы, скидки и фактические возвраты согласуются с оплатами; версия кеша
Z-выгрузок обновлена. Отчёты не меняют исходные операции и не раскрывают закупочные
цены. Рейтинг товаров подключает обычные, физические и смешанные продажи,
денежные возвраты и подтверждённые нулевые приёмы. Выручка агрегируется по товару,
обычные упаковки и физические единицы показываются отдельно; сортировка по
количеству требует выбранной единицы. Миграция 0195 выдаёт только агрегаты
с проверкой прав отчётов по точкам, без расширения доступа к сырым журналам.
«Остатки на дату» объединяют обычные партии и принятые физические партии v2
в API, экране и Excel. Остатки восстанавливаются из движений до конца местного
дня; обычные упаковки и базовые единицы сохраняют раздельные итоги. Закупочные
данные обоих видов партий требуют `batches.view_costs` в каждой точке.
При неполной стоимости полный денежный итог отсутствует, известная часть
показывается отдельно. Карантин не увеличивает обычный остаток.
Миграция 0196 добавляет только защищённое чтение. Прибыль ещё требует
подключения; неизвестная историческая себестоимость не подменяется текущей.
Отдельными этапами остаются электронная оплата, тестовый режим физических и смешанных продаж,
связанные документы поставщика/регулятора, оставшаяся общая отчётность
и автономная синхронизация Edge V3. Готовность кода в рабочей ветке
требует обязательного CI, слияния и обновления миграций перед выпуском.
Миграции 0194–0197 на общей dev-БД в ходе разработки не применяются;
модуль поштучных продаж целиком ещё не завершён.

Ниже описаны подготовительные компоненты v2. Их ограничения финансового
завершения сохраняются; физическое проведение v3 использует отдельный путь.

По запросу владельца добавлен отдельный этап [поштучной продажи](unit-sales.md).
Явные настройки упаковки и цены единицы подготовлены без изменения действующих
остатков. Добавлены расчёт выдачи, сохраняемый складской журнал и атомарные
операции с закрытыми и вскрытыми упаковками. Приёмка по явному запросу фиксирует
подготовительный снимок состава упаковки и переносит его в партию; действующие
остатки по-прежнему учитываются прежним журналом. Подготовлен точный расчёт
себестоимости и частичных возвратов по исходной сумме без потери копеек.
Подготовленный склад сохраняет исходную стоимость упаковки, физические
диапазоны и денежные части отпуска в одной транзакции; прежние партии не
переоцениваются. Связь с реальной продажей и оплатой ещё требует реализации.
Сохраняемый внутренний снимок строки связывает розничную цену, скидку и итог
с подготовленным складским списанием. Он ещё не связан с реальной `Sale`,
оплатой или кассовой сменой; скрытых черновиков действующей кассы не создаёт.
Отдельные внутренние контракты v2 различают упаковки и единицы, проверяют
суммы документа и строят строки чека и расчёт возврата из исходного снимка.
Они ещё не подключены к действующим API или событиям; совместимость v1 сохраняется.
Внутренний путь приёмки всего документа в журнал единиц создаёт единственный
остаток и закрепляет его источник в накладной. Повторы, откаты и область прав
защищены; обычная приёмка сохраняет прежний склад. Новый путь ещё не подключён
к HTTP до готовности последующих операций и отчётов.
Внутренний отпуск принятого товара выбирает только подтверждённые источники
приёмки. Подготовительные остатки не подменяют реальный товар; политика источника
сохранена в команде, а каждый источник и полномочия проверяются сервером и БД.
Внутренний отчёт по журналу единиц восстанавливает остатки на дату по истории,
разделяет закрытые упаковки и единицы во вскрытых упаковках, а также источники
приёмки и подготовки. Стоимость считается из исходных сумм и доступна только
при отдельном праве. Отчёт пока не подключён к экрану и не заменяет отчёты
по обычным партиям; кассовые показатели поштучных продаж ещё не реализованы.
Внутренний возврат фиксирует подготовительный карантин по исходным физическим
частям отпуска, без возврата товара в продажу. Количество, деньги, повторы и
полнота защищены в одной транзакции; финансовый возврат и публичный вызов
ещё не подключены. Закупочные сведения новых unit-записей маскируются в аудите.
Настоящий черновик продажи поддерживает отдельные внутренние намерения
поштучной покупки. Их правка не списывает товар; при наличии намерений база
блокирует прежнюю оплату и завершение. Публичная корзина, общий итог v2 и
атомарное завершение с оплатой ещё требуют реализации.
Внутренняя единая оценка корзины объединяет прежние упаковочные строки и
поштучные намерения, проверяет денежные суммы и актуальную конфигурацию.
Прежние цены не переоцениваются; оценка ещё не является продажей или оплатой.
Внутреннее подтверждение наличной суммы повторяет расчёт под блокировкой,
отклоняет изменившуюся корзину и недостаточную оплату, вычисляет сдачу.
Оно не сохраняет платёж, не списывает товар и не закрепляет команду повтора.
Неизменяемая команда подтверждения наличных теперь сохраняется отдельно:
повтор возвращает исходный снимок, изменение параметров команды отклоняется.
Она сохраняет историю и не является оплатой; при проведении требуется новый
контроль актуальности. Запрет финансового завершения `0170` сохранён.
Подготовлен отдельный адаптер целостности события продажи v2: разные виды
количества, контекст операции, контрольные суммы и отпечаток повтора.
Он не публикует события и не подключён к действующему обработчику v1.
Формат сохранения и восстановления v2 сверяется с независимой доверенной
опорой; постоянное хранилище и рабочее применение событий пока не введены.
Дальнейшее расширение поддерживаемых операций требует совместимой работы
физического склада, кассы, возвратов, отчётов и событий Edge. Каждый новый
сценарий включается после проверки всей цепочки; подготовка карточки товара
сама по себе его не разрешает.

Первые этапы [быстрых действий](context-actions.md) добавлены для каталога, партий,
приёмки, сотрудников, чеков и строк текущего чека кассы: правой кнопкой и через ⋯,
с личным порядком и видимостью
команд. В чеках доступны только открытие карточки и копирование номера; возврат и
печать сохраняют прежние проверки в карточке. Локальный Edge сохраняет только
просмотр и копирование. В кассе изменение количества и удаление строки доступны
только редактируемому черновику; оплата, завершение продажи, блокировки и
разделение товара по партиям сохраняют прежние правила. Основной приоритет
автономности и безопасной синхронизации остаётся прежним.

Короткая помощь встроена в кассу, приёмку, выплаты сотрудникам, сверку,
поставщиков и партии, включая возвраты покупателей.
Подсказки объясняют следующий шаг и подсвечивают элемент без выполнения операции.
Для сверки отдельно объясняются подтверждение денег и завершение чека;
для склада — доступные остатки и обработка возвращённого товара.
Помощь также доступна в профиле, «Моя работа», безопасности и уведомлениях:
суммы не раскрываются автоматически, действия требуют решения пользователя.
Следующий приоритет — автономный Edge; дополнительные подсказки добавляются
по результатам пользовательского тестирования.

Завершены безопасный выход ([ADR-0049](adr/0049-durable-browser-logout.md)),
[личный профиль](personal-profile.md), [свои смены](my-work-shifts.md),
[безопасность](account-security-page.md), [уведомления](notifications-page.md),
[ручные выплаты наличными](manual-staff-pay.md), [сотрудники](employees-page.md)
и [проверка изменений ролей](roles-builder-page.md) по согласованным макетам.
Автоматического начисления зарплаты нет; личные сведения и управляющие действия
разделены существующими разрешениями.

Следующий приоритет — локальный Edge. Добавлена явная
[TPM-проверка Windows preflight](windows-tpm-readiness.md), использующая готовый
read-only probe. Далее нужны доверенный enrollment, защищённое состояние и
календарное время, аппаратная проверка Windows-службы и recovery до включения
автономного входа. Затем — запись операций и безопасная синхронизация,
установщик и приёмка длительной автономности по этапам ниже.
Потеря сети сама по себе не означает выход;
полный автономный runtime остаётся отдельным направлением.

Переход от подписок к независимому доступу выполнен в PR №222 согласно
[ADR-0047](adr/0047-independent-tenant-access.md): запуск без trial, ограничения
Aurum, закрытые старые команды начисления, сохранённые исторические расчёты
и tenant-изоляция прошли обязательный CI gate.
Контракт offline lease v1 теперь включает подписанную версию политики доступа,
сужение команд при выпуске и проверку независимого защищённого состояния при
входе и каждой операции. Эти алгоритмы не включают автономную кассу: следующим
шагом остаются production enrollment и аппаратные адаптеры защищённого
состояния/времени. Подписанный пакет уже можно импортировать в неактивную
[SQL-очередь](offline-policy-inbox-v1.md), но автоматическая доставка и защищённое
принятие не подключены. Учёт наличных оплат клиентов Aurum реализован отдельным
финансовым документом с независимым подтверждением и авансом по
[ADR-0048](adr/0048-cash-settlements-with-aurum.md). Выпуск наличных возвратов,
юридических реквизитов и необходимых фискальных документов отложен до реальной
потребности в коммерческом учёте. Клиентское меню и главная больше не показывают
расчёты с Aurum; административный учёт и исторические документы сохранены.
Приоритет следующих этапов — автономная работа и безопасная синхронизация.


1. Предварительная проверка подписанного снимка и индексированные запросы
   реализованы. После обновления статистики каталога до активации снимка
   повторный изолированный замер на 100 000 товарах и 250 000 партиях дал
   p95 13,1 мс и первый готовый запрос 35,9 мс. Прежние цифры и методика — в
   [предыдущем замере](edge-full-snapshot-benchmark-2026-09-23.md), новые
   результаты и границы — в [протоколе](edge-windows-readiness-2026-09-24.md).
   Нагрузочные данные создавать только в изолированной БД.
2. На целевом Windows-ПК повторить холодный замер вместе с PostgreSQL, worker
   и клиентом. Проверить отключение интернета, перезапуск служб и ПК,
   прерванную установку снимка и восстановление резервной копии на другом
   устройстве. Зафиксировать время восстановления и полноту данных. Изолированный
   process/health smoke и перенос синтетического read-only снимка между
   изолированными контейнерами на одном Windows-хосте уже пройдены, но локальные
   службы, offline-вход и защищённый Edge backup/restore на другом физическом ПК
   остаются условиями реальной Windows-приёмки.
   Зашифрованная синтетическая репетиция через Restic также пройдена:
   точный snapshot ID, отказ при неверном ключе и повреждённой копии,
   подписанные чтения после восстановления и перезапуска. Она включена в CI;
   [границы репетиции](edge-encrypted-recovery-drill.md) не заменяют TPM,
   расписание backup и проверку запасного физического ПК.
3. Реализовать автономный вход и ограниченные по сроку разрешения, затем
   локальную запись продаж, смен и возвратов с безопасной синхронизацией.
   Разрабатывать в тестовом контуре; реальные продажи включать только после
   выполнения условий этапа 7.
4. Завершить установщик, службы, подписанные обновления, принтер и сканер;
   проверить установку с сайта и флешки без загрузки компонентов из интернета.
5. Пройти длительные сценарии автономности до 30 дней, сверку после подключения,
   несколько касс и пилотный допуск. Это целевая приёмка, не текущая возможность.

Cloud staging и импорт накладных остаются отдельными направлениями. Отсутствие
сервера не блокирует локальные тесты, но реальный пилот требует staging,
проверенных резервных копий и внешних платёжных/фискальных интеграций.

### Windows и оборудование

- Основная целевая конфигурация — Windows 11 x64. Windows 10 рассматривается
  как переходный вариант только для поддерживаемых редакций и после отдельной
  проверки всей поставки; возможность сборки не означает поддержку продукта.
- Windows 7/8/8.1 в текущий выпуск не включаются. Для таких аптек сначала
  оценить обновление ОС или замену ПК; отдельную устаревшую сборку не создавать.
- Перед окончательными системными требованиями обследовать 5–10 пилотных аптек:
  ОС, процессор, память, диск, принтер, сканер, LAN и перебои питания.
  Профиль ADR-0043 — исходная нагрузочная цель, а не измеренный минимум.
- Для основного ПК предусмотреть SSD, источник бесперебойного питания,
  отключение автоматического сна и резервную копию на другом носителе.
  Отсутствие интернета и отказ основного ПК — разные сценарии восстановления.

## 2. Где будет работать каждая часть

| Часть | Целевое расположение | Состояние и граница |
|---|---|---|
| Публичный сайт | Основной домен владельца проекта | Отдельная статическая сборка `website/`; домен и публикация ещё настраиваются |
| Рабочее приложение | Поддомен `app` того же проекта | Существующий `frontend/`, API через тот же origin; единый вход и действующие роли |
| Cloud | Будущий сервер | Существующий backend в Cloud-профиле, БД, задачи, объекты и наблюдаемость; настройки и секреты отдельны от dev |
| Windows-клиент | ПК клиента | Базовый WinUI 3 + WebView2 host реализован; общий frontend и ограниченный bridge, выпуск установщика впереди |
| Branch Edge | ПК внутри аптеки | Локальный профиль backend, PostgreSQL, синхронизация и локальная раздача UI; клиенты не подключаются к БД напрямую |
| Установщики и обновления | Отдельное хранилище артефактов релизов | Сайт ссылается только на выпущенные подписанные версии; исходники и данные аптек там не размещаются |

Для одной кассы Edge может работать на том же ПК. Для нескольких касс целевой
вариант из диалога — один назначенный ПК хранит общую базу и обслуживает другие
ПК по LAN; он должен оставаться включённым. Это не независимые базы на каждой
кассе. Потеря этого ПК или LAN требует отдельного сценария восстановления.

Размещение Edge на основном кассовом ПК уже разрешено
[ADR-0043](adr/0043-thirty-day-branch-edge-continuity.md), который уточняет
прежнее требование выделенного mini-PC из ADR-0001. До пилота остаются проверки
ресурсов, электропитания, LAN, восстановления и нескольких касс.

Cloud владеет справочниками и доступом, активный Edge — операциями своей точки.
Облако не меняет те же остатки параллельно. Переход существующей точки на Edge
требует процедуры передачи единственного права записи по
[ADR-0002](adr/0002-edge-writer-handover.md), проверки данных и управляемого
возврата. Копирование общей dev-БД клиентам не является установкой.

## 3. Последовательность и зависимости

Этап считается завершённым только при наличии указанного результата и
доказательств. Ответственные ниже — необходимые роли в команде, а не уже
нанятые люди. Календарные сроки и бюджет определяются после согласования
объёма этапа, оборудования и внешних участников.

### Этап 1. Публичный сайт и понятная карта проекта

- **Зависимости:** существующая веб-версия; реальный адрес входа задаётся
  конфигурацией, для разработки — `http://localhost:5173/login`.
- **Результат:** `website/` с главной страницей, описанием возможностей,
  страницей способов установки и ссылкой на общий вход. Статические HTML/CSS,
  сборка штатными возможностями Node, без новых библиотек. Локальный сайт —
  `http://127.0.0.1:4174`; существующее приложение остаётся на порту `5173`.
- **Приёмка:** переходы работают на компьютере и телефоне; клавиатура и фокус
  доступны; нет горизонтального переполнения; страница честно сообщает, что
  Windows-установщик ещё не выпущен. Нет фиктивной кнопки скачивания, обещаний
  готового offline-режима, выдуманных тарифов или опубликованного домена.
- **Доказательства:** тесты сборки и конфигурации, браузерная проверка размеров
  экрана и перехода ко входу, PR и успешный обязательный CI gate.
- **Ответственные:** frontend-инженер, QA, владелец продукта для текстов.

### Этап 2. Сценарии пользователей и контракт автономности

- **Зависимости:** карта текущих функций и возможностей ролей; существующие
  ADR Cloud/Edge, auth, прав и фискальной границы.
- **Результат:** макеты кассы, приёмки, обзора владельца и карточки аптеки для
  поддержки. Матрица действий по правам и точкам; состояния «сохранено»,
  «ожидает отправки», «результат неизвестен», «данные устарели».
- **Результат по отказам:** таблица действий при потере WAN, LAN, питания,
  диска и основного ПК; политика доступа и работы после 24 часов, 7 и 30 суток.
  Топология, границы и порядок реализации закреплены в
  [ADR-0043](adr/0043-thirty-day-branch-edge-continuity.md), пользовательские и
  аварийные состояния — в
  [контракте автономной работы](offline-operations-contract.md).
- **Приёмка:** кассир проходит продажу и исправление ошибки, сотрудник —
  приёмку, владелец — поиск расхождения без подсказок разработчика. Изменение
  составной роли открывает только соответствующие функции и точки; отзыв прав
  проверяется в уже открытой сессии. Названия ролей не управляют логикой.
- **Доказательства:** протокол наблюдения за пользователями, макеты состояний,
  принятые ADR и перечень операций, пока запрещённых без внешнего подтверждения.
- **Ответственные:** продуктовый дизайнер, backend-инженер, архитектор
  безопасности, QA; владелец продукта утверждает границы.

### Этап 3. Cloud staging и основа выпуска

- **Зависимости:** выбранный провайдер, регион, домен, ответственные за
  инфраструктуру и данные; это внешние решения, а не значения по умолчанию.
- **Результат:** отдельное тестовое окружение staging по существующему
  [production runbook](runbooks/production-deployment.md), HTTPS, секреты,
  мониторинг, резервное копирование и восстановление на другом устройстве.
  Основной домен раздаёт сайт; `app` — приложение и его API через один origin.
- **Приёмка:** данные и секреты dev не копируются в production; БД не доступна
  публично; проверены вход, refresh, logout, права, tenant-изоляция, срок
  сертификатов, уведомления об отказах и процедура восстановления.
- **Доказательства:** отчёт staging, измеренные RPO/RTO (допустимая потеря
  последних данных / время восстановления), журнал учебного восстановления,
  воспроизводимая сборка, перечень файлов релиза и CI gate.
- **Ответственные:** DevOps-инженер, backend-инженер, QA, архитектор
  безопасности. Сайт может публиковаться отдельно; его публикация не означает
  разрешение реальных продаж в приложении.

### Этап 4. Быстрое заполнение каталога и приходов

- **Текущий срез:** CSV/XLSX проходит предпросмотр, ручное сопоставление
  столбцов и загрузку в незавершённые позиции прихода по ADR-0045. Исходное
  название сохраняется для проверки; одинаковый файл не добавляется дважды.
  Форматы конкретных поставщиков, измерение времени на реальных накладных и
  фото/PDF остаются частью этапа.
- **Зависимости:** существующие черновики по ADR-0039/0040; образцы накладных,
  переданные законным способом для тестирования, и критерии качества данных.
- **Результат:** сначала Excel/CSV накладных и шаблоны колонок поставщиков;
  затем фото/PDF с исходником рядом и выделением сомнительных полей.
  Оба входа создают один проверяемый черновик прихода.
- **Приёмка:** сохранены введённые строки, нет дубля после повтора загрузки;
  понятны количество, упаковка, цены, партия и срок; неизвестный товар можно
  сопоставить или создать при наличии права; неполный документ не проводится.
  Распознавание предлагает значения, человек подтверждает проведение.
- **Доказательства:** измерение времени приёмки на реальных форматах, тесты
  конфликтов/повторов/изоляции, браузерный flow, отчёт точности по полям.
- **Ответственные:** backend- и frontend-инженеры, QA, специалист аптеки.
  OCR-провайдер, передача файлов и новые зависимости согласуются отдельно.
  Этап можно вести параллельно staging; он не блокирует разработку Edge.

### Этап 5. Проверка Edge без передачи права продажи

Первый read-only путь выполнен: строгий подписанный snapshot, RLS-хранилище,
Cloud transport, атомарная установка worker, локальный API и общий UI каталога,
поставщиков и партий. Worker криптографически проверяет подписанный snapshot,
БД связывает индексированные проекции с его неизменяемыми чанками, а API после
перезапуска повторно проверяет источник и кеширует успешный результат процесса.
Поиск, пагинация и сводки после этого не разбирают весь snapshot на каждом
запросе. Нагрузочный профиль целевого объёма выполнен на изолированном
контейнерном стенде. Этап остаётся незавершённым до реальных Windows
WAN/restart/restore проверок.

- **Зависимости:** этап 2, тестовые модели ПК и Windows, текущий sync-контракт
  и процедура активации. Локальные нагрузочные проверки не требуют этапа 3;
  проверка реального обмена перед пилотом требует готового staging.
- **Результат:** воспроизводимое локальное развёртывание на чистом тестовом
  ПК; один backend с явными Cloud/Edge-профилями; локальный PostgreSQL и
  защищённая связь с Cloud. Сначала режим проверки полученных данных без
  права выполнять реальные продажи и менять остатки точки.
- **Приёмка:** исходящая связь восстанавливается после перезапуска; повреждение
  или неполнота snapshots обнаруживаются; чужая точка не активируется;
  недельный объём обмена проходит частями и не создаёт повторных эффектов.
- **Доказательства:** автоматические интеграционные тесты плюс журнал на
  реальном ПК, сравнение контрольных сумм, проверка восстановления локальной
  БД. Docker окружения разработчика не объявляются клиентским установщиком.
- **Ответственные:** backend-инженер, Windows-инженер, QA, DevOps.

### Этап 6. Windows-клиент, установщик и обновления

- **Зависимости:** проверка Windows toolchain, этап 5, перечень оборудования,
  решение о подписи и формате пакета. Базовый host уже реализован по
  [desktop blueprint](desktop-host-implementation.md); остаются поставка
  локальных служб, установка, обновления и аппаратные проверки.
- **Результат:** `desktop/AurumPharma.Desktop` на WinUI 3 + WebView2, общий
  frontend, проверяемый bridge; установщик клиента и локальных компонентов
  с режимами «основной ПК точки» / «дополнительная касса». Установка
  ограничена поддерживаемыми конфигурациями и не требует Git/Python/Node у
  клиента. Устройство привязывается к аптеке, точке и кассе.
- **Приёмка:** чистая установка, повторный запуск и обновление сохраняют
  данные; служба стартует после перезагрузки; приложение работает без прав
  администратора. Внешний сайт не получает привилегированный desktop bridge.
  Удаление приложения по умолчанию не удаляет финансовую базу.
- **Обновления:** подписанные пакет и manifest, проверка совместимости UI,
  API и схемы, защита от отката к уязвимой версии, резервная копия и безопасный
  момент установки. Возврат версии приложения допускается только при
  совместимой схеме; автоматический downgrade БД не является откатом.
- **Доказательства:** Windows-тесты установки/ремонта/обновления и проверки
  подписи, аппаратная проверка принтера и сканера, release candidate и CI.
- **Ответственные:** Windows-инженер, DevOps, QA, архитектор безопасности.
  Только после этого сайт получает действительную ссылку на установщик.

### Этап 7. Управляемое включение автономной кассы

- **Зависимости:** этапы 2, 3, 5, 6, реальная фискальная интеграция и
  соответствующие внешние разрешения.
- **Результат:** одна тестовая касса, затем несколько касс одной точки;
  локальный сервер всегда остаётся путём продажи, независимо от WAN.
  Новые действия подключаются по одному: каждая операция получает собственные
  правила доступа, фискализации, повторов, синхронизации и восстановления.
- **Приёмка:** один writer, неизменяемая завершённая продажа, отсутствие
  отрицательных остатков и повторных списаний; потерянный ответ не вызывает
  слепой повтор оплаты. При потере LAN дополнительная касса не заводит свою
  независимую финансовую базу. Неподтверждённые операции видны оператору.
- **Доказательства:** сценарии отказов из раздела 4, сверка всех операций после
  восстановления связи и отдельная проверка отчётов Cloud на устаревших данных.
- **Ответственные:** backend-инженер, Windows-инженер, QA, специалист аптеки
  и представители платёжного/фискального провайдеров.

### Этап 8. Управление, сопровождение и пилотный допуск

- **Зависимости:** актуальные данные операций, роли и мониторинг; для реального
  запуска — все внешние требования из readiness manifest.
- **Результат:** владельцу — расхождения, дефицит, сроки и незавершённые
  документы с переходом к источнику цифр. Команде Aurum — подключение аптек,
  обращения, состояние узлов и синхронизации, расчёты и история поддержки.
- **Приёмка:** видна давность данных каждой точки; валовая прибыль не
  называется чистой; временный доступ поддержки персонален, ограничен сроком,
  причиной и аудитом. Переход к следующей аптеке не переносит чужие данные.
- **Доказательства:** сценарии владельца и поддержки, независимый аудит
  безопасности, тренировочный рабочий день, подписанный пилотный допуск.
- **Ответственные:** frontend/backend/DevOps/QA, руководитель поддержки,
  аптечный эксперт, юрист и владелец продукта по своей области.

## 4. Что означает проверка «до 30 дней без интернета»

Это три отдельных договора, которые нельзя подменять одним сроком токена:

| Контур | Что обязаны доказать | Что не следует из результата |
|---|---|---|
| Сохранность и доставка | Подтверждённые локальные операции переживают перезапуск и передаются после 24 часов / 7 / 30 суток без дублей и пропусков | Наличие базы не разрешает любую новую операцию |
| Вход и полномочия | Разрешённый сотрудник, точка, устройство, срок и защищённое время; явно задано поведение при невозможности получить отзыв прав | Долгий Cloud refresh-токен не становится offline-разрешением |
| Оплата и фискализация | Реальное оборудование и провайдер допускают конкретное действие в текущем состоянии и сроке | Внутренний чек и действующий вход не заменяют фискальное разрешение |

[ADR-0005](adr/0005-offline-auth-security-substrate.md) описывает grant v0 до
72 часов и защитную основу; это **не работающий 72-часовой offline-вход**.
Семидневное или 30-дневное продление, offline renewal и смена кассиров в v0 не
реализованы. Цель 30 дней требует authorization lease v1 и всех аппаратных
проверок из ADR-0043, а не правки константы.
SQL-попытки/сессии и внутренний алгоритм локального входа реализованы
отдельным [этапом v1](offline-local-sessions-v1.md), без включения runtime.
Следующий шаг: доверенный enrollment/подписи, защищённые время и состояние
активной сессии, recovery после сбоя commit и реальная TPM-приёмка.
Фискальные ограничения проверяются
отдельно по
[ADR-0018](adr/0018-tajikistan-regulatory-boundary.md) и официальным основаниям
на момент допуска. Если действие запрещено, данные сохраняются и показывается
согласованная аварийная процедура; «продолжить любой ценой» не допускается.

Минимальная матрица: WAN 24 часа / 7 / 30 суток; перезапуск клиента и службы;
потерянный ответ; повтор доставки; заполненный диск; потеря питания; изменение
часов; отзыв прав во время отсутствия связи; истечение разрешения; потеря LAN;
недоступный основной ПК; восстановление на другом ПК с передачей writer epoch;
обрыв во время выгрузки недельного объёма. Для каждого случая проверяются
данные, доступ, понятность интерфейса и время восстановления.

## 5. Общие условия завершения каждого модуля

1. Задача содержит наблюдаемую проблему, границы, владельца и критерии приёмки.
2. Изменение выполняется в отдельной `codex/*` ветке; общий dev/demo сохраняется.
3. Проверки выбираются через `scripts/verify-change.ps1 -Mode Auto -PlanOnly`;
   новые сценарии покрывают риск, а не повторяют строки реализации.
4. Просмотр финального diff, точечный commit, push и PR; обязательный CI gate
   должен быть зелёным для того commit, который сливается в `main`.
5. Развёртывается известная версия. Фиксируются версия кода, миграции, результат
   smoke, сохранность данных и возможный путь восстановления.
6. Обновляются только затронутые источники состояния и инструкции; в отчёте
   отдельно указано «реализовано», «проверено» и «работает у пользователя».

MFA остаётся добровольной для всех по
[ADR-0033](adr/0033-optional-account-mfa.md). Повторный пароль для критического
действия не расширяет полномочия сотрудника. RLS, immutable audit, область
прав и подтверждение уже включённой MFA не ослабляются при разработке новых
клиентов.

## 6. Внешние условия реального запуска

Этот план не заменяет
[pilot readiness manifest](compliance/pilot-readiness-manifest.json) и
[юридический gate](compliance/pilot-legal-gate.md). Требуются подтверждения по
законодательству, фармацевтическим правилам, ККУ/платежам, персональным данным,
инфраструктуре, независимому аудиту и восстановлению. У каждого условия должен
быть ответственный, действующий документ и проверяемый результат.

Публичный сайт, зелёные CI-проверки и технически работающий установщик по
отдельности не являются допуском аптеки к реальным операциям. Расширение пилота:
одна касса → несколько касс одной аптеки → несколько аптек; на каждом переходе
проверяется готовность именно новой конфигурации.
