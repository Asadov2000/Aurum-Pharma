# План развития Aurum Pharma

Статус: последовательность работ и критерии приёмки, а не отчёт о готовности.
Направление согласовано 2026-09-12; порядок работ обновлён 2026-09-23 после
PR №192 (`main 514fe26`). Текущий результат проверять по коду, CI и
[development-state.md](development-state.md).

## 1. Цель и исходное состояние

Развивать одну платформу с общими правилами продаж, складского учёта и доступа:
публичный сайт, рабочее веб-приложение и устанавливаемый Windows-клиент.
Пользователь получает функции по совокупности ролей и разрешённых точек.
«Касса», «Склад» и «Управление» — представления задач, а не отдельные продукты
и не жёсткие типы аккаунтов.

Сейчас разработка и demo работают на ПК владельца проекта. Облачного рабочего
окружения, распространяемого Windows-приложения и готового установщика нет.
Production-конфигурация и отдельные механизмы Edge существуют в репозитории;
это не означает, что они уже развёрнуты или дают автономную кассу.

Уже реализованы касса, роли, каталог и его Excel/CSV-импорт, поставщики,
сохраняемые черновики приходов, создание товара из прихода, отчёты, аудит,
защита от части сетевых сбоев и механизмы резервного копирования. Их не нужно
переписывать заново. Импорт **накладных** Excel/CSV и распознавание фото/PDF
остаются отдельными будущими этапами.

Текущий блок — проверка локального Edge: индексированные данные уже доступны
только для чтения. Автономные продажи и готовый установщик ещё не выпущены.

### Ближайший порядок работ

1. Предварительная проверка сохранённого подписанного снимка до готовности
   Edge API и при смене ревизии, а также ускорение страницы каталога без поиска
   реализованы. Повторный изолированный замер на 100 000 товарах и 250 000
   партиях: предварительная проверка 15,4 с, первый готовый запрос 0,92 с,
   повторные запросы p95 1,17 с. Методика и границы — в
   [отчёте](edge-full-snapshot-benchmark-2026-09-23.md). Эти цифры не являются
   допуском на Windows и ещё превышают ориентир 300 мс. Нагрузочные данные
   создавать только в изолированной БД.
2. На целевом Windows-ПК повторить холодный замер вместе с PostgreSQL, worker
   и клиентом. Проверить отключение интернета, перезапуск служб и ПК,
   прерванную установку снимка и восстановление резервной копии на другом
   устройстве. Зафиксировать время восстановления и полноту данных.
3. Реализовать автономный вход и ограниченные по сроку разрешения, затем
   локальную запись продаж, смен и возвратов с безопасной синхронизацией.
   Разрабатывать в тестовом контуре; реальные продажи включать только после
   выполнения условий этапа 7.
4. Завершить установщик, службы, подписанные обновления, принтер и сканер;
   проверить установку с сайта и флешки без загрузки компонентов из интернета.
5. Пройти длительные сценарии автономности до 30 дней, сверку после подключения,
   несколько касс и пилотный допуск. Это целевая приёмка, не текущая возможность.

Cloud staging и импорт накладных остаются отдельными направлениями. Отсутствие
сервера не блокирует локальные тесты, но реальный пилот требует staging,
проверенных резервных копий и внешних платёжных/фискальных интеграций.

### Windows и оборудование

- Основная целевая конфигурация — Windows 11 x64. Windows 10 рассматривается
  как переходный вариант только для поддерживаемых редакций и после отдельной
  проверки всей поставки; возможность сборки не означает поддержку продукта.
- Windows 7/8/8.1 в текущий выпуск не включаются. Для таких аптек сначала
  оценить обновление ОС или замену ПК; отдельную устаревшую сборку не создавать.
- Перед окончательными системными требованиями обследовать 5–10 пилотных аптек:
  ОС, процессор, память, диск, принтер, сканер, LAN и перебои питания.
  Профиль ADR-0043 — исходная нагрузочная цель, а не измеренный минимум.
- Для основного ПК предусмотреть SSD, источник бесперебойного питания,
  отключение автоматического сна и резервную копию на другом носителе.
  Отсутствие интернета и отказ основного ПК — разные сценарии восстановления.

## 2. Где будет работать каждая часть

| Часть | Целевое расположение | Состояние и граница |
|---|---|---|
| Публичный сайт | Основной домен владельца проекта | Отдельная статическая сборка `website/`; домен и публикация ещё настраиваются |
| Рабочее приложение | Поддомен `app` того же проекта | Существующий `frontend/`, API через тот же origin; единый вход и действующие роли |
| Cloud | Будущий сервер | Существующий backend в Cloud-профиле, БД, задачи, объекты и наблюдаемость; настройки и секреты отдельны от dev |
| Windows-клиент | ПК клиента | Базовый WinUI 3 + WebView2 host реализован; общий frontend и ограниченный bridge, выпуск установщика впереди |
| Branch Edge | ПК внутри аптеки | Локальный профиль backend, PostgreSQL, синхронизация и локальная раздача UI; клиенты не подключаются к БД напрямую |
| Установщики и обновления | Отдельное хранилище артефактов релизов | Сайт ссылается только на выпущенные подписанные версии; исходники и данные аптек там не размещаются |

Для одной кассы Edge может работать на том же ПК. Для нескольких касс целевой
вариант из диалога — один назначенный ПК хранит общую базу и обслуживает другие
ПК по LAN; он должен оставаться включённым. Это не независимые базы на каждой
кассе. Потеря этого ПК или LAN требует отдельного сценария восстановления.

Размещение Edge на основном кассовом ПК уже разрешено
[ADR-0043](adr/0043-thirty-day-branch-edge-continuity.md), который уточняет
прежнее требование выделенного mini-PC из ADR-0001. До пилота остаются проверки
ресурсов, электропитания, LAN, восстановления и нескольких касс.

Cloud владеет справочниками и доступом, активный Edge — операциями своей точки.
Облако не меняет те же остатки параллельно. Переход существующей точки на Edge
требует процедуры передачи единственного права записи по
[ADR-0002](adr/0002-edge-writer-handover.md), проверки данных и управляемого
возврата. Копирование общей dev-БД клиентам не является установкой.

## 3. Последовательность и зависимости

Этап считается завершённым только при наличии указанного результата и
доказательств. Ответственные ниже — необходимые роли в команде, а не уже
нанятые люди. Календарные сроки и бюджет определяются после согласования
объёма этапа, оборудования и внешних участников.

### Этап 1. Публичный сайт и понятная карта проекта

- **Зависимости:** существующая веб-версия; реальный адрес входа задаётся
  конфигурацией, для разработки — `http://localhost:5173/login`.
- **Результат:** `website/` с главной страницей, описанием возможностей,
  страницей способов установки и ссылкой на общий вход. Статические HTML/CSS,
  сборка штатными возможностями Node, без новых библиотек. Локальный сайт —
  `http://127.0.0.1:4174`; существующее приложение остаётся на порту `5173`.
- **Приёмка:** переходы работают на компьютере и телефоне; клавиатура и фокус
  доступны; нет горизонтального переполнения; страница честно сообщает, что
  Windows-установщик ещё не выпущен. Нет фиктивной кнопки скачивания, обещаний
  готового offline-режима, выдуманных тарифов или опубликованного домена.
- **Доказательства:** тесты сборки и конфигурации, браузерная проверка размеров
  экрана и перехода ко входу, PR и успешный обязательный CI gate.
- **Ответственные:** frontend-инженер, QA, владелец продукта для текстов.

### Этап 2. Сценарии пользователей и контракт автономности

- **Зависимости:** карта текущих функций и возможностей ролей; существующие
  ADR Cloud/Edge, auth, прав и фискальной границы.
- **Результат:** макеты кассы, приёмки, обзора владельца и карточки аптеки для
  поддержки. Матрица действий по правам и точкам; состояния «сохранено»,
  «ожидает отправки», «результат неизвестен», «данные устарели».
- **Результат по отказам:** таблица действий при потере WAN, LAN, питания,
  диска и основного ПК; политика доступа и работы после 24 часов, 7 и 30 суток.
  Топология, границы и порядок реализации закреплены в
  [ADR-0043](adr/0043-thirty-day-branch-edge-continuity.md), пользовательские и
  аварийные состояния — в
  [контракте автономной работы](offline-operations-contract.md).
- **Приёмка:** кассир проходит продажу и исправление ошибки, сотрудник —
  приёмку, владелец — поиск расхождения без подсказок разработчика. Изменение
  составной роли открывает только соответствующие функции и точки; отзыв прав
  проверяется в уже открытой сессии. Названия ролей не управляют логикой.
- **Доказательства:** протокол наблюдения за пользователями, макеты состояний,
  принятые ADR и перечень операций, пока запрещённых без внешнего подтверждения.
- **Ответственные:** продуктовый дизайнер, backend-инженер, архитектор
  безопасности, QA; владелец продукта утверждает границы.

### Этап 3. Cloud staging и основа выпуска

- **Зависимости:** выбранный провайдер, регион, домен, ответственные за
  инфраструктуру и данные; это внешние решения, а не значения по умолчанию.
- **Результат:** отдельное тестовое окружение staging по существующему
  [production runbook](runbooks/production-deployment.md), HTTPS, секреты,
  мониторинг, резервное копирование и восстановление на другом устройстве.
  Основной домен раздаёт сайт; `app` — приложение и его API через один origin.
- **Приёмка:** данные и секреты dev не копируются в production; БД не доступна
  публично; проверены вход, refresh, logout, права, tenant-изоляция, срок
  сертификатов, уведомления об отказах и процедура восстановления.
- **Доказательства:** отчёт staging, измеренные RPO/RTO (допустимая потеря
  последних данных / время восстановления), журнал учебного восстановления,
  воспроизводимая сборка, перечень файлов релиза и CI gate.
- **Ответственные:** DevOps-инженер, backend-инженер, QA, архитектор
  безопасности. Сайт может публиковаться отдельно; его публикация не означает
  разрешение реальных продаж в приложении.

### Этап 4. Быстрое заполнение каталога и приходов

- **Зависимости:** существующие черновики по ADR-0039/0040; образцы накладных,
  переданные законным способом для тестирования, и критерии качества данных.
- **Результат:** сначала Excel/CSV накладных и шаблоны колонок поставщиков;
  затем фото/PDF с исходником рядом и выделением сомнительных полей.
  Оба входа создают один проверяемый черновик прихода.
- **Приёмка:** сохранены введённые строки, нет дубля после повтора загрузки;
  понятны количество, упаковка, цены, партия и срок; неизвестный товар можно
  сопоставить или создать при наличии права; неполный документ не проводится.
  Распознавание предлагает значения, человек подтверждает проведение.
- **Доказательства:** измерение времени приёмки на реальных форматах, тесты
  конфликтов/повторов/изоляции, браузерный flow, отчёт точности по полям.
- **Ответственные:** backend- и frontend-инженеры, QA, специалист аптеки.
  OCR-провайдер, передача файлов и новые зависимости согласуются отдельно.
  Этап можно вести параллельно staging; он не блокирует разработку Edge.

### Этап 5. Проверка Edge без передачи права продажи

Первый read-only путь выполнен: строгий подписанный snapshot, RLS-хранилище,
Cloud transport, атомарная установка worker, локальный API и общий UI каталога,
поставщиков и партий. Worker криптографически проверяет подписанный snapshot,
БД связывает индексированные проекции с его неизменяемыми чанками, а API после
перезапуска повторно проверяет источник и кеширует успешный результат процесса.
Поиск, пагинация и сводки после этого не разбирают весь snapshot на каждом
запросе. Этап остаётся незавершённым до
нагрузочного профиля целевого объёма и реальных Windows WAN/restart/restore
проверок.

- **Зависимости:** этап 2, тестовые модели ПК и Windows, текущий sync-контракт
  и процедура активации. Локальные нагрузочные проверки не требуют этапа 3;
  проверка реального обмена перед пилотом требует готового staging.
- **Результат:** воспроизводимое локальное развёртывание на чистом тестовом
  ПК; один backend с явными Cloud/Edge-профилями; локальный PostgreSQL и
  защищённая связь с Cloud. Сначала режим проверки полученных данных без
  права выполнять реальные продажи и менять остатки точки.
- **Приёмка:** исходящая связь восстанавливается после перезапуска; повреждение
  или неполнота snapshots обнаруживаются; чужая точка не активируется;
  недельный объём обмена проходит частями и не создаёт повторных эффектов.
- **Доказательства:** автоматические интеграционные тесты плюс журнал на
  реальном ПК, сравнение контрольных сумм, проверка восстановления локальной
  БД. Docker окружения разработчика не объявляются клиентским установщиком.
- **Ответственные:** backend-инженер, Windows-инженер, QA, DevOps.

### Этап 6. Windows-клиент, установщик и обновления

- **Зависимости:** проверка Windows toolchain, этап 5, перечень оборудования,
  решение о подписи и формате пакета. Базовый host уже реализован по
  [desktop blueprint](desktop-host-implementation.md); остаются поставка
  локальных служб, установка, обновления и аппаратные проверки.
- **Результат:** `desktop/AurumPharma.Desktop` на WinUI 3 + WebView2, общий
  frontend, проверяемый bridge; установщик клиента и локальных компонентов
  с режимами «основной ПК точки» / «дополнительная касса». Установка
  ограничена поддерживаемыми конфигурациями и не требует Git/Python/Node у
  клиента. Устройство привязывается к аптеке, точке и кассе.
- **Приёмка:** чистая установка, повторный запуск и обновление сохраняют
  данные; служба стартует после перезагрузки; приложение работает без прав
  администратора. Внешний сайт не получает привилегированный desktop bridge.
  Удаление приложения по умолчанию не удаляет финансовую базу.
- **Обновления:** подписанные пакет и manifest, проверка совместимости UI,
  API и схемы, защита от отката к уязвимой версии, резервная копия и безопасный
  момент установки. Возврат версии приложения допускается только при
  совместимой схеме; автоматический downgrade БД не является откатом.
- **Доказательства:** Windows-тесты установки/ремонта/обновления и проверки
  подписи, аппаратная проверка принтера и сканера, release candidate и CI.
- **Ответственные:** Windows-инженер, DevOps, QA, архитектор безопасности.
  Только после этого сайт получает действительную ссылку на установщик.

### Этап 7. Управляемое включение автономной кассы

- **Зависимости:** этапы 2, 3, 5, 6, реальная фискальная интеграция и
  соответствующие внешние разрешения.
- **Результат:** одна тестовая касса, затем несколько касс одной точки;
  локальный сервер всегда остаётся путём продажи, независимо от WAN.
  Новые действия подключаются по одному: каждая операция получает собственные
  правила доступа, фискализации, повторов, синхронизации и восстановления.
- **Приёмка:** один writer, неизменяемая завершённая продажа, отсутствие
  отрицательных остатков и повторных списаний; потерянный ответ не вызывает
  слепой повтор оплаты. При потере LAN дополнительная касса не заводит свою
  независимую финансовую базу. Неподтверждённые операции видны оператору.
- **Доказательства:** сценарии отказов из раздела 4, сверка всех операций после
  восстановления связи и отдельная проверка отчётов Cloud на устаревших данных.
- **Ответственные:** backend-инженер, Windows-инженер, QA, специалист аптеки
  и представители платёжного/фискального провайдеров.

### Этап 8. Управление, сопровождение и пилотный допуск

- **Зависимости:** актуальные данные операций, роли и мониторинг; для реального
  запуска — все внешние требования из readiness manifest.
- **Результат:** владельцу — расхождения, дефицит, сроки и незавершённые
  документы с переходом к источнику цифр. Команде Aurum — подключение аптек,
  обращения, состояние узлов и синхронизации, расчёты и история поддержки.
- **Приёмка:** видна давность данных каждой точки; валовая прибыль не
  называется чистой; временный доступ поддержки персонален, ограничен сроком,
  причиной и аудитом. Переход к следующей аптеке не переносит чужие данные.
- **Доказательства:** сценарии владельца и поддержки, независимый аудит
  безопасности, тренировочный рабочий день, подписанный пилотный допуск.
- **Ответственные:** frontend/backend/DevOps/QA, руководитель поддержки,
  аптечный эксперт, юрист и владелец продукта по своей области.

## 4. Что означает проверка «до 30 дней без интернета»

Это три отдельных договора, которые нельзя подменять одним сроком токена:

| Контур | Что обязаны доказать | Что не следует из результата |
|---|---|---|
| Сохранность и доставка | Подтверждённые локальные операции переживают перезапуск и передаются после 24 часов / 7 / 30 суток без дублей и пропусков | Наличие базы не разрешает любую новую операцию |
| Вход и полномочия | Разрешённый сотрудник, точка, устройство, срок и защищённое время; явно задано поведение при невозможности получить отзыв прав | Долгий Cloud refresh-токен не становится offline-разрешением |
| Оплата и фискализация | Реальное оборудование и провайдер допускают конкретное действие в текущем состоянии и сроке | Внутренний чек и действующий вход не заменяют фискальное разрешение |

[ADR-0005](adr/0005-offline-auth-security-substrate.md) описывает grant v0 до
72 часов и защитную основу; это **не работающий 72-часовой offline-вход**.
Семидневное или 30-дневное продление, offline renewal и смена кассиров в v0 не
реализованы. Цель 30 дней требует authorization lease v1 и всех аппаратных
проверок из ADR-0043, а не правки константы. Фискальные ограничения проверяются
отдельно по
[ADR-0018](adr/0018-tajikistan-regulatory-boundary.md) и официальным основаниям
на момент допуска. Если действие запрещено, данные сохраняются и показывается
согласованная аварийная процедура; «продолжить любой ценой» не допускается.

Минимальная матрица: WAN 24 часа / 7 / 30 суток; перезапуск клиента и службы;
потерянный ответ; повтор доставки; заполненный диск; потеря питания; изменение
часов; отзыв прав во время отсутствия связи; истечение разрешения; потеря LAN;
недоступный основной ПК; восстановление на другом ПК с передачей writer epoch;
обрыв во время выгрузки недельного объёма. Для каждого случая проверяются
данные, доступ, понятность интерфейса и время восстановления.

## 5. Общие условия завершения каждого модуля

1. Задача содержит наблюдаемую проблему, границы, владельца и критерии приёмки.
2. Изменение выполняется в отдельной `codex/*` ветке; общий dev/demo сохраняется.
3. Проверки выбираются через `scripts/verify-change.ps1 -Mode Auto -PlanOnly`;
   новые сценарии покрывают риск, а не повторяют строки реализации.
4. Просмотр финального diff, точечный commit, push и PR; обязательный CI gate
   должен быть зелёным для того commit, который сливается в `main`.
5. Развёртывается известная версия. Фиксируются версия кода, миграции, результат
   smoke, сохранность данных и возможный путь восстановления.
6. Обновляются только затронутые источники состояния и инструкции; в отчёте
   отдельно указано «реализовано», «проверено» и «работает у пользователя».

MFA остаётся добровольной для всех по
[ADR-0033](adr/0033-optional-account-mfa.md). Повторный пароль для критического
действия не расширяет полномочия сотрудника. RLS, immutable audit, область
прав и подтверждение уже включённой MFA не ослабляются при разработке новых
клиентов.

## 6. Внешние условия реального запуска

Этот план не заменяет
[pilot readiness manifest](compliance/pilot-readiness-manifest.json) и
[юридический gate](compliance/pilot-legal-gate.md). Требуются подтверждения по
законодательству, фармацевтическим правилам, ККУ/платежам, персональным данным,
инфраструктуре, независимому аудиту и восстановлению. У каждого условия должен
быть ответственный, действующий документ и проверяемый результат.

Публичный сайт, зелёные CI-проверки и технически работающий установщик по
отдельности не являются допуском аптеки к реальным операциям. Расширение пилота:
одна касса → несколько касс одной аптеки → несколько аптек; на каждом переходе
проверяется готовность именно новой конфигурации.
