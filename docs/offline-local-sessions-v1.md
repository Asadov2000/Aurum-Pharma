# Сохраняемые попытки и локальные сессии v1

Внутренний этап подготовки Edge: `local_auth_service.py` и
`local_auth_repository.py`. HTTP, Windows bridge и разрешающий runtime
не подключены. `DenyAllOfflineLeaseVerifierV1` остаётся действующим правилом.

## Порядок входа

1. Проверить канонический digest и Cloud-подпись lease независимым verifier.
2. В собственной SQL-транзакции установить tenant/actor только из проверенного
   lease. Заблокировать существующий guard сотрудника; неизвестный guard
   не создаётся автоматически.
3. Сопоставить доверенный допуск, credential/context, ревизии, TPM-привязку,
   защиту от отката и время. Затем заблокировать рабочее место.
4. Проверить отдельный секрет реальным bcrypt/HMAC вне event loop, удерживая
   блокировки. Повторно проверить время и допуск после вычисления.
5. Сохранить результат и обновить защищённый high-water. Ответ разрешается
   вернуть только после успешного SQL commit и завершения доверенного контекста.

Пять неправильных секретов блокируют вход на пять минут доверенного времени.
Заблокированный вход не запускает bcrypt. Отказ из-за неправильного секрета
возвращается **после commit**, чтобы вызывающий код не откатил счётчик.
После окончания блокировки правильный секрет сбрасывает число ошибок; очередной
неправильный секрет снова блокирует вход. Последовательность попыток никогда
не обнуляется при успешном входе.

Ключ guard: tenant + Edge node + сотрудник + credential ID. Lease, смена,
рабочее место, writer epoch, credential revision и перезапуск процесса не
создают новый счётчик. Изменение enrollment-контекста требует отдельного
доверенного recovery/provisioning; вход не обновляет контекст сам.

Успешный вход создаёт новый UUID сессии и отзывает предыдущую активную сессию
рабочего места. Срок ограничен меньшим из срока lease и политики повторного
входа (не более 24 часов). Сессия содержит область доступа, ссылки на credential
и политику, контекст смены и доверенное время. UUID не является bearer token.
Пароли, pepper, verifier и Cloud-токены в этих таблицах не сохраняются.

## Границы защиты

`local_auth_guard` и `local_auth_session` имеют tenant RLS, audit-поля,
неизменяемый audit-log и ограничения БД. Обычная транзакция использует
`aurum_app`; scope не даёт обхода RLS. Repository не делает commit, не выдаёт
допуск и не выполняет автоматическое provisioning.

PostgreSQL сохраняет состояние после нормального перезапуска, но сам
по себе не защищает от подмены или восстановления старой копии БД. Алгоритм
требует `TrustedLocalLoginStateProviderV1`: он подтверждает актуальность допуска
и независимого enrollment, выдаёт TPM-protected pepper, проверяет guard против
аппаратно закреплённого состояния и удерживает сериализацию до commit.
При успехе одним защищённым обновлением сохраняются guard и digest полной
новой сессии по рабочему месту. Такой указатель заменяет сессию предыдущего
сотрудника; при ошибочном секрете указатель сохраняется. Последующее доверенное
чтение должно сверять сессию с этим seal, иначе выборочный откат session-row
может вернуть старую сессию при неизменённом guard.
Реального положительного адаптера пока нет.

Защищённый high-water продвигается **до** SQL commit. Если SQL commit затем
не выполнен, между хранилищами возникает forward gap: следующий вход
обязан отказать до доверенного recovery. Это безопасный отказ, а не обещание
атомарности между PostgreSQL и TPM.

Проверка целостности сохраняемой сессии, подпись enrollment, восстановление
защищённых часов после перезапуска, TPM provisioning, ACL Windows-службы
и аппаратная fault matrix остаются следующими этапами. SQL repository нельзя
напрямую считать защищённым session-provider для lease pipeline. Полноценный
автономный вход и продажи не включены; месяц без сети ещё не принят.
