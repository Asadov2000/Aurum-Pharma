# TPM-счётчик и checkpoint защищённого локального состояния

Внутренний шаг E6-06 после native-проведения физических и смешанных наличных
продаж: `WindowsTpmNvCounter` и `WindowsTpmProtectedStateStore` реализуют границу
между уже подготовленным аппаратным счётчиком и существующим файлом checkpoint.
Runtime автономного входа и продаж остаётся DenyAll. Это ещё не реализация
provider из `offline_auth_lease_state.py` или `local_auth_state.py`.

## Независимая привязка

Будущий доверенный enrollment должен совместно закрепить NV index, его Name,
SHA256 секрета авторизации, tenant/device context digest, минимальный счётчик
и путь к единственному файлу службы. SQL, файл, UI и RSA-encrypted envelope
не могут сами установить эту привязку. В частности, открытый RSA-ключ позволяет
создать новый envelope: отдельно закреплённый auth digest запрещает принять
подставленный секрет. Проверка подписи enrollment и Windows ACL службы ещё
не реализованы этим компонентом.

`OpenExisting` открывает только инициализированный TPM 2.0 NV counter:
SHA256 Name, пустая authPolicy, размер 8 и точные атрибуты `0x22040014`
(`AUTHREAD | AUTHWRITE | COUNTER | NO_DA | WRITTEN`). `ORDERLY`, доступ через
owner/platform/policy и неизвестные атрибуты отклоняются. Name одновременно
сверяется с независимой привязкой и пересчитывается по public area.

Поддерживаются только фиксированные `NV_ReadPublic`, `NV_Read` и
`NV_Increment`. Создание, удаление, сброс индекса, поиск подходящего индекса
и автоматическое восстановление отсутствуют. Секрет используется только
в локальном TBS password session; ответы проверяются строго по длине,
заголовку, коду и auth-area. Это граница доверенного Windows-хоста,
не удалённая аттестация и не защита от скомпрометированного ядра/TBS.

## Сохранение и отказ

Checkpoint фиксированного размера содержит versioned magic, digest полной
привязки, аппаратное поколение, digest полного будущего защищённого состояния
и HMAC-SHA256. Отдельный MAC-ключ выводится из секретного NV auth с разделением
доменов и полной привязкой. В файле нет auth, pepper или полного состояния
пользователя. Метод не интерпретирует policy, guard или session: их полное
каноническое содержимое обязан связать будущий доверенный provider.

1. Открыть существующий обычный файл с исключительным доступом. Не создавать
   отсутствующий файл; отклонить неверный размер, reparse points, UNC и ADS.
2. Сверить HMAC, привязку и поколение с текущим authenticated NV read.
   При изменении также сравнить точный ожидаемый checkpoint.
3. Продвинуть TPM ровно на один шаг и проверить обратным чтением. Только затем
   записать новый checkpoint, выполнить `Flush(true)` и сверить все байты.
4. Закрыть файловый дескриптор до выдачи результата. Сбой native-вызова,
   закрытия, flush, чтения или сверки необратимо блокирует этот экземпляр
   и очищает ключи. Неоднозначный increment автоматически не повторяется.

Восстановление старой копии файла при более новом аппаратном счётчике
отклоняется даже с корректным старым HMAC. Сбой между аппаратной записью
и сохранением файла создаёт forward gap и требует доверенного recovery.
Если файл уже сохранён, но последующий SQL commit не состоялся, будущий
provider обязан сверить полный SQL state с checkpoint и отказать при разрыве.
Хранилище самостоятельно SQL не читает и разрыв не исправляет.

TPM Increment не является межпроцессным CAS. Lock экземпляра и exclusive
файловый дескриптор сериализуют сотрудничавшие вызовы одного закреплённого
файла; будущая служба обязана обеспечить единственного владельца NV index,
защищённый каталог и независимый canonical path. Проверки reparse points
не заменяют ACL и не устраняют TOCTOU при враждебной подмене каталогов.

## Границы приёмки

Согласно TCG, новый counter с тем же Name начинает с большего значения,
чем этот Name имел за время жизни TPM. TPM Clear или замена устройства
не считаются новым доверенным началом: прежние hardware key, enrollment
и recovery должны проверяться независимо. Один NV Name не доказывает
непрерывность устройства. Ошибки TPM, включая rate/availability, дают отказ.

Детерминированные native-протокольные и файловые тесты проверяют подмену,
откат, сбои, конкуренцию и порядок commit без доступа к реальному TPM.
Не выполнены provisioning, защищённый policy/session provider, trusted UTC,
служба/IPC/ACL, recovery и аппаратная Windows fault matrix из существующего
контракта. Runtime не включается; E6-06 открыт: **2/7 (4)**.
