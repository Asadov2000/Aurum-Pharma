# Подключение Payom для входа

Решение и границы: [ADR-0042](../adr/0042-account-login-identities.md).

## До включения

Получить в кабинете Payom персональный адрес HTTPS API, Bearer-ключ и разрешённое
имя отправителя. Публичный пример `https://HOST/api/message` — шаблон, а не адрес
сервиса. Уточнить схему успешного/ошибочного ответа, стоимость сообщения и
доставку на нужные операторы. Не присылать ключи в чат или PR.

## Текущее состояние подключения

Реализованы адаптер Payom и проверки с подменённым HTTP-транспортом. Реальные
учётные данные ещё не подключены; доставка SMS на номера операторов не проверена.
Зелёный CI подтверждает поведение кода, а не готовность платной отправки.

Параметры SMS передаются API только в обычном `docker-compose.yml`.
`docker-compose.demo.yml` и `docker-compose.production.yml` пока не передают их
и не подключают Payom-секрет. В этих профилях остаётся `SMS_PROVIDER=disabled`;
`GET /api/v1/auth/methods` сообщает, что вход по телефону недоступен.

## Обычная локальная разработка

По умолчанию SMS отключены. Для изолированных тестов используется
`SMS_PROVIDER=development`: отправки нет, тестовый код доступен только в
development. Этот режим нельзя предоставлять реальным пользователям.

Для отдельной проверки через обычный `docker-compose.yml` задать в локальной,
исключённой из Git конфигурации:

```dotenv
SMS_PROVIDER=payom
PAYOM_API_URL=https://<выданный-Payom-хост>/api/message
PAYOM_SENDER_NAME=AurumPharma
SMS_TIMEOUT_SECONDS=10
SMS_DAILY_LIMIT=100
```

`PAYOM_API_TOKEN` заполнить отдельно секретным значением. Имя отправителя в
примере заменить, если Payom разрешил другое. Не выводить полный `docker compose
config` или environment контейнера в публичный лог: там может оказаться ключ.
После изменения конфигурации API этого профиля нужно пересоздать с сохранением
БД и томов. Не запускать второй стек поверх работающего demo с теми же портами.
Очистка и повторный seed общей БД не нужны. Demo launcher не является способом
активации этих параметров: он запускает другой compose-профиль.

После подключения проверить реальную доставку на согласованном тестовом номере,
затем на доступных номерах разных операторов: время получения, имя отправителя,
повторный запрос, неправильный/просроченный код и вход после перезагрузки. Эти
проверки отправляют платные SMS и выполняются отдельно от CI. При
`SMS_PROVIDER=payom` тестовые коды клиенту не выдаются даже в development.

## Current-main demo и серверное включение

Цепочка `start-current-main-demo.ps1` → `start-local-demo-admin.ps1` →
`start-showcase-demo.ps1` использует `docker-compose.demo.yml`. Файл
`.env.showcase.local` имеет строгий список разрешённых секретов: добавление
`SMS_PROVIDER` или `PAYOM_*` будет отвергнуто launcher. Передача этих переменных
через окружение процесса тоже не подключит их к API: в demo compose отсутствует
такое сопоставление. `Rebuild` и `SkipSeed` обновляют код, но не включают SMS.

Demo API подключён к обычной сети `web`, а также внутренним `db`, `broker` и
`storage`; утверждать, что его исходящий доступ полностью изолирован, нельзя.
Для включения Payom в demo нужен отдельный проверяемый шаг: явно подключить
параметры и защищённый секрет, сохранив проверку launcher и существующие данные.
Нельзя добавлять Bearer-ключ в файл с генерируемыми hex-секретами или ослаблять
его проверку ради ручного обхода.

Текущий production-профиль изолирует API внутренними Docker-сетями. Перед
серверным включением Payom нужно отдельно настроить ограниченный исходящий
HTTPS-доступ к выданному endpoint и подключение секрета к API. Отправка сейчас
выполняется самим API, а не почтовым worker: его сеть `mailer-egress` не решает
эту задачу. Нужно явно добавить параметры и монтирование `PAYOM_API_TOKEN` из
защищённого secret-файла для `AURUM_SECRETS_DIR`, проверить DNS, TLS-доверие
сертификату Payom и отсутствие ключа в логах. Нынешний список production secrets
не содержит Payom. Само изменение `SMS_PROVIDER` сетевой доступ не открывает.
Эти deployment-изменения и проверка настоящей доставки выполняются отдельным
этапом перед включением; текущая реализация их не подтверждает.

## Сбой провайдера

Показывается понятное сообщение, вход по почте с паролем остаётся доступным.
После таймаута не повторять запрос автоматически: неизвестно, принял ли Payom
первую отправку. Повтор пользователь инициирует после периода ожидания. HTTP 2xx
не означает, что телефон получил сообщение; отсутствие SMS проверять по
кабинету провайдера. Не отключать MFA, лимиты и проверку кода для обхода сбоя.

Для остановки отправок установить `SMS_PROVIDER=disabled` и обновить API.
Подтверждённые номера и действующие сессии удалять не требуется.
