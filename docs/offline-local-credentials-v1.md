# Локальный секрет сотрудника и защита устройства v1

Статус: криптографические примитивы, не готовый автономный вход. HTTP, допуск
владельцем, доверенный выпуск, лимиты попыток, постоянное хранилище с защитой от
отката и создание локальной сессии не подключены. Runtime по-прежнему DenyAll.

## Отдельная проверка на Edge

`backend/app/domains/sync/local_credentials.py` создаёт отдельный случайный
секрет с энтропией 192 бита. Это не PIN и не пароль Cloud; импорта Cloud password
hash, refresh/access-токена или SMS-кода нет. Секрет возвращается только в
результате выдачи, а запись содержит скрываемый в представлении verifier.

Контекст связывает аудиторию `aurum-edge-local-auth-v1`, точный scope,
идентификатор/ревизию credential, TPM binding и отдельный ключ защиты секрета.
Lease ID не входит в контекст: новый lease не требует автоматически менять
credential. Смена activation, writer epoch или credential revision меняет digest
и требует явно согласованного повторного выпуска. Ключ владения устройством и
ключ защиты локального секрета должны иметь разные ID и SPKI.

Verifier использует `bcrypt(base64(HMAC-SHA384(...)))` с фиксированным cost 12.
Однозначный HMAC-вход состоит из отдельного domain, 32-байтного SHA-256 digest
канонического контекста и локального секрета фиксированного формата. Base64
результат занимает 64 ASCII-байта. 32-байтный device pepper хранится отдельно
от verifier и получается только через доверенный protector. Неизвестный
алгоритм, изменённый cost и повреждённые модели отсекаются до дорогого verify.
Модели после `model_copy`/`model_construct` повторно валидируются.
Подход к peppering сверён с
[OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

`verify_local_credential` принимает ожидаемый контекст независимо от записи.
Совпадение означает только криптографическую проверку. Оно не доказывает допуск
владельцем, актуальность revision или отсутствие отзыва и само не создаёт
сессию. Перед вызовом будущий аутентификатор обязан атомарно проверить доверенное
состояние и ограничения попыток; после него — надёжно сохранить новую сессию.
При неудаче счётчик попыток должен переживать commit, перезапуск и восстановление.

`SecretStr` и скрытый `repr` предотвращают случайный вывод, но не шифруют память.
Python получает pepper в память; гарантированное стирание immutable `str`/`bytes`
не обещается. Персистентный адаптер не должен принимать masked JSON как запись
verifier: сохранение чувствительного значения требует отдельного контролируемого
кодека и защищённого канала. UI не хранит эти материалы в localStorage.

## Windows protector

`WindowsTpmSecretProtector` в `desktop/AurumPharma.Desktop.Core/Security/`
является нативным криптографическим адаптером, а не владельцем авторизации.
Host и WebView bridge его не вызывают. Будущий Edge security broker получает
доступ к ключу по service ACL; решения о сотрудниках и сессиях остаются в backend.

Protector открывает только уже подготовленный machine key через Microsoft
Platform Crypto Provider, сверяет ожидаемый SPKI и параметры RSA. Он не создаёт
и не импортирует ключ, не использует software/DPAPI fallback. Поведение открытия
существующего ключа основано на
[Microsoft CngKey.Open](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cngkey.open?view=net-10.0).

RSA-OAEP-SHA256 защищает только 32-байтный pepper. Фиксированный frame содержит
domain/version, ожидаемый 32-байтный context digest и секрет. Проверяются размер,
ключ, версия и привязка; временный расшифрованный буфер очищается при любом исходе.
Ожидаемые SPKI и digest берутся из доверенного состояния, а не из самого envelope.

Шифрование обеспечивает конфиденциальность и привязку, **не легальность записи**:
владеющий публичным ключом может зашифровать новый известный pepper. Согласованная
замена pepper/verifier и возврат старой копии требуют отдельно проверенного
хранилища, signed revisions и anti-rollback. Успех software RSA-теста не означает
приёмку TPM, прав Windows-службы или физического восстановления.

Перед включением нужны: доверенный enrollment, постоянный учёт попыток и сессий,
TPM provisioning/attestation и service ACL, trusted time, sealed high-water state,
Windows-испытания и recovery на другом ПК. Этот этап не меняет срок lease
и не разрешает автономные денежные операции.
