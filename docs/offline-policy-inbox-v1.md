# Неактивная очередь подписанных offline-политик

`OfflinePolicyInboxService` сохраняет проверенный Cloud-пакет в PostgreSQL,
включая ограничивающую политику без lease. Это приём и сохранение артефакта,
но не его защищённое применение: все записи имеют единственный статус
`pending_protected_acceptance`. HTTP, worker и Windows runtime эту очередь
не используют для входа или выполнения команд.

## Формат и проверка

`SignedOfflinePolicyDeliveryV1` содержит строгие claims, их SHA-256, ID доверенного
ключа и PureEd25519-подпись. Подписываются canonical JSON bytes с отдельным
префиксом `aurum-edge-policy-delivery-v1` и нулевым разделителем. Подпись lease,
digest либо иной режим EdDSA не являются подписью доставки.

Claims включают обязательные версию/issuer/audience, UUID доставки, положительный
64-битный `delivery_sequence`, точные tenant/branch/node/register/activation,
writer epoch и capability, TPM binding, policy, UTC-время Cloud и поле `lease`.
Последнее обязательно присутствует, но может быть `null`: отзыв должен
доставляться даже тогда, когда новый lease выдавать нельзя.

`delivery_sequence` упорядочивает сообщения одного enrollment отдельно от
`tenant_access_revision`. Например, `active` → `archived` допускается при той же
версии policy, но более новом номере доставки. Подписанная tenant policy сохраняет
все состояния, включая запрещающие; сохранение не снимает ограничения.

Вложенный lease проверяется отдельной подписью и отдельно предоставленным
реестром ключей. Scope, устройство и ревизия должны совпадать с пакетом;
lease должен быть уже выпущен и ещё не просрочен в момент выпуска пакета.
Его команды не могут превосходить доставленную policy. Ни lease, ни пакет
не содержат Cloud-пароля, refresh-токена, локального секрета или pepper.

Публичные ключи задаёт доверенный оператор, вне входного пакета. Повторные ID,
одинаковый ключ под разными ID и неизвестный ключ отклоняются. Нет автообнаружения
ключей, загрузки их по URL и доверия ключу из входного JSON.

## Сохранение и повторы

Подпись и совпадение с ожидаемым устройством проверяются до SQL. Tenant-контекст
берётся из доверенной конфигурации назначения. Repository проверяет существующие
current writer activation/epoch/stream обычным RLS SELECT; импорт не создаёт
enrollment. Частная таблица `sync_node` остаётся недоступной `aurum_app`; FK
проверяет существование и scope узла, но не его актуальный статус либо TPM.

Доставки одного назначения сериализуются advisory lock. Таблица
`offline_policy_inbox` имеет tenant RLS, неизменяемые строки, trigger audit,
уникальность номера и scope FK. Приложению доступны только SELECT/INSERT;
UPDATE/DELETE запрещены, в том числе триггером для владельца.

Точный повтор возвращает прежнюю запись без изменения latest. Повтор ID или
номера с другим содержимым отклоняется. Новая запись не может уменьшать номер,
версию policy или Cloud-время относительно последней сохранённой записи.
Пропуски номеров допустимы: пакет содержит полный снимок policy, а не финансовую
операцию. Квитанция возвращается только после commit и закрытия SQL-контекста.
Ошибка ответа после commit требует точного повтора, а не нового номера.

При перечитывании проверяются подписи, строгая схема и совпадение всех
индексированных полей с signed payload. Данные остаются после переподключения
к БД; receipt и факт хранения не являются разрешением на работу.

## Служебный импорт

Из каталога `backend`, в настроенном процессе с обычным `DATABASE_URL_APP`:

```text
python -m app.domains.sync.offline_policy_import --delivery delivery.json --trusted-config trusted-import.json
```

`trusted-import.json` готовит доверенный оператор из проверенного enrollment.
Он содержит `expected_scope`, `expected_device`, отдельные массивы `policy_keys`
и `lease_keys`; каждый ключ — UUID4 `key_id` и 64 hex-символа `public_key`.
Scope/device имеют формат контракта. Реальные Cloud public keys и проверенный
TPM binding необходимы: тестовые ключи не являются provisioning. Конфигурацию
нельзя создавать из присланного пакета или давать пользователю изменять в
будущем установщике.

Каждый файл ограничен 64 KiB. DB-пароли и private signing keys не передаются
аргументами. Команда выводит только результат сохранения либо общий отказ,
не payload и не внутренние диагностики. Автоматический HTTP/Windows-импорт
ещё не подключён.

## Что ещё требуется

SQL-порядок и подпись **не защищают от восстановления всей старой БД**.
Snapshot enrollment не удерживает lifecycle lock: отзыв сразу после его чтения
может оставить новую pending-запись, но она ничего не разрешает. Перед будущим
применением необходимо повторно проверить lifecycle, writer и устройство под
доверенной сериализацией.

Защищённое принятие обязано закреплять независимо от SQL как минимум точный
enrollment/device, `delivery_sequence`, digest policy и её ревизию, включая
ограничивающие пакеты без lease. Одна `tenant_access_revision` недостаточна для
изменения lifecycle при той же версии. Нужны аппаратный монотонный источник,
crash recovery и проверка на реальном Windows-ПК; `WindowsTpmSecretProtector`
даёт шифрование, но не anti-rollback.

Пока эти условия не выполнены, положительный auth runtime остаётся DenyAll.
Аппаратная реализация, production key provisioning и автоматическая доставка
будут отдельными изменениями. Миграция 0158 проверяется upgrade на dev;
downgrade разрешён только в одноразовой тестовой БД.
