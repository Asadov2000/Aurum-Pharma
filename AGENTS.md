# Aurum Pharma - правила для AI-ассистентов

Этот файл - единственный источник постоянных правил для Codex, Claude и других
AI-агентов. Читай его перед работой. Загружай остальные документы только в части,
которая относится к текущей задаче.

## 1. Проект и источники истины

Aurum Pharma - SaaS для автоматизации аптек Таджикистана. Язык пилота - русский,
валюта - TJS. Backend: FastAPI/PostgreSQL/Redis/Celery/MinIO. Frontend:
React/TypeScript/Vite. Точные версии всегда смотри в `backend/pyproject.toml`,
`frontend/package.json`, lock-файлах и Docker-конфигурации, а не дублируй здесь.

Приоритет источников:

1. Реальный код, миграции и тесты - текущее поведение.
2. Принятые `docs/adr/*.md` - обязательные архитектурные решения.
3. `docs/spec-v3.md` - продуктовый замысел и границы этапов.
4. `docs/db-schema-v2.md` - проектная схема БД.
5. `docs/handoff.md` - исторический план, не доказательство реализации.

Если документы расходятся с кодом, не угадывай: следуй коду для текущего
поведения, перечисли расхождение в отчете и предложи отдельную синхронизацию.

## 2. Неприкосновенные правила

- Общую dev-БД нельзя удалять, очищать или пересоздавать. На ней разрешен только
  `alembic upgrade`; `alembic downgrade` запускай лишь в специально созданной
  одноразовой тестовой БД. Сид-аккаунты и шаблоны ролей вручную не пересоздавай.
- Все tenant-таблицы имеют `tenant_id` и RLS. Обычные запросы используют
  `aurum_app`; обход RLS для developer/administrator - только через
  `aurum_support`. Не имитируй обход RLS флагами Python.
- Завершенную продажу нельзя изменять. Исправление или возврат - новая связанная
  операция. Audit-log остается триггерным и иммутабельным.
- Не меняй стек, модульный монолит или зависимости без явного согласования.
- Не хардкодь секреты и не выводи их в команды, diff или логи. Не логируй email,
  телефоны, пациентов, рецепты, чеки и закупочные цены.
- Refresh-токен остается только в `httpOnly` cookie, access-токен - только в
  памяти приложения. Sensitive-токены запрещены в `localStorage`.
- Permissions не хранятся списком в JWT. CORS с credentials использует только
  явные origins, methods и headers. URL разбираются стандартным парсером.
- Без прямого запроса не изменяй UI-эталоны: `SalesPage`, состояния
  `CatalogPage`, `DashboardPage`, `BillingPage`, `ReceiptPrintModal` и
  `OnboardingPage`.
- Никогда не выполняй `git reset --hard`, `git push --force`, удаление миграций
  из `main`, рекурсивное удаление или запись вне workspace.

## 3. Рабочий процесс

1. Определи тип задачи: ответ/review - только чтение; изменение - реализация;
   диагностика - причина без исправления, если исправление не попросили.
2. Перед изменением сделай короткий recon: `git status`, `rg`, затем читай только
   нужные диапазоны файлов и релевантные разделы документации.
3. Для задачи больше примерно 100 строк дай план из 3-5 шагов. Предлагай один
   лучший вариант и кратко объясняй выбор.
4. Вноси минимальный связный diff. Не делай попутные рефакторы и не исправляй
   чужие изменения. Новые идеи перечисляй отдельно.
5. После первой ошибки установи причину. Если один и тот же проверяемый шаг
   падает дважды подряд по одной причине, остановись и сообщи блокер.

Делай разумные обратимые предположения сам. Задай не больше одного вопроса,
только если без ответа нужны секреты, внешнее подтверждение или необратимый
выбор. Зависимости не устанавливай без согласования.

## 4. Агенты и экономия контекста

- Не создавай субагентов для простых, последовательных или тесно связанных задач.
- Используй максимум 2-3 субагента только для независимых частей, которые реально
  выполняются параллельно. Называй их должностями: `Архитектор безопасности`,
  `Backend-инженер`, `QA-инженер`.
- Не поручай нескольким агентам одинаковый recon. Основной агент ведет критический
  путь, проверяет результаты и закрывает задачу end-to-end.
- Не читай целиком большие документы и логи. Сначала найди нужное через `rg`,
  затем открой небольшой контекст. На успехе сохраняй только итог и числа;
  подробный лог показывай только для ошибки.
- Не повторяй в ответах уже известное описание проекта и не создавай отчеты после
  каждого действия. Для долгой работы давай короткие содержательные обновления.

## 5. Архитектурные границы

Backend-домен: `models.py` -> `repository.py` (только БД) -> `service.py`
(бизнес-логика без HTTP) -> `router.py`; внешние схемы находятся в `schemas.py`.
Frontend-фича хранит API, queries, types и компоненты внутри
`frontend/src/features/<domain>/`; общие примитивы - в `components/ui`.

Не ослабляй существующие formatter/linter/typecheck-конфигурации. Python-код
остается полностью типизированным; `Any` и `type: ignore` требуют объяснения.
TypeScript остается strict; формы делаются через React Hook Form + Zod,
не через набор `useState`; `any` и `console.log` запрещены. Не monkey-patch
базовые классы SQLAlchemy. Каждая миграция обязана иметь рабочий `downgrade()`.

Деньги: `NUMERIC(14,2)` и TJS. Время: UTC в `TIMESTAMPTZ`, отображение в часовом
поясе аптеки. Гибкий JSONB валидируется Pydantic-схемой. Новая tenant-таблица
обязана получить RLS, audit-поля, миграцию и тест изоляции. Новый домен минимум
покрывается happy path, важным бизнес-правилом и tenant-изоляцией.

## 6. Проверки по риску

- Только docs/prompt: `git diff --check`; тесты приложения не нужны.
- Backend: затронутые pytest-тесты с `-q`, затем `ruff`, `black --check`, `mypy`.
- Frontend: затронутые Vitest-тесты с компактным reporter, затем `typecheck` и
  `lint`; при изменении сборки также `pnpm build`.
- Auth, RLS, миграции, POS, общий middleware/router или cross-stack изменение:
  полный backend pytest, полный Vitest и соответствующие Playwright flow.
- Перед релизом или широким изменением: полный pytest + Vitest + E2E; перед E2E
  выполнить `docker compose restart frontend`.
- Миграция: проверить `alembic upgrade head` на dev. Ее `downgrade()` проверять
  только на одноразовой тестовой БД, никогда на общей dev-БД.
- Всегда: `git diff --check`, просмотр финального diff и отсутствие случайных
  файлов. Пока полный CI не реализован, необходимую полную матрицу запускай
  локально. После его реализации локально допускаются целевые тесты, а полный
  набор обязан пройти в CI.

## 7. Git

Изменения выполняются в отдельной ветке `codex/<краткая-задача>` и попадают в
`main` только через pull request после успешного обязательного `CI gate`. Прямой
push в `main`, force-push и удаление `main` запрещены. Один Conventional Commit
соответствует одной логической задаче. Сохраняй грязное рабочее дерево
пользователя. Добавляй только точные файлы через `git add -- <paths>`;
`git add .` запрещен. После зеленой реализации делай commit, push и создавай или
обновляй pull request. Для анализа, плана или review без изменений commit не
создавай.

## 8. Общение и итог

Отвечай по-русски, прямо и без лишней похвалы. Пользователь не разработчик:
незнакомый термин коротко поясняй при первом употреблении. Не перегружай деталями.

Финальный отчет:

1. Что попросили или что было сломано.
2. Что сделано.
3. Что проверено и результаты.
4. Что закоммичено и выполнен ли push.
